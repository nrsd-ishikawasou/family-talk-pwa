- version.json の形（`ft.release/1`。第2章 12。動いているサーバーの `/version` の応答 `ft.version/1`（第2章 5.11）とは別の形）：

```text
{ "v": 1, "server": {"version": "1.2.3", "released_at": "2026-…", "image_digest": "sha256:…"},
  "web": {"version": "1.2.3"}, "ft": {"version": "1.2.3", "sha256": {"linux/amd64": "…", "linux/arm64": "…"}},
  "android": {"version": "1.2.3", "code": 10203, "min_sdk": 26,
     "apks": {"universal": {"url": "/dl/app.apk", "sha256": "…"}, "arm64-v8a": {...}, "armeabi-v7a": {...}},
     "signing_cert_sha256": ["<現在>", "<旧（交代の後）>"], "released_at": "…"},
  "boundary": "1.4.0", "min_app": {"web": "1.0.0", "android": "1.0.0"}, "notes_url": "https://…/releases/tag/v1.2.3",
  "revoked_digests": ["sha256:…"] }
```

- `revoked_digests`：誤りのある版・鍵の事故で取り消したイメージの digest（第1章 18.3）。`ft update` と自動の更新はこの digest を取らず、動いているイメージが該当すれば管理者に知らせる（全体実装設計書 8）。
- 家族のサーバーの `/dl/version.json` はイメージと同じ版を返す（イメージを更新すると APK の版の情報も上がる）。公開リポジトリの Release の version.json は最新の版。管理者の画面は Release のものを見て「新しい版」を知る（第11章 10）。

### 3.1 `ft` のイメージの検証

`ft`（ホストの更新。第11章 3.4、10）は、イメージを入れ替える前に次の順で確かめる。どれかが通らなければ入れ替えない。

1. 新しいイメージの digest の参照の成果物（OCI Image 1.1 の referrer）の一覧を GHCR から読む。cosign v3 は署名をこの形で置く。GHCR は Referrers API に応じないので、OCI の配布の仕様の代わりの形（tag `sha256-<hex>` の索引）から読む（調査資料 調査 H 1.15）。
2. 一覧から Sigstore の bundle を 2 つ取る。cosign の署名と、ビルド証明（SLSA v1.0 の provenance）である。どちらかが無ければ失敗。
3. 信頼の起点（trusted root）を、Sigstore の TUF のリポジトリから取る（第1章 4.2）。TUF は信頼の起点の更新を署名で守るので、取得の経路を信用しなくてよい。最初の root は `ft` に埋め込む。取った物は `/etc/family-talk/tuf/` にキャッシュし、取れない時はキャッシュで検証する。
4. 2 つの bundle を検証する。証明書の身元は本リポジトリの release のワークフロー（タグ `v*`）、発行者は `https://token.actions.githubusercontent.com`。透明性ログの記録（bundle の中の inclusion proof）を 1 つ以上求める。
5. 署名の対象とビルド証明の subject の digest が、入れ替えるイメージの digest と一致することを確かめる。ビルド証明の種類は SLSA provenance v1。
6. version.json の `revoked_digests` に含まれないことを確かめる。

- 部品は sigstore-go と go-containerregistry（第14章 5.2）。cosign の CLI は同梱しない（`ft` は 1 本の静的なバイナリ）。
- release のワークフローは、ビルド証明を registry にも置く（第14章 11.2）。

## 4. Android の署名（DD-13-4、DD-13-5）

### 4.1 鍵

|項目|値|
|---|---|
|方式|EC P-256（apksigner が対応。小さく HSM で扱いやすい）|
|有効期間|30 年|
|保管|ハードウェアのトークン（PKCS#11。非エクスポート）。暗号化したバックアップ（age の形式。パスフレーズは別に保管）を 2 か所以上に分散（第1章 18.3）|
|指紋|証明書の SHA-256 を README、version.json、`assetlinks.json`（家族のサーバーが配る）に|
|署名の方式|v2 + v3（`--v1-signing-enabled false --v2-signing-enabled true --v3-signing-enabled true --rotation-min-sdk-version 28`）。v4 は不要|
|署名の場所|保守者の機器。`apksigner sign --ks-type PKCS11 --ks-provider-class sun.security.pkcs11.SunPKCS11 --ks-provider-arg <設定>`|
|交代|`--next-signer` と `--lineage`。新しい指紋を version.json と `assetlinks.json` の配列に追加（旧も残す）。開発者の確認の制度に追加の登録。アプリは自己更新で受け入れ（第9章 10 の照合は配列のどれか）|

### 4.2 手順（リリースのたび）

1. CI が未署名の APK（3 種）とビルド証明を出す（第14章 11.2）。
2. 保守者が成果物を取得し、ビルド証明を検証（`gh attestation verify`）。
3. 署名（4.1）。
4. 一致の検証：署名を除いた中身が CI の成果物とバイト一致（署名の複製の道具。build-tools の版の相性は【未確認】。一致しなければ公開しない）。
5. `apksigner verify --print-certs -v` で指紋を確認。
6. Release に資産として載せ、`.sha256` を添える。
7. イメージの `/dl/app.apk`：イメージは CI で組むため、保守者の機器で署名した APK を後からイメージに差し込めない。**CI の後段が、Release の署名済み APK を検証（sha256 と指紋）して取り込み、イメージを組んで署名する**（第14章 11.2 の後段）。リリースは 2 段になる（6.3 の 7〜9）。
8. `assetlinks.json` の中身（パッケージ名と指紋の配列）はイメージの設定に入り、家族のサーバーが配る。

### 4.3 利用者の検証（手順書）

- Android の設定でアプリの署名の指紋を見るか、`apksigner verify --print-certs` の結果と README の指紋を照合。自己更新はシェルが照合する（第9章 10）。

## 6. 版とリリース（DD-13-8）

### 6.1 版

- SemVer 2.0.0。major：境界の破壊的な変更またはデータの形式の互換のない変更。minor：機能の追加。patch：修正。1.0.0 まで 0.y.z（破壊的な変更を minor で許す）。
- 全体で 1 つの版（第14章 DD-14-8）。Android の `versionCode` は `major*10000 + minor*100 + patch`。
- タグ `vX.Y.Z`（署名コミットのタグ）。Release は immutable。

### 6.2 互換の期間（第1章 DD-1-14）

|組み合わせ|判定|振る舞い|
|---|---|---|
|サーバーが新しく、アプリが古い|アプリの公開日がサーバーの公開日の 12 か月前より後なら支援|支援の範囲なら動き、新しい版があれば version.json による更新の案内（DD-13-7）。範囲外は `NET-006` で更新の画面|
|アプリが新しく、サーバーが古い|サーバーの公開日がアプリの公開日の 6 か月前より後なら支援|支援の範囲なら新しい機能を落として動く。範囲外は「管理者に更新を頼んでください」|

- 判定は version.json の `released_at` と `/version` の `released_at`。サーバーの側の判定は `min_app`（platform ごとの最低の版）に置き換えて行う。`min_app` は配布の道具が公開の時に決める。過去の Release のうち、今回の公開日の 12 か月前より後に出た最も古い版である（無ければ今回の版）。api は要求の `X-Family-Talk-App` の版が `min_app` を下回れば `NET-006` を返す。
- `Deprecation` と `Sunset` のヘッダは廃止する経路の告知に限る（第2章 10）。古いアプリへの告知には使わない。支援の終わりの日はサーバーの今後の更新で決まり、前もって決まらないため。
- 境界の版（`boundary`）は SemVer。境界の major が違えば支援の範囲でも `/v1` と `/v2` の並行（第1章 8.3）。

### 6.3 リリースの確認の一覧

|順|確認|

## 8. 失敗の扱い

|失敗|扱い|
|---|---|
|APK の一致の検証が失敗（再現できない）|公開しない。差分を調べて CI を直す（公開のアプリ配布の仕組みの再現可能ビルドの知見：時刻、最適化、PNG。第14章の調査）|
|署名のトークンが使えない|バックアップから復元（第1章 18.3）。復元できなければ鍵の事故の手順（新しい鍵、lineage を使えないので全構成員が再インストール。H-13-1）|
|GHCR または Release が使えない|公開を待つ。家族のサーバーの運用は続く|
|Release の資産を間違えた|immutable のため消せない。新しい patch の版を出し、ノートに注記|
|開発者の確認の制度の登録が遅れた|手順書の「上級者の手順」で構成員が入れる（24 時間）|
|名前が決まらないまま公開|仮の名前で 0.y.z を公開しない（1.0.0 の前に決める。6.1）|
|security.txt の期限切れ|CI の警告。更新の patch|

## 10. 本章で宣言する既知の制約

|番号|既知の制約|理由|緩和|
|---|---|---|---|
|H-13-1|署名鍵とそのバックアップを全部失うと、新しい鍵では更新を配れず、全構成員が再インストールになる|OS の署名の仕組み|分散したバックアップ、第1章 18.3|
|H-13-2|開発者の確認の制度の登録は NRSD の費用と身元の確認に依り、未登録の期間は構成員に手順が増える|OS の提供者の制度|【要確認】R-1、手順書|
|H-13-3|イメージの `/dl/app.apk` は署名済み APK を取り込むため、リリースが 2 段になり時間がかかる|署名を CI の外で行う|確認の一覧|
|H-13-4|配布物の取得と更新の確認は公開リポジトリの運営者の設備に依る|第14章 H-14-6|家族のサーバーの運用は続く|
|H-13-5|利用者が指紋や digest を照合しなければ、偽の配布物を見分けられない|利用者の操作|自己更新と `ft` は自動で検証。手順書|

［未確認］：署名の複製の道具と build-tools の版の相性、無人更新の targetSdk の下限（Android 16・17）、開発者の確認の制度の日本の時期と限定配布の上限。
