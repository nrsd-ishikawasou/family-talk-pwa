## 本書の位置付け

- 概要設計書 第7章「通知」を詳細化する。経路、購読、中身と見せ方、規則、着信の通知、届かない時、システムの知らせ、初回の案内を定める。設計計画書 D-10-2 の【要設計】（配布元 2 系統の遅延・電池・エンドポイント）は本章で設計し、実測の項目を 14 に残す。
- 通知の中身は第2章 7、経路は第2章 5.8、通知の復号は第12章 5.8、シェルの受信は第9章、ミュート（人）は第4章 5.10、子どもの時間帯は第3章 9.2。
- 準拠：RFC 8030（TTL、Urgency、Topic）、RFC 8291、RFC 8292、W3C Push API、WHATWG Notifications API、W3C Badging API、UnifiedPush の仕様 AND_3.1.0、OS の提供者の通知の文書（調査 I-01、I-02、I-04、I-13）、一般的な通信アプリの通知の慣行（調査資料 準拠の調査 2 §6、準拠の調査 3 §4）、法務調査 L-3、L-11。

## 3. 経路（DD-7-1、DD-7-2）

|端末|経路|購読の形|
|---|---|---|
|iPhone（ホーム画面のウェブアプリ）|Web Push。OS の提供者の中継|`PushSubscription`（endpoint、p256dh、auth）。宣言型は `declarative: true`（iOS 18.4 以上。`pushManager.subscribe` の応答で判定）|
|PC（ブラウザ）|Web Push。ブラウザの提供者の中継|同上。閉じていても届くのは一部のブラウザ（手順書）|
|Android（シェル）(ii)|UnifiedPush → OS の提供者の中継の Web Push のエンドポイント（VAPID）|配布元が返す endpoint（Web Push の形）。公開の値だけで動く（NRSD の秘密を配らない）|
|Android（シェル）(i)|UnifiedPush → 家族のサーバーの受け口（api）→ 常駐の WebSocket → シェル|endpoint は `https://<サーバー>/up/<token>`。token はシェルの登録で api が発行|

### 3.1 家族のサーバーの受け口（(i)）

- `POST /up/{token}`（無認証。UnifiedPush の push server のエンドポイント。RFC 8291 の暗号文をそのまま受ける。4,096 バイトまで）：api が端末のメールボックスに入れ、常時接続があれば即時に送る。TTL（ヘッダ）で保持。既定 86,400 秒、着信は 60 秒。
- `wss://<サーバー>/api/v1/up/ws`：シェルがシェルのトークン（第2章 4.4）で接続。接続時に未配信を順に送り、シェルは ack を返す。ping 60 秒（シェルの電池のため長め）。切れたらシェルが指数の待ちで再接続（第9章）。
- 1 端末 1 接続。保管は端末ごとに 1,000 件まで。

### 3.2 送信（api）

- 購読ごとに RFC 8291（aes128gcm）で暗号化し、RFC 8292（VAPID。`aud` は中継の origin、`exp` 12 時間、`sub` は `https://<サーバー>`）で署名して POST。ヘッダは第2章 DD-2-8。
- 送る条件：受け手の端末が WebSocket で開いていない（開いている端末にはイベントで届く。ただし着信は開いていても送る）。
- 同じトークの連続（10 秒以内）は `Topic` で中継が置き換える。

## 5. 中身と見せ方（DD-7-3、DD-7-4）

### 5.1 表示の流れ

|端末|流れ|
|---|---|
|iPhone、PC（SW）|push → `event_id` と `room_id` → 暗号文を取得（`GET /rooms/{id}/events/{eid}`）→ MLS の状態で復号（IndexedDB。Web Locks `mls:<room_id>` で画面と排他）→ `showNotification(title, {body, tag: room_id, renotify: true, icon, badge, data})` → `setAppBadge(未読の合計)`。10 秒で復号できなければ汎用の本文。通知の中身の `sender_id` から表示名（端末のコピー）を引く|
|iPhone 18.4 以上（宣言型）|中継が `notification` の JSON で先に表示（title: トーク名または送信者、body: 「○○さんからメッセージ」、navigate: `/r/<room_id>`、tag、app_badge）。SW の `push` が復号して `showNotification` を同じ tag で置き換える|
|Android（シェル）|配布元 → connector → シェルの `onMessage` → 復号用の非表示の WebView（`/notify.html`。画面の部品を含まない復号の入口だけのバンドル。全体実装設計書 2.2）に `event_id` を渡す（10 秒）→ 結果で通知（チャネル、グループ、返信のアクション）。失敗は汎用の本文。第9章|

### 5.2 内容の表示（設定）

|設定|title|body|
|---|---|---|
|名前と本文（既定）|送信者（1 対 1）／トーク名（グループ）|「送信者: 本文の冒頭 100 文字」。写真は「[写真]」、動画「[動画]」、スタンプ「[スタンプ]」、ファイル「[ファイル: 名前]」、音声「[音声メッセージ]」、位置「[位置情報]」、投票「[投票] 質問」、予定「[予定] 題」|
|名前のみ|同上|「新しいメッセージ」|
|なし|家族の名前|「新着メッセージがあります」|

- サムネイルは通知に出さない（復号した画像の添付は手間と漏れのため。第2巡で検討）。
- 通知の件数：同じトークは 1 件に置き換え、「3 件の新着」の本文にする。

### 5.3 バッジ

- 未読の合計（全トーク。通知なし送信も数える。ミュートのトークも数える（設定で除外可））。サーバーが `/rooms` の未読から計算して通知の `app_badge` に入れ、SW とシェルが `setAppBadge` する。既読で減る（イベントを受けた端末が更新。閉じている端末は次の通知で更新）。

### 5.4 通知からの返信

- Android：シェルの直接返信 → 非表示の WebView で暗号化 → `POST /rooms/{id}/events`。既読は付けない。
- PC：`actions: [{action: "reply", type: "text"}]`（対応ブラウザだけ。`Notification.maxActions` で判定）。
- iPhone：なし（通知のタップでトークへ）。

## 6. 規則（DD-7-5、DD-7-6）

|規則|所在|サーバーの判定|端末の判定|
|---|---|---|---|
|着信を受けない|`/me/settings`|発信者に `CALL-005`。通知を送らない|—|
|人のミュート|`/me/settings.muted_users[]`|送らない|鳴らさない|
|トークのミュート（期間）|`/rooms/{id}/me.mute_until`|送らない（期限まで）。メンションは `mentions` を見て送る（設定 `mention_overrides_mute`、既定 ON）|同じ|
|一時停止|`/me/notifications/pause`|送らない（期限まで）。着信は送る|同じ|
|子どもの時間帯|保護者の設定（第3章）|送らない（時間帯）。着信とメンションは送る|同じ|
|通知なし送信|イベントの `silent`|送らない|バッジだけ更新|
|開いている端末|WebSocket の接続|送らない（着信を除く）|—|

- サーバーの判定は、設定をエンベロープ暗号文から api が復号して行う（第12章 6.2。api は KEK を持つ）。
- 一時停止の「翌朝 8 時まで」は端末の時刻帯（設定に tz を持つ）。

## 7. 着信の通知（DD-7-7）

|端末|着信|止める|
|---|---|---|
|iPhone|15 秒ごとに 4 回の push（`kind: call`、同じ tag）。SW が「○○さんから着信」「応答するには開いてください」。各回に OS の音。アプリが前面なら呼び出し画面（第6章）|応答・拒否・取消・60 秒で、最後の push（`kind: call_end`）を「不在着信」に置き換え|
|Android|シェルが CallStyle の着信（全画面、着信音の繰り返し、60 秒で自動停止）。第9章|`kind: call_end` で消す|
|PC|通知 + アプリが開いていれば呼び出し画面と音|同上|

- グループ通話の開始は着信ではなく通常の通知（「○○さんが通話を始めました」。ミュートの規則に従う）+ トークのバナー。

## 8. 届かない時（DD-7-8）

- 起動・前面化・接続の復帰で `/sync?since`（第2章 5.9）。通知が 1 件も届いていなくても全部の新着と不在着信が並ぶ。
- 購読の失効は 4。中継の障害は第1章 12（知らせない。検知できない）。
- 常時接続（Android (i)）：シェルが再接続（指数、最大 5 分）。Android 15 の強制停止は `wasForceStopped()` で検知し、次の起動で案内（第9章）。
- 端末が長く現れない：購読は消さない（中継が 410 を返すまで）。90 日で leaf の Remove（第12章 5.2）。

## 13. 失敗の扱い

|失敗|扱い|
|---|---|
|SW が暗号文を取得できない（圏外）|汎用の本文「○○さんからメッセージ」|
|SW が復号できない（鍵のバックアップに未登録）|汎用の本文。画面を開いた時に鍵の転送を求める（第12章 13）|
|中継が 413（大きすぎ）|起きない（中身は小さい）。起きれば記録|
|中継が 429|Retry-After の後に 1 回|
|VAPID の鍵が交代した|端末は `GET /me/push/vapid` の版で再購読（第12章 10）|
|シェルの非表示 WebView が 10 秒で応答しない|汎用の本文。シェルは WebView を作り直す|
|Android の全画面の許可が拒否|ヘッドアップの通知で着信（鳴る）。設定への誘導|
|常時接続が OS に止められた|再接続。強制停止は起動時に案内|
|通知の許可が取り消された（iPhone の規則の違反）|起きない設計（必ず表示）。起きれば設定の画面で再許可の案内|

## 14. 本章で宣言する既知の制約

|番号|既知の制約|理由|緩和|
|---|---|---|---|
|H-7-1|プッシュ配信サービスは、いつどの端末に通知が送られたか（メタデータ）を知る|中継の仕組み|本文を送らない。明示（第12章 8）|
|H-7-2|iPhone の着信は鳴り続けられず、4 回の通知の後は不在になる|OS の仕様（I-01）|繰り返しと呼び出し画面|
|H-7-3|iPhone は通知の音を選べず、通知から直接に応答・返信できない|OS の仕様|—|
|H-7-4|PC のブラウザを閉じている間は、一部のブラウザでしか通知が届かない|ブラウザの仕様（I-13）|手順書|
|H-7-5|常時接続は製造者の省電力の実装により止まることがある|OS と製造者|電池の最適化の除外、2 系統、起動時の同期|
|H-7-6|OS の提供者の中継（Android (ii)）の着信の遅延は Doze の状態に依る|中継の仕様|(i) への切り替えの勧め|
|H-7-7|通知の本文の表示は端末の復号に依り、復号できない時は汎用の本文になる|E2EE|10 秒の待ちと汎用の本文|

［要実測］：(ii) の着信の遅延（Doze）、(i) の電池、SW の復号の時間、シェルの復号の時間、全画面の着信の許可の既定（サイドロード）、iPhone の 4 回の通知の挙動（置き換えと音）。
