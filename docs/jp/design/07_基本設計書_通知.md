## 3. 経路（DD-7-1、DD-7-2）

|端末|経路|購読の形|
|---|---|---|
|iPhone（ホーム画面のウェブアプリ）|Web Push。OS の提供者の中継|`PushSubscription`（endpoint、p256dh、auth）。宣言型は `declarative: true`（iOS 18.4 以上。`window.navigator.pushManager` の有無で判定。購読は SW の registration の物と同じ）|
|PC（ブラウザ）|Web Push。ブラウザの提供者の中継|同上。閉じていても届くのは一部のブラウザ（手順書）|
|Android（シェル）(ii)|UnifiedPush で、OS の提供者の中継の Web Push のエンドポイント（VAPID）へ|配布元が返す endpoint（Web Push の形）。公開の値だけで動く（NRSD の秘密を配らない）|
|Android（シェル）(i)|UnifiedPush で、家族のサーバーの受け口（api）から常駐の WebSocket でシェルへ|endpoint は `https://<サーバー>/up/<token>`。token はシェルの登録で api が発行|

### 3.1 家族のサーバーの受け口（(i)）

- `POST /up/{token}` は無認証で、UnifiedPush の push server のエンドポイント。RFC 8291 の暗号文を 4,096 バイトまで、そのまま受ける。api は端末のメールボックスに入れ、常時接続があれば即時に送る。TTL（ヘッダ）で保持。既定 86,400 秒、着信は 60 秒。
- `wss://<サーバー>/api/v1/up/ws`：シェルが配布元の接続の秘密（`/up/register` の応答の `ws_secret`。第2章 4.4）で接続する。秘密に期限は無く、端末の取り消しで失効する。接続とメッセージの形は第2章 6.4。シェルのトークン（24 時間）に依らない。接続時に未配信を順に送り、シェルは ack を返す。ping 60 秒（シェルの電池のため長め）。切れたらシェルが指数の待ちで再接続（第9章）。
- 1 端末 1 接続。保管は端末ごとに 1,000 件まで。

### 3.2 送信（api）

- 購読ごとに RFC 8291（aes128gcm）で暗号化し、RFC 8292 の VAPID で署名して POST する。VAPID は `aud` が中継の origin、`exp` が 12 時間、`sub` が `https://<サーバー>`。ヘッダは第2章 DD-2-8。
- 送る条件：受け手の端末が WebSocket で開いていない（開いている端末にはイベントで届く。ただし着信は開いていても送る）。
- 同じトークの連続（10 秒以内）は `Topic` で中継が置き換える。`Topic` の値は第2章 DD-2-8（RFC 8030 の 32 文字の上限に収めた形）。

## 5. 中身と見せ方（DD-7-3、DD-7-4）

### 5.1 表示の流れ

|端末|流れ|
|---|---|
|iPhone、PC（SW）|push を受け、`event_id` と `room_id` から暗号文を取得する（`GET /rooms/{id}/events/{eid}`）。イベントの epoch が端末の状態より新しければ `GET /rooms/{id}/mls/commits?since_epoch` で Commit を先に取り込む。MLS の状態で復号し（IndexedDB。Web Locks `mls:<room_id>` で画面と排他）、`showNotification(title, {body, tag: room_id, renotify: true, icon, badge, data})` を出す。続いて `setAppBadge(未読の合計)`。10 秒で復号できなければ汎用の本文。通知の中身の `sender_id` から表示名（端末のコピー）を引く|
|iPhone 18.4 以上（宣言型）|サーバーは第2章 7 の宣言型の形（`mutable: true` を外側と `notification` の中の両方に。`notification` に title: 家族の名前、body: 「{name}さんからメッセージ」、navigate: `/r/<room_id>`、tag、app_badge、data: `ft.push/1`）を RFC 8291 で暗号化して送る。OS は復号した JSON を解析し、SW があれば提案の通知を持たせた `push` を発火する（`event.data` は null。`event.notification.data` が `ft.push/1`）。SW が時間内に復号して `showNotification` を出せば提案の通知は出ない。出せなければ OS が提案の通知を出す。SW が無い（削除された）時も提案の通知が出る|
|Android（シェル）|配布元、connector、シェルの `onMessage` の順に届く。シェルは復号用の非表示の WebView（`/notify.html`。画面の部品を含まない復号の入口だけのバンドル。全体実装設計書 2.2）に `event_id` を渡す（10 秒）。結果で通知を出す（チャネル、グループ、返信のアクション）。失敗は汎用の本文。第9章|

### 5.2 内容の表示（設定）

|設定|title|body|
|---|---|---|
|名前と本文（既定）|送信者（1 対 1）／トーク名（グループ）|「送信者: 本文の冒頭 100 文字」。写真は「[写真]」、動画「[動画]」、スタンプ「[スタンプ]」、ファイル「[ファイル: 名前]」、音声「[音声メッセージ]」、位置「[位置情報]」、投票「[投票] 質問」、予定「[予定] 題」|
|名前のみ|同上|「新しいメッセージ」|
|なし|家族の名前|「新着メッセージがあります」|

- サムネイルは通知に出さない（復号した画像の添付は手間と漏れのため。第2巡で検討）。
- 通知の件数：同じトークは 1 件に置き換え、「3 件の新着」の本文にする。PC は `tag` の置き換えで足りる。iPhone（18.2 以降）は `tag` で置き換わらないので、SW は同じ `tag` の前の通知を `getNotifications` で探して閉じてから出す。表示から 30 秒は閉じられない（26.4 以降）ので、30 秒の内に続けて届いた分は並ぶ（14 の H-7-8）。

### 5.3 バッジ

- 未読の合計（全トーク）。通知なし送信とミュートのトークも数える（ミュートのトークは設定で除外可）。サーバーが `/rooms` の未読から計算して通知の `app_badge` に入れ、SW とシェルが `setAppBadge` する。既読で減る（イベントを受けた端末が更新。閉じている端末は次の通知で更新）。

### 5.4 通知からの返信

- Android：シェルの直接返信を、非表示の WebView で暗号化して `POST /rooms/{id}/events` で送る。既読は付けない。
- PC：`actions: [{action: "reply", type: "text"}]`（対応ブラウザだけ。`Notification.maxActions` で判定）。
- iPhone：なし（通知のタップでトークへ）。

## 6. 規則（DD-7-5、DD-7-6）

|規則|所在|サーバーの判定|端末の判定|
|---|---|---|---|
|着信を受けない|`/me/settings`|発信者に `CALL-005`。通知を送らない|—|
|人のミュート|`/me/settings.muted_users[]`|送らない|鳴らさない|
|トークのミュート（期間）|`/rooms/{id}/me.mute_until`|送らない（期限まで）。メンションは `mentions` を見て送る（設定 `mention_overrides_mute`、既定 ON）|同じ|
|一時停止|`/me/notifications/pause`|送らない（期限まで）。着信は送る|同じ|
|子どもの時間帯|保護者の設定（第3章）|送らない（時間帯）。着信とメンションは送る|同じ|
|通知なし送信|イベントの `silent`|送らない|バッジだけ更新|
|開いている端末|WebSocket の接続|送らない（着信を除く）|—|

- サーバーの判定は、設定をエンベロープ暗号文から api が復号して行う（第12章 6.2。api は KEK を持つ）。
- 一時停止の「翌朝 8 時まで」は端末の時刻帯（設定に tz を持つ）。

## 7. 着信の通知（DD-7-7）

|端末|着信|止める|
|---|---|---|
|iPhone|20 秒ごとに 3 回の push（`kind: call`、同じ tag `call:<call_id>`。0 秒、20 秒、40 秒）。SW は受けるたびに `GET /calls/{id}` で `ringing` を確かめ、鳴っていれば「{name}さんから着信」「応答するには開いてください」を出す（遅れて届いた push で終わった通話を鳴らさない。終わっていれば `call_end` と同じ表示）。iOS 18.2 以降は 1 回ごとに別の通知として並び、毎回 OS の音が鳴る。tag の置き換えと `renotify` には頼らない（18.1 以前の置き換えと音は資料で決まらないが、頼らない形なので設計に効かない）。アプリが前面なら呼び出し画面（第6章）。通知のタップは `/call/<call_id>` を開き、`ringing` のままなら着信の画面（第6章 4.1）|応答・拒否・取消・60 秒で `kind: call_end`（`reason` は `answered`、`declined`、`cancelled`、`missed` のいずれか）。SW は `call:<call_id>` の通知を閉じ、`missed` なら「不在着信」、それ以外は音なし（`silent`）で「終わりました」を出す。閉じるのは表示から 30 秒の後（26.4 以降の規則。SW は自分が出した時刻を IndexedDB に持ち、30 秒に足りない分を待ってから閉じる。最長の待ちは 20 秒で、push の処理の持ち時間 30 秒の内）。アプリを開いた時も同じ通知を閉じる|
|Android|シェルが CallStyle の着信（全画面、着信音の繰り返し、60 秒で自動停止）。第9章|`kind: call_end` で消す|
|PC|通知 + アプリが開いていれば呼び出し画面と音。push は iPhone と同じ 3 回|同上（PC のブラウザは直ちに閉じられる）|

- グループ通話の開始は着信ではなく通常の通知（「{name}さんが通話を始めました」。ミュートの規則に従う）+ トークのバナー。

## 8. 届かない時（DD-7-8）

- 起動・前面化・接続の復帰で `/sync?since`（第2章 5.9）。通知が 1 件も届いていなくても全部の新着と不在着信が並ぶ。
- 購読の失効は 4。中継の障害は第1章 12（知らせない。検知できない）。
- 常時接続（Android (i)）：シェルが再接続（指数、最大 5 分）。Android 15 の強制停止は `wasForceStopped()` で検知し、次の起動で案内（第9章）。
- 端末が長く現れない：購読は消さない（中継が 410 を返すまで）。90 日で leaf の Remove（第12章 5.2）。

- `notice` は WebSocket のイベント（第2章 6.2）で、宛先の構成員の端末のうち開いていない端末へ通知もする（`ft.push/1` の kind `notice`。第2章 7）。通知の `event_id` は知らせの id で、端末は `GET /me/notices/{id}` で中身を取り、第10章 9.4 の文言で表示する。トークに残るものは `ft.event.system/1`。
- level の意味：`info` は知るだけでよい。`warning` は対処を勧める（放置してもすぐには壊れない）。`error` は失敗して処理が止まっている。端末は warning と error をバナーにも出す（第10章 12）。
- 宛先は発行の時に構成員へ解いて記録する（第2章 5.3 の `/me/notices`）。宛先の種類は、本人、全員、管理者、子の保護者、そのトークの構成員（active）の 5 つ。1 つの知らせの宛先は 1 つ以上の列で、同じ種類を何度でも並べてよい（本人を人ごとに）。表の「新旧の保護者」「他の保護者」「秘密分散の断片を持つ構成員」は、発行する側が構成員の識別子を知っているので本人の列で渡す。前の保護者と断片の持ち主は、発行の時点の保護者の表や srv-push の読める記録から解けないため。
- 1 つの事象の知らせは 1 回の発行で、表の宛先の全部を渡す。発行の側（srv-push）は宛先を構成員へ解いて和を取る。同じ人は 1 回にし（保護者が管理者でもある、新旧の保護者が同じ人、などの重なり）、状態が停止・削除・抹消の人を除く。記録は知らせ 1 行と宛先の人ごとに 1 行で、`notice` のイベントと通知は人ごとに 1 回。解いた宛先が 0 人でも知らせの行は書く（事象の記録と、同じ日の重複の抑えに要る。イベントと通知は無い）。同じ事象を宛先の種類ごとに分けて 2 回以上発行してはならない（次の重複の規則で 2 回目以降は何も出ず、その宛先に届かない）。
- 同じ事象の重複は（識別子、事象の鍵、日）で抑える。事象の鍵は表の「事象の鍵」の欄が正で、全行に書く。発行する側が欄の値を `:` で連ねて組む（時刻は RFC 3339、週や日数は 10 進の整数）。鍵の欄が「日」の行は鍵を空にし、同じ日に 1 件。
  - 即時の知らせ（1 回の事象に 1 件）の鍵は、その事象の記録の識別子（端末・求め・承認・引き継ぎ・構成員のどれか）。
  - 繰り返しの判定（監視の 5 分、1 時間、日次）で見つける知らせの鍵は、その事象の段（しきい値、残りの日数、`what`、版、始まった時刻、経過した週・30 日・年の数）。段が同じ間は 1 日 1 件、段が変われば新しい知らせ。7 日ごとに出す知らせは経過した週の数（`floor((今 − 立てた時刻) / 7 日)`）、30 日ごとは経過した 30 日の数、年 1 回は経過した年の数。
  - 日はサーバーの時刻帯（設定 `server.tz`。第11章 3.2）の暦日。
  - 抑えた知らせは何も出さない。記録の行、宛先、`notice` のイベント、通知、家族全員のトークの `ft.event.system/1` のどれも出ない。
- 停止された本人への知らせは出さない（セッションと購読を失効させるので届く経路が無い。第3章 8.1）。
