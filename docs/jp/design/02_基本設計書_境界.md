## 本書の位置付け

- 概要設計書 第2章「サーバーとクライアントの境界」を詳細化する。サーバー側とクライアント側の間のすべてのやり取りの種類、形、認証と認可、冪等性、版を本章が持ち、機能の章（第3〜7章）はここを参照して再掲しない（第1章 DD-1-1、4.3）。
- 本章の第1版は「一覧と規則」である。各経路の型（JSON Schema）の中身は api/ の文書（10）が正本であり、本章は経路と規則と番号を定める。機能の章が閉じた後の第2巡で、型とエラーコード表を確定する。
- 前提：第12章の結論により、本文と添付は端から端で暗号化される。サーバーが担うのは、配送サービスと認証サービス、端末宛メールボックス、鍵バンドルと鍵のバックアップの保管、URL の取得の代理で、検索の API は持たない。
- 準拠するものは次のとおり。
  - 語彙：公開のメッセージングのプロトコルの仕様 v1.19（調査資料 準拠標準 1）。イベントと状態、transaction id、関係、意図的メンション、既読 3 種、入力中、redaction、pusher、メディア、同期
  - 語彙：XMPP の拡張（アーカイブの照会、スロットの先行発行、権限の 2 層）、IETF MIMI の内容の形式の欄名
  - 形：OpenAPI 3.1、AsyncAPI 3.1、JSON Schema 2020-12、RFC 9457、RFC 6585 と ratelimit の草案
  - 形：RFC 9562、RFC 3339、RFC 6265bis（`__Host-`）、Fetch Metadata、RFC 8628、WebAuthn Level 3
  - 形：RFC 9745、RFC 8594、RFC 9110（Range、ETag）

### 2.2 扱うもの・扱わないもの

- 扱う：やり取りの分類と規則、認証と認可、資源の一覧（経路、動詞、認可、冪等、備考）。イベントの一覧と同期、通知の中身、通話のシグナリング、メディアの URL、配布と版。管理者の API、鍵の運搬、エラーコード表、レート制限、競合の規則、境界の文書と生成。

- すべて TLS の上（第12章 4）。平文の HTTP は caddy が HTTPS へ転送する。
- 要求の大きさの上限：JSON は 1 MiB、添付の追記は 1 回 64 MiB（初期値）。
- 応答の圧縮：前段の caddy の `encode` が zstd または gzip で圧縮する（既定の Content-Type の一覧。api は圧縮しない）。添付（暗号文、`application/octet-stream`）は一覧に無いので圧縮しない。
- 一覧の取得はカーソル方式（`?limit=&before=&after=`。識別子または pos）で、オフセットは使わない。JSON:API の Cursor Pagination プロファイルに倣う。
  - `limit` は 1〜100、既定 50。範囲の外は `NET-001`（上限に丸めない。端末の誤りを隠さないため）。
  - 結果は常に古い順に並べる。`after` は cursor の直後から `limit` 件、`before` は cursor の直前までの最後の `limit` 件を返す。両方を指定すればその間を `after` の側から返す。どちらも無ければ最新の `limit` 件を返す。
  - 応答の `has_more` は、進む向きにまだ要素があることを示す。`after` がある時は新しい側（`before` もあればその手前まで）、どちらも無いか `before` だけの時は古い側である。終わりの合図は `has_more` が false であることだけで、件数が `limit` より少なくても終わりとは限らない。
  - cursor の値は要素の識別子（UUIDv7）。構成員の一覧は利用者の識別子。キャッチアップの一覧（`/sync`、`/me/inbox`、`/me/keybackup`）は `since=<pos>`（`after` と同じ意味。省略は最初から。`/sync` だけは省略が初回）。MLS の Commit は `since_epoch`。

## 4. 認証と認可

### 4.1 セッション

- ログイン（パスキー、QR の承認、招待の受諾、管理者の作成のリンク。第3章）に成功すると、サーバーは端末に紐づくセッションを作る。応答で `__Host-session` の Cookie（Secure、HttpOnly、SameSite=Lax、Path=/）を返す。値は 256 ビットの乱数で、DB にはハッシュを置く。
- 寿命：第1章 DD-1-17（絶対 90 日、無操作 30 日。初期値）。無操作の期限は要求のたびに延びる。絶対の期限の 7 日前から、API の応答の `X-Session-Expires` で端末に知らせ、端末はパスキーで静かに作り直す（第3章）。
- 端末の識別子は Cookie に入れず、セッションに紐づく。端末は `GET /me/session` で自分の端末の識別子を得る。
- ログアウト、端末の取り消し、構成員の停止、セッションの署名鍵の交代で失効する。失効はイベント `session.revoked` で端末に届き、届かなくても次の要求が 401（`AUTH-002`）になる。
- 未認証で使える経路：
  - `/api/v1/invite-tokens/{token}`（GET。限られた情報）、`/api/v1/invite-tokens/{token}/accept`
  - `/api/v1/auth/*`（ログインの開始と検証）
  - `/api/v1/setup/*`（初回。第11章）
  - `/api/v1/family`（名前とアイコン。ログインの画面用）
  - 配布と版、`/health`

### 4.2 CSRF と cross-site

- 状態を変える要求（POST、PUT、PATCH、DELETE）には、2 つの条件がある。`Sec-Fetch-Site` が `same-origin` または `none` であること。`X-Requested-With: family-talk` を付けること。欠けていれば 403（`NET-003`）。
- `Sec-Fetch-Site` の無い要求（シェルのネイティブなど、ブラウザでない端末）は、`X-Requested-With` の確かめに頼る。独自のヘッダは CORS を許さない限り他のサイトから付けられない（OWASP の CSRF Prevention Cheat Sheet の、Fetch Metadata が無い時の互換側の扱い）。対象のブラウザ（第1章の最低要件）は `Sec-Fetch-Site` を必ず送る。
- Android のシェルの WebView はウェブアプリを家族のサーバーのオリジンから読むため same-origin。シェルのネイティブの要求（版の情報、通知の登録の補助）は、`X-Requested-With` を付ける。Cookie は WebView と共有せず、シェルは自分の短命トークンを `POST /auth/shell-token` で得る（第9章）。
- CORS は許さない（`Access-Control-Allow-Origin` を返さない）。

### 4.3 認可の 3 つの基本

|名|意味|判定|
|---|---|---|
|本人|自分の資源（`/me/...`、自分の端末、自分の設定）|セッションの構成員 = 資源の持ち主|
|トークの構成員|トークのイベント、添付、通話、MLS の配送|セッションの構成員がトークの現在の構成員。退出・削除の後は過去のイベントも取得できない（端末のコピーは残る）|
|管理者|`/admin/...`、招待の発行（設定で構成員にも許せる）、構成員の停止と削除|役割 = 管理者。複数可。自分自身の停止・削除・管理者の解除は最後の 1 人ならできない|

- トークごとの権限（作成者が構成員を外せる等。第4章）は「トークの構成員」の上に重ねる。
- 未承認の端末（第12章 5.5）は、鍵の運搬の経路と自分の端末の経路だけが使え、トークの経路は 403（`KEY-004`）。

### 4.4 WebSocket と通知と SFU

- WebSocket：`POST /auth/ws-token` で 60 秒のトークン（セッションと端末に紐づく）を得て、接続後の最初のメッセージ `{type: "auth", token}` で渡す。Origin は許可リスト（家族のサーバーのオリジン）。1 端末 1 接続（2 本目は古い方を切る）。
- 通知：購読の登録（5.9）は本人。中継からの配送は購読の秘密（RFC 8291 の `auth`）で端末だけが復号。
- SFU：通話の開始・参加で得るトークン（JWT。SFU の鍵で署名。`room = call_id`、`identity = device_id`、権限は publish/subscribe、5 分）。TURN の資格はトークンに含まれる（埋め込み TURN）。
- シェル：`POST /auth/shell-token` で 24 時間のトークンを得る（第9章）。使える経路は `/api/v1/up/register`、`/api/v1/me/devices/{id}/keys` の補助、版の情報の取得。
- 配布元の常時接続（`/api/v1/up/ws`）：`/up/register` の応答で得る「配布元の接続の秘密」（`ws_secret`。256 ビット。サーバーはハッシュだけを持つ）で接続する。期限は無く、端末の取り消し・ログアウト・購読の解除で失効する。シェルのトークン（24 時間）に依らないので、WebView を開かない端末でも接続が続く（第7章 3.1、第9章 5）。シェルは秘密を鍵保管庫で包んで置く（第9章 8）。

## 6. イベント（WebSocket と同期）

### 6.1 共通の形

```text
{ "pos": 12345, "id": "<uuidv7>", "type": "room.event", "ts": "2026-10-13T12:34:56.789Z", "room_id": "...", "payload": { ... } }
```

- `pos` は利用者ごとに単調増加。端末は最後に処理した pos を保存し、再接続と `/sync` に使う。
- 同じイベントは本人の全端末に届く（自分の送信のエコーを含む。`payload.transaction_id`）。例外は 6.2 で「その端末」に届く種類で、サーバーは宛先の端末にだけ送る（全体実装設計書 2.4）。端末から見ると、他の端末宛ての分だけ pos が飛ぶ。飛びは欠けではなく、端末は飛びで `/sync` を呼ばない。取りこぼしを埋めるのは再接続の時の `/sync?since=` だけで、接続中の WebSocket はサーバーが feed を順に読むので取りこぼさない。
- 大きさは 1 件 256 KiB まで（MLS の暗号文を含む）。超える本文は添付にする（第4章）。

### 6.3 接続の規則

- 接続後 5 秒以内に `auth` が来なければ切る。認証後、サーバーは `{type: "ready", pos: <最新>}` を返す。端末は保存した pos と比べる。`ready` の pos の方が大きければ `/sync?since=` で埋める。`ready` の pos の方が小さければ、サーバーがバックアップから戻った（11）ので全差分を取り直す（`sync.gap` と同じ）。戻ったサーバーの feed には端末の pos より後の行が無く、`sync.gap` の行だけでは届かない。接続中のイベントはそのまま流れるので、端末は pos で順序を直す。
- 切断と再接続：端末は指数の待ち（1、2、4、…、60 秒。乱数のゆらぎ）で再接続し、`auth`、`ready`、`/sync` の順に進む。
- サーバーの再起動（更新）：切断の前に `{type: "bye", retry_after}` を送る。
- サーバーが閉じる時の状態の番号（IANA の WebSocket Close Code の登録。4000〜4999 は私用）と端末の振る舞い：

|番号|いつ|端末|
|---|---|---|
|1008|auth の失敗・期限切れ、知らない type、メッセージの数の超過（9.3）|新しいトークンを得て再接続|
|1009|1 件が 64 KiB を超えた（第1章 10.6）|再接続（送った物は送り直さない）|
|1011|サーバーの内部の誤り|指数の待ちで再接続|
|1012|サーバーの再起動（`bye` の後）|`retry_after` の後に再接続|
|1013|送りのキューが満杯（遅い端末）|再接続して `/sync` で埋める|
|4001|セッションの失効（`session.revoked` をその端末に書いた直後にサーバーが閉じる。理由は 6.2 の `reason` の 7 つ）|再接続しない。ログインの画面|
|4002|同じ端末の 2 本目の接続ができた（古い方を閉じる）|再接続しない（新しい方が使われている）|

- 1 端末 1 接続。シェルの Android は WebView の接続とは別に常時接続（通知）を持つが、それは境界の「通知」であり本節の WebSocket ではない（第7章、第9章）。

### 6.4 配布元の常時接続（`/up/ws`。第7章 3.1）

- 接続：Android のシェルがネイティブの部品から `wss://<サーバー>/api/v1/up/ws` へ接続する。upgrade の要求には `Authorization: Bearer <配布元の接続の秘密>`（4.4 の `ws_secret`）を付ける。ブラウザの WebSocket ではないのでヘッダを付けられ、`/ws` の `auth` のメッセージは使わない。秘密が無効（失効、端末の取り消し）なら upgrade を 401（`AUTH-002`。reason は `device_revoked` か `logout`）で拒む。シェルは次に WebView を開いた時に登録し直す。1 端末 1 接続。

|type|向き|形|備考|
|---|---|---|---|
|`msg`|サーバーから端末|`{type, id, body, expires_at}`|`body` は `/up/{token}` で受けた RFC 8291 の暗号文の base64url。接続の直後に未配信を古い順に送り、以後は受けるたびに送る|
|`ack`|端末からサーバー|`{type, id}`|受け取った `msg` の `id`。サーバーは ack を受けた項目を消す。ack の無い項目は次の接続で再送する|
|`ping`／`pong`|両方|`{type}`|60 秒（シェルの電池のため `/ws` より長い）|

## 7. 通知の中身（第7章）

- Web Push：次の形の JSON を RFC 8291 で暗号化する（最大 4,096 バイト。本文は入れないので常に小さい）。ヘッダは DD-2-8。

  ```text
  {v: 1, event_id, room_id, sender_id, kind: message|call|call_end|notice, call_id?, video?, reason?}（`video` は kind が call の時に必須。Android の着信の画面が使う。第9章 6。`reason` は kind が call_end の時に必須で、`missed`、`answered`、`declined`、`cancelled` のいずれか。第7章 7）
  ```

- kind が `notice` の時、`event_id` は知らせの id で、`room_id` と `sender_id` は無い。端末は `GET /me/notices/{id}`（5.3）で中身（kind、level、text_key、params）を取り、第10章 9.4 の文言で表示する（第7章 9）。

- 宣言型の Web Push（iOS 18.4 以上。購読の `declarative: true`）では次の形（`ft.push.declarative/1`）を RFC 8291 で暗号化する。Service Worker には `event.data` が無く `event.notification` だけが届くので、上の中身は `notification.data` に入れる。`mutable: true` が無いと Service Worker は呼ばれない。`mutable` は外側と `notification` の中の両方に置く。W3C の作業草案は外側だが、iOS 18.4〜26.1 の WebKit は `notification` の中だけを読み、26.2 からは外側を先に読む（調査資料 I-01 1.11）。知らない欄は無視されるので、両方に置けばどの版でも効く。Service Worker が時間内に通知を出せば提案の通知は出ない（第7章 5.1、第12章 5.8）。

  ```text
  {web_push: 8030, mutable: true,
   notification: {title: "<家族の名前>", body: "<送信者の表示名>さんからメッセージ", navigate: "/r/<room_id>",
                  tag: "<room_id>", silent: false, mutable: true, app_badge: "<未読の合計>", data: {...上の中身...}}}
  ```

  着信（kind が call）は次の値にする。title「<送信者の表示名>さんから着信」、body「応答するには開いてください」。navigate `/call/<call_id>`、tag `call:<call_id>`。通話の終わり（kind が call_end）は title「<送信者の表示名>さんからの着信」とする。body は `reason` が `missed` なら「不在着信」、それ以外は「終わりました」で、`missed` 以外は `silent: true`。`renotify` は置かない（WebKit は実装せず、tag の置き換えにも頼らない。第7章 7）。`app_badge` は W3C の作業草案に無い OS の提供者の拡張で、文字列の数で送る。

- UnifiedPush：同じ中身を RFC 8291 で暗号化し、端末の配布元のエンドポイントへ POST（UnifiedPush の仕様 AND_3.1.0。VAPID）。シェルが受けて WebView に渡す（第9章）。
- 購読の失効：中継が 404 または 410 を返したら購読を消し、端末が次に開いた時に `device.changed` で知らせて取り直す。`pushsubscriptionchange` は端末が `PUT /me/devices/{id}/push` で更新する。
- 未読の数（バッジ）：`app_badge` と、端末が `/rooms` から計算する値の両方。iPhone は宣言型の値、Android はシェルが `/rooms` の合計を出す（第9章）。

## 9. エラーコード表（初期の項目）とレート制限

### 9.1 形

```text
{ "type": "https://<サーバー>/errors/ROOM-002", "title": "トークの構成員ではありません", "status": 403, "code": "ROOM-002", "retryable": false, "params": {"room_id": "..."}, "instance": "urn:uuid:0199e1c2-...." }
```

- `title` と `detail` は機械向けの英語または短い日本語。利用者に見せる文言は端末が `code` で引く（第1章 10.3）。エラーコード表の各項目は `user_text_key`（文言の表の鍵。第10章 9.2）を持つ。
- `instance` は要求の識別子を `urn:uuid:` の形（RFC 9562 の URN）で入れる。要求の識別子は api が要求ごとに発行する UUIDv7 で、ログの `req_id` と同じ値である。RFC 9457 の `instance` は問題の発生を識別する URI 参照であり、経路では発生を区別できない。管理者は SRV-003 の時にこの値でログを引く。
- 端末が送る `X-Request-Id` の頭は使わない。端末の値をログの鍵にすると、他の要求の記録と同じ値を作れるためである。

## 10. 境界の文書と生成（R-2-8-1）

```text
api/
  openapi.yaml        API と管理者の API（OpenAPI 3.1）。servers は /api/v1。securitySchemes: cookie、wsToken、shellToken
  asyncapi.yaml       イベント（WebSocket、/sync）と通知の中身（AsyncAPI 3.1）。channels は 6.2 の type
  schemas/            JSON Schema 2020-12。ft.event.*、ft.content.*（復号後。クライアントのみ）、fkb/*、fdev/*、ft.push/*、ft.settings/*、ft.version/*、ft.bridge/*（Android のシェルと WebView の JS ブリッジの命令とイベントの契約。第9章 4.2。TypeScript と Kotlin を生成）
  errors.yaml         9.2 のエラーコード表（番号、状態、title、retryable、params の型、利用者の文言の鍵、記録の有無）
  ratelimits.yaml     9.3
  config.yaml         設定の一覧（第11章）：鍵、型、既定値、範囲、置き場（ファイル・環境変数・DB）、画面でのロック
  CHANGELOG.md        境界の版の履歴
```

- openapi.yaml の各 operation は `x-authz` を必ず持つ。`x-authz` は認可の門で、下の表の値の配列とし、どれか 1 つを満たせば通す。サーバーは起動時に、全 operation が `x-authz` を持つことを確かめる。
- 未承認の端末（4.3）が使えるのは、`session` か `device_self` を含む経路だけで、他は `KEY-004`。
- 資源を読んでから行う確かめは `x-authz-rule`（下の表の名前）で示す。
- 読み取り専用（第1章 DD-1-15）の時、GET と HEAD 以外は `SRV-001` で拒む。ただし `x-readonly: allow` の経路は通す。対象は、読むために要る認証（パスキーのログイン、ログアウト、WebSocket とシェルのトークン）と、管理者が状態を直す経路（バックアップ、更新、保持と設定）である。
- `x-errors` は経路が返し得る番号で、x- の属性から暗に返る番号を含む。認可が全部セッションかシェルの値なら AUTH-001、AUTH-002。そのうち承認を要する値（approved、room_member、admin）だけなら KEY-004。device_self を含めば KEY-001、room_member を含めば ROOM-002、admin を含めば ADM-001。`x-idempotency: key` なら NET-007、NET-008。`x-reauth` があれば AUTH-006。`x-ratelimit` の policy の `on_exceed` が NET-004 以外ならその番号。
- 廃止する経路は OpenAPI の `deprecated: true` と `x-deprecation: {at, sunset}` を持つ。値は RFC 3339 の日時で、sunset は at より前にしない。サーバーはその経路の応答に `Deprecation`（RFC 9745。`@<秒>`）と `Sunset`（RFC 8594）を付け、`/version` の `deprecations` に載せる。
- 再認証を要する経路は `x-reauth: true` とする。条件つきの再認証は `x-reauth: conditional` とし、条件はハンドラが見る（`AUTH-006`。どの操作かは第3章 4.5）。再認証を求めるのは次の時。
  - 他の端末の承認と取り消し（自分の端末の自己承認と取り消しは要しない）
  - 2 本目からのパスキーの登録、2 回目からの回復コード
  - 鍵の作り直し

## 11. 競合の規則（R-2-2-5）

|競合|規則|
|---|---|
|同じメッセージへの同時の編集（本人の 2 端末）|サーバーの順で後のものが勝つ（`m.replace` の最新）。端末は pos の順で適用|
|既読の後退（古い端末が古い位置を送る）|サーバーは単調に進めるだけ。後退は無視して 200|
|構成員の変化中の送信（Remove の Commit の後に古い epoch で送った）|サーバーはイベントの `epoch` が現在より古ければ `ROOM-006`。端末は新しい epoch を取り込んで作り直す。Commit の直列化は `KEY-007`|
|同じ 1 対 1 のトークの同時の作成|`ROOM-004` で既存を返す（どちらか先に作った方）|
|同じ Idempotency-Key の再送|同じ応答。本文が違えば `NET-008`|
|添付の追記の重複（同じ offset を 2 回）|2 回目は `MEDIA-003`（現在の offset を返す）。端末は HEAD で確かめる|
|通話の同時の開始（互いに発信）|サーバーは同じトークに進行中の通話があれば 2 件目を `CALL-002` で既存に合流させる|
|予約送信の時刻に端末がオフライン|サーバーが予約の暗号文をそのままイベントにする（epoch が古ければ受け手は鍵のバックアップで復号。第12章 5.7）|
|サーバーの復元（バックアップから）の後の pos|復元の後、サーバーは `sync.gap` を全端末に送り、端末は全差分を取り直す。端末のキューの未送信は再送（Idempotency-Key で二重にならない）|

## 13. 失敗の扱い

|失敗|扱い|
|---|---|
|WebSocket が使えない（企業のネットワーク、古いプロキシ）|`/sync` のロングポール（timeout 30 秒）に自動で切り替え、1 時間ごとに WebSocket を試す|
|`/sync` の 410|全差分の取り直し（`/rooms`、各トークの `events` と `receipts`、`/me/notices`、`/me/inbox`、`/me/keybackup`）。端末のコピーは保持し、重複はイベントの識別子で除く|
|Idempotency-Key の衝突（別の本文）|`NET-008`。端末の不具合なので記録して利用者には「送信に失敗」|
