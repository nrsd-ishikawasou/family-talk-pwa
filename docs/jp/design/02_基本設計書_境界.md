## 本書の位置付け

- 概要設計書 第2章「サーバーとクライアントの境界」を詳細化する。サーバー側とクライアント側の間のすべてのやり取りの種類、形、認証と認可、冪等性、版を本章が持ち、機能の章（第3〜7章）はここを参照して再掲しない（第1章 DD-1-1、4.3）。
- 本章の第1版は「一覧と規則」である。各経路の型（JSON Schema）の中身は api/ の文書（10）が正本であり、本章は経路と規則と番号を定める。機能の章が閉じた後の第2巡で、型とエラーコード表を確定する。
- 前提：第12章の結論（本文と添付は端から端で暗号化。サーバーは配送サービスと認証サービス、端末宛メールボックス、鍵バンドルと鍵のバックアップの保管、URL の取得の代理を担い、検索の API を持たない）。
- 準拠：語彙は公開のメッセージングのプロトコルの仕様 v1.19（調査資料 準拠標準 1。イベントと状態、transaction id、関係、意図的メンション、既読 3 種、入力中、redaction、pusher、メディア、同期）と XMPP の拡張（アーカイブの照会、スロットの先行発行、権限の 2 層）、IETF MIMI の内容の形式の欄名。形は OpenAPI 3.1、AsyncAPI 3.1、JSON Schema 2020-12、RFC 9457、RFC 6585 と ratelimit の草案、RFC 9562、RFC 3339、RFC 6265bis（`__Host-`）、Fetch Metadata、RFC 8628、WebAuthn Level 3、RFC 9745、RFC 8594、RFC 9110（Range、ETag）。

## 2. 目的と範囲

### 2.1 受ける要件

概要設計書 第2章の R-2-1-1〜R-2-8-2。対応は 14。

### 2.2 扱うもの・扱わないもの

- 扱う：やり取りの分類と規則、認証と認可、資源の一覧（経路、動詞、認可、冪等、備考）、イベントの一覧と同期、通知の中身、通話のシグナリング、メディアの URL、配布と版、管理者の API、鍵の運搬、エラーコード表、レート制限、競合の規則、境界の文書と生成。
- 扱わない：各経路の意味と画面（第3〜7章、第10章）、シェルと WebView の JS ブリッジ（第8章、第9章）、家族のサーバーの外部との接続の中身（第11章、第12章）。

- すべて TLS の上（第12章 4）。平文の HTTP は caddy が HTTPS へ転送する。
- 要求の大きさの上限：JSON は 1 MiB、添付の追記は 1 回 64 MiB（初期値）。
- 応答の圧縮：JSON は gzip または brotli。添付（暗号文）は圧縮しない。
- 一覧の取得はカーソル方式（`?limit=&before=&after=`。識別子または pos）で、オフセットは使わない。

## 4. 認証と認可

### 4.1 セッション

- ログイン（パスキー、QR の承認、招待の受諾、管理者の作成のリンク。第3章）に成功すると、サーバーは端末に紐づくセッションを作り、`__Host-session` の Cookie（Secure、HttpOnly、SameSite=Lax、Path=/）を返す。値は 256 ビットの乱数で、DB にはハッシュを置く。
- 寿命：第1章 DD-1-17（絶対 90 日、無操作 30 日。初期値）。無操作の期限は要求のたびに延びる。絶対の期限の 7 日前から、API の応答の `X-Session-Expires` で端末に知らせ、端末はパスキーで静かに作り直す（第3章）。
- 端末の識別子は Cookie に入れず、セッションに紐づく。端末は `GET /me/session` で自分の端末の識別子を得る。
- ログアウト、端末の取り消し、構成員の停止、セッションの署名鍵の交代で失効する。失効はイベント `session.revoked` で端末に届き、届かなくても次の要求が 401（`AUTH-002`）になる。
- 未認証で使える経路：`/api/v1/invites/{token}`（GET。限られた情報）、`/api/v1/invites/{token}/accept`、`/api/v1/auth/*`（ログインの開始と検証）、`/api/v1/setup/*`（初回。第11章）、`/api/v1/family`（名前とアイコン。ログインの画面用）、配布と版、`/health`。

### 4.2 CSRF と cross-site

- 状態を変える要求（POST、PUT、PATCH、DELETE）は、`Sec-Fetch-Site` が `same-origin` または `none`、かつ `X-Requested-With: family-talk` を要する。欠けていれば 403（`NET-003`）。
- Android のシェルの WebView はウェブアプリを家族のサーバーのオリジンから読むため same-origin。シェルのネイティブの要求（版の情報、通知の登録の補助）は `X-Requested-With` を付け、Cookie は WebView と共有しない（シェルは自分の短命トークンを `POST /auth/shell-token` で得る。第9章）。
- CORS は許さない（`Access-Control-Allow-Origin` を返さない）。

### 4.3 認可の 3 つの基本

|名|意味|判定|
|---|---|---|
|本人|自分の資源（`/me/...`、自分の端末、自分の設定）|セッションの構成員 = 資源の持ち主|
|トークの構成員|トークのイベント、添付、通話、MLS の配送|セッションの構成員がトークの現在の構成員。退出・削除の後は過去のイベントも取得できない（端末のコピーは残る）|
|管理者|`/admin/...`、招待の発行（設定で構成員にも許せる）、構成員の停止と削除|役割 = 管理者。複数可。自分自身の停止・削除・管理者の解除は最後の 1 人ならできない|

- トークごとの権限（作成者が構成員を外せる等。第4章）は「トークの構成員」の上に重ねる。
- 未承認の端末（第12章 5.5）は、鍵の運搬の経路と自分の端末の経路だけが使え、トークの経路は 403（`KEY-004`）。

### 4.4 WebSocket と通知と SFU

- WebSocket：`POST /auth/ws-token` で 60 秒のトークン（セッションと端末に紐づく）を得て、接続後の最初のメッセージ `{type: "auth", token}` で渡す。Origin は許可リスト（家族のサーバーのオリジン）。1 端末 1 接続（2 本目は古い方を切る）。
- 通知：購読の登録（5.9）は本人。中継からの配送は購読の秘密（RFC 8291 の `auth`）で端末だけが復号。
- SFU：通話の開始・参加で得るトークン（JWT。SFU の鍵で署名。`room = call_id`、`identity = device_id`、権限は publish/subscribe、5 分）。TURN の資格はトークンに含まれる（埋め込み TURN）。
- シェル：`POST /auth/shell-token` で 24 時間のトークン（シェルの API の経路：`/api/v1/up/*`、`/api/v1/me/devices/{id}/keys` の補助、版の情報の取得。第9章）。

## 5. 資源の一覧（API）

経路は `/api/v1` を省く。「冪等」の欄：K = `Idempotency-Key`、N = 自然な鍵、— = GET/PUT/DELETE。エラーは 9 のエラーコード表の分類。

## 6. イベント（WebSocket と同期）

### 6.1 共通の形

```
{ "pos": 12345, "id": "<uuidv7>", "type": "room.event", "ts": "2026-10-13T12:34:56.789Z", "room_id": "...", "payload": { ... } }
```

- `pos` は利用者ごとに単調増加。端末は最後に処理した pos を保存し、再接続と `/sync` に使う。
- 同じイベントは本人の全端末に届く（自分の送信のエコーを含む。`payload.transaction_id`）。
- 大きさは 1 件 256 KiB まで（MLS の暗号文を含む）。超える本文は添付にする（第4章）。

### 6.2 イベントの一覧（asyncapi.yaml の `channels`）

### 6.3 接続の規則

- 接続後 5 秒以内に `auth` が来なければ切る。認証後、サーバーは `{type: "ready", pos: <最新>}` を返し、端末は保存した pos と比べて差があれば `/sync?since=` で埋める（接続中のイベントはそのまま流れるので、端末は pos で順序を直す）。
- 切断と再接続：端末は指数の待ち（1、2、4、…、60 秒。乱数のゆらぎ）で再接続し、`auth` → `ready` → `/sync` の順。
- サーバーの再起動（更新）：切断の前に `{type: "bye", retry_after}` を送る。
- 1 端末 1 接続。シェルの Android は WebView の接続とは別に常時接続（通知）を持つが、それは境界の「通知」であり本節の WebSocket ではない（第7章、第9章）。

## 7. 通知の中身（第7章）

- Web Push：`{v: 1, event_id, room_id, sender_id, kind: message\|call\|call_end\|notice, call_id?}` を JSON にして RFC 8291 で暗号化（最大 4,096 バイト。本文は入れないので常に小さい）。ヘッダは DD-2-8。宣言型の Web Push（iOS 18.4 以上。購読の `declarative: true`）では `{web_push: 8030, notification: {title: "<家族の名前>", body: "<送信者の表示名>さんからメッセージ", navigate: "/r/<room_id>", tag: "<room_id>", app_badge: <未読の合計>}, ft: {...上の中身...}}` とし、Service Worker が復号できれば置き換える（第12章 5.8）。
- UnifiedPush：同じ中身を RFC 8291 で暗号化し、端末の配布元のエンドポイントへ POST（UnifiedPush の仕様 AND_3.1.0。VAPID）。シェルが受けて WebView に渡す（第9章）。
- 購読の失効：中継が 404 または 410 を返したら購読を消し、端末が次に開いた時に `device.changed` で知らせて取り直す。`pushsubscriptionchange` は端末が `PUT /me/devices/{id}/push` で更新する。
- 未読の数（バッジ）：`app_badge` と、端末が `/rooms` から計算する値の両方。iPhone は宣言型の値、Android はシェルが `/rooms` の合計を出す（第9章）。

## 8. 外部との経路（第12章 8 と一致）

|経路|方向|認証|中身|
|---|---|---|---|
|プッシュ配信サービス（Web Push のエンドポイント、OS の提供者のエンドポイント）|サーバー → 外|VAPID|7 の暗号文|
|証明書の発行機関（ACME、DNS-01）|サーバー → 外|アカウントの鍵|家族のサーバーの名前|
|DNS の提供者（DDNS、DNS-01 のレコード）|サーバー → 外|API トークン（*_FILE）|名前と IP、検証のレコード|
|URL のプレビューの取得先|サーバー → 外|なし|URL の GET（`User-Agent` は本システムの名前と版）|

|---|---|
|同じメッセージへの同時の編集（本人の 2 端末）|サーバーの順で後のものが勝つ（`m.replace` の最新）。端末は pos の順で適用|
|既読の後退（古い端末が古い位置を送る）|サーバーは単調に進めるだけ。後退は無視して 200|
|構成員の変化中の送信（Remove の Commit の後に古い epoch で送った）|サーバーはイベントの `epoch` が現在より古ければ `ROOM-006`。端末は新しい epoch を取り込んで作り直す。Commit の直列化は `KEY-007`|
|同じ 1 対 1 のトークの同時の作成|`ROOM-004` で既存を返す（どちらか先に作った方）|
|同じ Idempotency-Key の再送|同じ応答。本文が違えば `NET-008`|
|添付の追記の重複（同じ offset を 2 回）|2 回目は `MEDIA-003`（現在の offset を返す）。端末は HEAD で確かめる|
|通話の同時の開始（互いに発信）|サーバーは同じトークに進行中の通話があれば 2 件目を `CALL-002` で既存に合流させる|
|予約送信の時刻に端末がオフライン|サーバーが予約の暗号文をそのままイベントにする（epoch が古ければ受け手は鍵のバックアップで復号。第12章 5.7）|
|サーバーの復元（バックアップから）の後の pos|復元の後、サーバーは `sync.gap` を全端末に送り、端末は全差分を取り直す。端末のキューの未送信は再送（Idempotency-Key で二重にならない）|

## 13. 失敗の扱い

|失敗|扱い|
|---|---|
|WebSocket が使えない（企業のネットワーク、古いプロキシ）|`/sync` のロングポール（timeout 30 秒）に自動で切り替え、1 時間ごとに WebSocket を試す|
|`/sync` の 410|全差分の取り直し（`/rooms` → 各トークの `events`）。端末のコピーは保持し、重複はイベントの識別子で除く|
|Idempotency-Key の衝突（別の本文）|`NET-008`。端末の不具合なので記録して利用者には「送信に失敗」|
|型の検証の失敗（アプリが新しく、サーバーが古い）|`NET-001`。端末は `/version` を見て、サーバーが古ければ機能を落として続ける（第1章 10.9）|
|アプリが古い（`NET-006`）|更新の案内で止まる|
|SFU のトークンの期限切れ（5 分）|参加の前に取り直す。接続後は SFU のセッションが続く|
|プッシュ配信サービスの失敗（5xx）|指数の待ちで 3 回（第7章）。着信は 1 回（TTL 60 の意味がない）|
|caddy の forward auth の失敗（地図、静的）|401。端末はログインへ|
|レート制限|端末は `Retry-After` の後に 1 回だけ再試行し、利用者には「少し待ってください」|

## 15. 用語

|用語|意味|
|---|---|
|pos|利用者ごとのイベントの位置。単調増加の整数|

|イベント|トークに記録される不変の 1 件（`room.event` の payload）|

|forward auth|caddy が静的な配信の前に api に認可を問い合わせる仕組み|

## 16. 本章で宣言する既知の制約

|番号|既知の制約|理由|緩和|
|---|---|---|---|
|H-2-1|`mentions`、`relates_to`、添付の大きさとハッシュ、送信者、時刻は平文のメタデータとしてサーバーに見える|通知の規則、整列、認可、配送に要る|第12章 H-12-3 の明示|
|H-2-2|サーバーは本文の書き出し（テキストの履歴）を作れない。書き出しは端末が行う|E2EE|端末の書き出し（第4章）|
|H-2-3|サーバーは添付の種類（画像か動画か）を知らず、添付の上限は暗号文の大きさでしか数えられない|E2EE|端末が種類ごとの上限を守る（第5章）。サーバーは総量だけ|
|H-2-4|再開可能なアップロードの形は IETF の草案の最終形と異なり得る|草案が未確定|HEAD/PATCH の形は変えず、ヘッダ名だけを揃える|
|H-2-5|レート制限の残量のヘッダは草案の形|同上|「草案準拠」と注記|
|H-2-6|WebSocket が使えないネットワークではロングポールに落ち、遅延と電池が悪くなる|ネットワークの制約|自動の切り替えと復帰|
