## 本書の位置付け

- 概要設計書 第14章「開発基盤」を詳細化し、設計計画書の未決事項 O-02「開発基盤」を閉じる。設計計画書 D-6-1「固定しない」は本章で「固定する」に転じ、D-6-2「第6.1節の条件で選定」を本章の 3 で行う。
- 本章は「大枠」であり、次を定める。言語と主要な部品。境界の型の生成。ライセンスの方針。リポジトリの構成と CI。書き方の取り決め。部品の版の下限は 2026-10-13 時点の確認値を置く。第2章（境界）、第5章（メディア）、第12章（データと暗号化）、第13章（配布と更新）が閉じた時に第2巡で詰める。
- 本章が名指しするソフトウェアは、本システムが実際に採用して同梱または依存するものに限る。退けた候補は種類で書き、名を書かない。採用するものは設計計画書 第19章の表に版とライセンスを加える（21）。
- 調べた事実の出典は、調査資料「調査 H」「準拠する標準規格の一覧」「準拠の調査 1」と、本章の各節が挙げる公式文書である。部品の版・日付・ライセンス・保守の状態は 2026-10-13 に各公式のレジストリと公開リポジトリで確認した値である。

## 2. 目的と範囲

### 2.1 受ける要件

概要設計書 第14章の R-14-1-1、R-14-1-2、R-14-2-1、R-14-3-1、R-14-3-2、R-14-4-1。対応は 17。

### 2.2 扱うもの・扱わないもの

- 扱う：サーバー側とウェブのクライアントの言語と部品。Android のシェルの部品。境界の型の生成。ライセンスの方針と第三者の表示。リポジトリの構成と CI。再現可能なビルド、署名、ビルド証明。保守の備えと脆弱性の走査。書き方の取り決めと版の規則。対応する OS とブラウザの最低要件。
- 扱わない：ストアの配布の道具（設計計画書 D-5-2）。配布物の中身と更新の手順（第13章）。設置の手順（第11章）。各部品の使い方の詳細（全体実装設計書）。

### 3.2 候補の集め方

- サーバー側の言語は、Web のサーバーを書く主要な 4 系統を候補とした（JavaScript の実行環境の上の言語、Go、所有権の型を持つシステム言語、JVM の上の言語）。部品は下の 12 の領域ごとに確かめた。確かめた事項は、部品の版・日付・ライセンス・保守の状態（最終の公開、未解決の件数、最多の貢献者の比率）・脆弱性の勧告である。確かめ方は、各公式のレジストリと公開リポジトリの API による。
  - 通信と認証：Web Push、WebAuthn、Argon2id、WebSocket
  - データ：PostgreSQL、PostgreSQL 上の仕事のキュー、UUIDv7
  - 境界の文書：OpenAPI 3.1、AsyncAPI 3.1
  - その他：画像、SFU の SDK、ログ
- 最小の HTTP サーバーのメモリと初応答の時間を同じ機械で実測した（20 コア 64 GiB の機械での相対比較。2〜4 コアの家族のサーバーでの絶対値は［要実測］）。
- ウェブ、Android、CI の部品も同じ観点で確認した。確認の記録は NRSD の作業記録にあり、本章には採用するものの値だけを載せる。

### 3.4 照合（ウェブ、Android、CI）

- ウェブ（C-1、C-2、C-9、C-14）：TypeScript は唯一。画面の部品は 4 つの条件で照合した：財団または組織の統治、見やすさの部品の成熟、トークの型の仮想の一覧、最低要件のブラウザでの動作。採るのは React + React Aria Components + TanStack Virtual（DD-14-3）。
- Android（C-3、C-9）：言語は設計計画書 D-5-7 で決定済み。部品は OS の提供者の公式の部品（androidx）を一次とし、通知は UnifiedPush の仕様の部品を採る（DD-14-4、DD-14-5）。
- CI（C-9、C-13）：公開リポジトリの運営者の仕組みが arm64 のネイティブのランナーとビルド証明の証明を無料で提供する（DD-14-9、DD-14-10）。

## 5. サーバー側の開発基盤

### 5.3 退けた部品の種類と理由

- コードから OpenAPI を生成する枠組み：正本がコードになる（DD-14-2 に反する）。
- OpenAPI 3.0 系の検証器：2026 年に認証を素通りさせる致命的な勧告があった。
- 停滞した UUID と WebSocket の部品：2024 年以降公開なし。
- PostgreSQL 上の仕事のキューの部品：MPL-2.0（ファイル単位のコピーレフト）であり、SKIP LOCKED のキューは小さいので自前が軽い。

### 5.4 イメージ

- 本システムのイメージは 1 つで、次を含む。api、worker、`ft`（同じ静的なバイナリ）、ウェブアプリ、APK、version.json。加えて手順書、THIRD_PARTY_NOTICES、restic、pmtiles の CLI（5.2）、PostgreSQL のクライアントの道具。非 root の固定の UID（第1章 DD-1-12）。`HEALTHCHECK` を持つ。
- 基盤は最小の静的な基盤（CGO なし）。基盤のイメージは digest で固定し、Dependabot で更新する。
- 別のイメージ：caddy（DNS の提供者のモジュール入り。本システムが CI で組む）、coturn（回線の形 C の VPS だけ）。postgres と sfu は公式のイメージを digest で固定。
- amd64 と arm64（DD-14-10）。

- WebView の中では Push API、Notification、Badging、画面内の PiP、WebAuthn の条件付き UI と PRF、音声の出力先の選択が使えない。これらはシェルが担う。通知の受信と表示、着信（CallStyle、全画面、Core-Telecom）、バッジ（ランチャーの仕組み）である。PiP（通話のアクティビティ全体）、音声の経路（Core-Telecom のエンドポイント）、認証の画面（第3章）もシェルが担う。
- Chromium は音声の入力を開くと `MODE_IN_COMMUNICATION` に自動で入る。Core-Telecom のエンドポイントの制御との相互作用は［要実測］（第9章）。

### 7.3 退けた部品の種類と理由

- OS の提供者の通知の SDK：NRSD の鍵が要る（設計計画書 D-10-2）。
- `addJavascriptInterface`：オリジンの検査なし。

## 8. 境界の型の生成

- 正本は次の 6 つ。中身は第2章が定める。
  - api/openapi.yaml（OpenAPI 3.1。HTTP の API）
  - api/asyncapi.yaml（AsyncAPI 3.1。WebSocket のイベントと通知の中身）
  - api/schemas/（両方から参照する JSON Schema 2020-12）
  - api/errors.yaml（エラーコード表。第1章 10.3）
  - api/ratelimits.yaml（レート制限。第2章 9.3）
  - api/config.yaml（設定の一覧。第11章）
- 生成：
  - server/：oapi-codegen がサーバーのインターフェースと型を生成。実行時は libopenapi-validator が要求と応答を仕様で検証する（開発と試験では応答も検証し、本番では要求だけ）。
  - server/ の生成の前に、束ねる道具（tools/bundle_openapi）が外のファイルへの参照を components/schemas に名前つきで取り込む。oapi-codegen は外のファイルへの参照から型の名を作れず、oneOf の和の型が壊れるため（2026-10-14 に手元で確かめた）。束ねた物は中間の生成ファイルでコミットしない。あわせて各経路の path に実際の前置き（経路の servers、無ければ全体の `/api/v1`）を付けて絶対の path にする。oapi-codegen は経路ごとの servers を読まず、`/health` などを `/api/v1` の下に登録してしまうため。
  - 続いて genimpl が、生成したサーバーの interface をタグごとの interface に分ける（srv-boundary の `Implementations`）。
  - 検証が読む spec は、束ねた物を genimpl が `go:embed` で取り込む。oapi-codegen の spec の埋め込みは使わない。読み出しに別の OpenAPI の読み込みの部品が要り、部品の表（5.2）に無い依存が増えるため。
  - web/：openapi-typescript が型を、openapi-fetch が呼び出しを生成。AsyncAPI のイベントの型は Modelina で生成する（AsyncAPI 3.1 の入力は【未確認】。3.0 からの破壊的変更はないので 3.0 と書いても同じ）。
  - android/：シェルが使う API は少ない（版の情報、通知の登録、着信の通知の中身、認証の JS ブリッジ）。fabrikt で Kotlin の型（kotlinx.serialization）を生成する。
- 生成ファイル（サーバー・ウェブ・シェルのコードの型）はコミットせず、ビルドのたびに生成する（第2章 10）。ただし api/schemas の `ft.settings.*` は境界の文書の一部なのでコミットする（config.yaml から `tools/gen_config` が作る JSON Schema）。CI は `python -m tools.gen_config --check` で、生成し直した結果とコミットした物の差分が 0 であることを確かめる。CI は「生成の再現性」として 2 つを確かめる。同じ正本から 2 回生成して結果が一致すること（生成の道具と版を固定）。生成した型でサーバー・ウェブ・シェルがビルドできること。
- 境界の変更は oasdiff で破壊的な変更を検出し、破壊的なら版の major を上げる PR に限る。AsyncAPI は AsyncAPI CLI の diff。
- 廃止する経路は、応答の `Deprecation`（RFC 9745）と `Sunset`（RFC 8594）のヘッダで機械可読に告げる（第2章 10 の `x-deprecation`）。アプリの互換の期間（第1章 DD-1-14）は `/version` の `min_app` で判定する（第13章 6.2）。

### 11.4 ワークフローの安全

- アクションは全ての `uses:` をコミットの SHA で固定し（zizmor が検査）、Dependabot が SHA を更新する。推移的な依存（アクションが中で使うアクション）の固定は、公開リポジトリの運営者のワークフローの依存のロックが正式になったら採る（H-14-8）。このロックは 2026-10 時点で設計と意見募集の段階で、形と Dependabot との連携は未定である。
- `permissions` は既定 `contents: read`。書き込みはジョブ単位。`id-token: write` と `attestations: write` はリリースのジョブだけ。
- `pull_request_target` を使わない（公開リポジトリの運営者が 2026-11-02 から既定で無効にする）。外部の PR のワークフローは秘密を持たない。
- 入力は環境変数を介して渡し、式をシェルに直接展開しない。
- ランナーは公開リポジトリの運営者のホストのもの（自前のランナーを置かない）。

### 11.5 Android の署名鍵の扱い

- 鍵はハードウェアのトークン（PKCS#11。非エクスポート）に置き、バックアップは設計計画書 D-15-4 の分散した保管に従う。
- apksigner は PKCS#11 の鍵で署名する。引数は次のとおり。

  ```text
  --ks-provider-class sun.security.pkcs11.SunPKCS11 --ks-provider-arg <設定> --ks-type PKCS11
  ```

- 鍵の回転は v3 の lineage（`--next-signer --lineage`）で行う。Android 開発者検証に複数の鍵を登録できる。
- 鍵を CI に置かない理由：公開リポジトリの運営者の秘密は「ログからの伏せ字は保証されない」と明記され、2025 年 3 月に広く使われたアクションのタグの付け替えで秘密がログに出た事故があった。署名鍵は失うと再生成できず、漏れれば他人が同じ名前で配布できる。

## 14. 書き方の取り決め

1. 他社・他製品・他サービスの名称を書かない。例外は次のとおり。採用して同梱・依存する部品（設計計画書 第19章の表）。標準規格の団体と文書。OS とブラウザの提供者の公式文書。前提の基盤（Ubuntu、Docker、iPhone/iOS、Android、GitHub）。CI は痕跡の語を走査し、準拠の元の名前は NRSD が手元で走査する。
2. 安全に関する断定的な表現（「完全に安全」「絶対に漏れない」）を書かない。「〜に従う」「〜を目標とする」「〜の範囲で」と書く（法務調査 L-13）。
3. 仕様は番号で参照する（RFC、W3C、OWASP、ISO の文書と節）。「準拠」はどの版の何に従うかを書く。
4. 番号には名前を添える（D-、R-、DD-、T-、H-、L-、I-、O-）。意味を明示しない記号を使わない。
5. 文書は日本語、である調（設計計画書はです・ます）。識別子（変数、関数、ファイル、API のパス）は英語。コードのコメントは日本語。
6. コミットの題は Conventional Commits 1.0.0（`feat`、`fix`、`docs`、`chore`、`ci`、`refactor`、`test`。`!` で破壊的）。本文は日本語。作者とコミッターは NRSD の担当者。
7. 版は Semantic Versioning 2.0.0。CHANGELOG は Keep a Changelog 1.1.0（Added/Changed/Deprecated/Removed/Fixed/Security）。
8. 図は Mermaid（classDiagram、sequenceDiagram、flowchart）で md に埋め込む。全ての図を PNG にも描き出し、その図の直前に画像として置く（dev/docs/jp/fig/）。公開リポジトリの運営者の画面は Mermaid の図を枠に縮めて表示し、文字が読めないためである。Mermaid の元の文は畳んで残す。Mermaid で描けない図は PNG だけ（docs/jp/design/fig/）。
9. 文字コードは UTF-8、改行は LF、末尾に改行（EditorConfig）。
10. 見出しの下に表題・版・日付・作者・NRSD と著作権の行（本書の書式）。
11. textlint は日本語の技術文書の規則を既定のまま使い、本節の決まりに合わせて 3 つだけ設定する。文体（です・ます、である）は文書ごとに本文と箇条書きを揃える（5）。漢字の連続の上限（6 文字）は、言い換えると参照が辿れなくなる固有の語（文書の名前「全体実装設計書」、法令の名前と法令の定義語、機関・計画・画面の設定の名前、法令と判決の文言の引用）に限って許す。図の表題の行（「図1　文書体系」の形。句点を付けない）は句点の規則から外す（許す行の正規表現の部品 textlint-filter-rule-allowlist）。設定は tools/node/.textlintrc.json。

## 15. 版の規則

- 版は全体で 1 つ（DD-14-8）。`vX.Y.Z` のタグがイメージ・APK・ウェブアプリ・version.json に同じ値で入る。
- major：境界の破壊的な変更（oasdiff が検出）、データの形式の互換のない変更。minor：機能の追加。patch：修正。
- 家族のサーバーは `/version` で版と境界の版を返す（第1章 10.9）。アプリは要求のヘッダに自分の版を載せる。互換の判定は第1章 DD-1-14 の期間を版の公開日で行う（version.json に公開日を持つ）。
- 0.y.z の間は破壊的な変更を minor で許す（SemVer 2.0.0 第4項）。家族に配る最初の版を 1.0.0 とする。

## 16. 失敗の扱い

|失敗|扱い|
|---|---|
|CI の検査（lint、型、試験、生成の再現性、ライセンス、脆弱性）が失敗|PR を merge しない。脆弱性は修正か、到達不能の根拠を書いた例外（期限つき）|
|再現可能なビルドが一致しない|リリースを止め、原因（時刻、並び、最適化）を直す。一致するまで公開しない|
|署名またはビルド証明の生成が失敗|リリースを止める。部分的な公開（イメージだけ、APK だけ）をしない|
|APK の署名の検証（保守者の手元）で CI の成果物と不一致|公開しない。ビルドの環境の差を潰す|
|依存の更新で試験が失敗|Dependabot の PR を閉じず、修正の PR を別に出す。security update は優先|
|部品の保守が止まった|13.1 の表に従う。表にない部品が止まれば表を更新してから対処する|
|公開リポジトリの運営者の障害|リリースは待つ。家族のサーバーの運用は続く（第1章 12）|
|ライセンスの食い違いが見つかった（公開物と POM の不一致など）|採用を保留し、権利者に確認する。確認できなければ自前に置き換える（DD-14-5）|
