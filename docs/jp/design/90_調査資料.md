## 調査 I-01：iPhone のホーム画面のウェブアプリの能力と制約（2026-10-13）

### 1. 確認した事実（出典つき）

#### 1.1 Web Push

- iOS および iPadOS 16.4（2023年2月16日発表）以降、ホーム画面に追加したウェブアプリは Web Push を受けられる。条件は、manifest の `display` が `standalone` または `fullscreen` であること、通知の許可の要求がユーザーの操作（タップ）を起点とすること、Push API、Notifications API および Service Worker を用いることである。Focus モードと連動し、Apple Watch にも表示される。manifest の `id` により、同じアプリの複数のインストールを区別する。［A1］［A2］
- Safari のタブ（ホーム画面に追加していない状態）では、iOS に Web Push はない。［A3］
- Apple Developer Program は要しない。Web Push は VAPID（RFC 8292）の鍵により送る。［A4］
- 通知を表示しない受信の扱い：Apple の開発者向けの講演（2022年）は、通知を所定の時間内に表示しない push が3回あると、そのサイトの購読を取り消すと述べている（macOS の beta 版についての記述）。WebKit の記事は「`userVisibleOnly` の約束に反すると購読を取り消す」とのみ述べ、回数を示さない。iOS における回数は未確認［要実測］。［A4］［A5］
- 購読が消える他の条件：ユーザーによるホーム画面のアプリの削除、通知の許可の取り消し、保存領域の消去。長期間の未使用で消えるかの明文はない（未確認）。
- 通知のオプションの対応：Safari は `actions`（通知の中のボタン）、`image`、`badge`、`renotify`、`requireInteraction`、`vibrate` に対応しない。`silent` は macOS の Safari 16.6 以降のみで、iOS は非対応。したがって、通知にボタン（「返信」「既読」）を置くことはできない。［A3］

#### 1.2 宣言型の Web Push（Declarative Web Push）

- iOS および iPadOS 18.4（2025年3月31日）、macOS 15.5 以降で使える。Service Worker を要さず、push の中身を JSON で書けば、ブラウザが通知を表示する。必須の項目は `title`（空でない）と `navigate`（タップした時に開く URL）。任意の項目は `body`、`lang`、`dir`、`silent`、`app_badge` ほか。トップレベルに `"web_push": 8030` を置いて選ぶ。［A6］［A7］
- Service Worker があれば、push のイベントが「提案された通知」とともに配送され、ハンドラが代わりの通知を出せばそれが採用され、出さなければ提案された通知が表示される。宣言型の push には、通知を表示しない受信の罰則（購読の取り消し）が適用されない。Service Worker が ITP により削除されても、購読は無効にならない。WebKit の記事は、「復号の鍵がアプリの中にしかない、安全な通信のアプリ」を用途として挙げている。［A6］
- `mutable` という項目の名前、および Content-Encoding に関する記述は、WebKit の記事にない（未確認）。W3C の Push API の作業草案（2026年10月5日）には、宣言型の push が統合されている。［A8］

#### 1.3 バッジ

- iOS 16.4 以降、`navigator.setAppBadge` と `clearAppBadge` が使える。通知の許可を得れば自動的に許可される。宣言型の push の `app_badge` により、Service Worker なしで更新できる。［A2］［A9］

#### 1.4 カメラ、マイクおよび WebRTC（ホーム画面のウェブアプリ）

- `getUserMedia` は Safari の iOS 11 以降で使える。
- 既知の不具合（WebKit の不具合の記録）：
  - カメラがホーム画面のウェブアプリで動かない（iOS 17.4.1〜17.6.1。iOS 18 の beta 5 で解消したとの報告があるが、記録は未解決のまま）。［A10］
  - カメラとマイクの許可が保持されず、起動のたび、再読み込みのたびに再び許可を求める（2024年9月25日起票、未解決）。2026年の報告では「26.2 で保持されたが 26.3.1 で退行した」「画面のロック中にストリームが生きていると、解除の後に再び許可を求める。ロックの前に停止すれば避けられる」とある。［A11］
  - 背景および画面のロック中の通話：WebKit の技術者は「マイクを取得している間は、ページは背景でもサスペンドされない」「音声の取得のコールバックが定期的に呼ばれているかを検査し、止まるとトラックを終了にする」「割り込み（電話の着信等）でトラックがミュートされ、ページがサスペンドされ、ネットワークの接続が切れ得る」と説明している。これは Safari のタブでの報告であり、ホーム画面のウェブアプリおよび iOS 15 以降の振る舞いは未確認［要実測］。関連して、Bluetooth の切断の後に背景およびロック中の通話の音声が戻らない報告（2024年11月）、iOS 27 で `getUserMedia` の音声が止まる退行の報告（2026年9月）がある。［A12］［A13］［A14］
- Media Session API は Safari 15 以降。マイクとカメラのミュートの API（`setMicrophoneActive`、`setCameraActive`）は 18.4 以降。［A3］
- Picture-in-Picture：iOS のホーム画面のウェブアプリでの対応は未確認［要実測］。
- Safari 26.0（iOS 26）：iOS で Speaker Selection API、`ImageCapture.grabFrame`、`enumerateDevices` の権限の修正。26.1：誤った `devicechange` の発火の修正。26.2：「ホーム画面のウェブアプリを再び開いた際に audio 要素が再生しない問題」の修正、カメラの表示の残留の修正。［A15］
- `MediaStreamTrackProcessor`（映像の加工）は Safari 18 で dedicated worker の中でのみ使える。［A15］

#### 1.5 Screen Wake Lock（画面の自動消灯の抑止）

- Safari 16.4 で追加されたが、ホーム画面のウェブアプリでは 18.4 まで動かなかった（18.4 で修正）。［A3］［A7］

#### 1.6 共有

- `navigator.share` と `canShare`（ファイルを含む）は iOS 14 以降で使える。
- 共有の受け手（manifest の `share_target`）は WebKit に実装されていない（2026年5月23日更新の記録でも未解決）。したがって、写真アプリからの「共有」で本システムに写真を渡すことはできない。本システムの側の「写真を選ぶ」で受ける。［A16］

#### 1.7 ファイルの入力（写真と動画）

- 「フォトライブラリ」から選ぶと、HEIC は JPEG に変換され、`accept` を無視して `image/jpeg` が来る（iOS 15 の記録、未解決）。「ファイルを選択」からなら元の HEIC が来る。複数を選ぶと1枚ずつ読み込まれ、進捗の表示がない（2026年9月30日の記録）。［A17］［A18］
- 動画（MOV、HEVC）の変換の有無、Live Photo の扱い、`capture` 属性の振る舞いは未確認［要実測］。

#### 1.8 保存領域

- 7日の制限（iOS 13.4、2020年3月24日）：Safari のタブでは、サイトの操作なしに Safari を7日使うと、スクリプトから書ける保存領域（IndexedDB、LocalStorage、Service Worker の登録とキャッシュ等）をすべて削除する。ホーム画面のウェブアプリは Safari の一部ではなく独自の使用日数の数え方を持ち、first-party のデータが削除されることは想定されていない。［A19］
- Safari 17 の保存の方針（2023年8月10日）：ホーム画面のウェブアプリはブラウザと同じ割り当て（オリジンごとにディスクの60%、全体で80%）。確認の表示は廃止。削除は、全体の割り当ての超過、容量の逼迫、長期の未使用の時に、使っていないものから行う。「アクティブなページを持つか、persistent のオリジンは対象外」。`navigator.storage.persist()` は「ホーム画面のウェブアプリとして開かれているか等の基準で許可」される。［A20］
- `persist()` と `persisted()` は Safari 15.2 以降、`estimate()` は 17 以降。OPFS の `getDirectory` と `createSyncAccessHandle` は 15.2 以降、`createWritable` は 26 以降。Storage Buckets API は非対応。［A3］
- Service Worker の寿命と、OS がホーム画面のウェブアプリのプロセスを終了する条件は、公開の文書がなく未確認［要実測］。

#### 1.9 ホーム画面への追加の検出と Safari 26 の変更

- `@media (display-mode: standalone)` は iOS 12.2 以降。`navigator.standalone` は Apple 独自。`beforeinstallprompt`（インストールの促し）は非対応。［A3］
- Safari 26.0（iOS 26）：ホーム画面に追加したすべてのサイトが、既定でウェブアプリとして開く（manifest は不要。ユーザーは追加の時に「Open as Web App」を切れる）。「ホーム画面に追加」が失敗する問題の修正。［A21］
- iOS 16.4 以降、ウェブブラウザの資格（`com.apple.developer.web-browser`）を持つ第三者のブラウザも、共有メニューから「ホーム画面に追加」を提供できる（WebKit を用いる）。［A1］

#### 1.10 日本における WebKit 以外のブラウザのエンジン（iOS 26.2 以降）

- Apple の「Changes to iOS in Japan」：iOS 26.2 以降、日本のユーザー向けに、WebKit 以外のエンジンを「専用のブラウザアプリ」と「アプリに埋め込んだブラウザ」で使える。初回の起動時に既定のブラウザを選ぶ画面が出る。［A22］
- Apple の「Using alternative browser engines in Japan」は、エンジンに求める要件（Web Platform Tests の90%、Test262 の80%、メモリ安全な言語、30日以内の脆弱性への対処、第三者 Cookie の既定の遮断等）のみを記し、ホーム画面のウェブアプリ、Web Push および Service Worker に関する記述を一切含まない。［A23］
- 日本で WebKit 以外のエンジンのブラウザが実際に出荷されたか、それがホーム画面のウェブアプリと push を提供するかは未確認。

### 2. 設計への帰結（第5章、第9章、第10章、第13章へ）

- 本システムの iPhone の対象は、Safari（または WebKit を用いる第三者のブラウザ）から追加した WebKit のホーム画面のウェブアプリに限る。WebKit 以外のエンジンから追加したものは対象外と設計書に書く。
- 通知は宣言型の Web Push（iOS 18.4 以降）を基本とし、Service Worker による push のハンドラを併せて置く（旧い iOS と、端から端の暗号化を採った場合の復号のため）。push の中身は、通知を必ず表示できる最小のもの（トークの識別子、イベントの識別子、未読の数、汎用の本文）とし、通知を表示しない受信を行わない。
- 通知にボタンを置かない。通知からの返信は Android と PC に限る（設計計画書 D-10-3 の「できる端末に限る」）。
- 起動のたびに購読の状態を確かめ、必要なら再び購読する。`pushsubscriptionchange` を扱う。
- 通話：画面のロック中の継続は「切れる、またはミュートされる」ことを前提に設計する。通話中は Screen Wake Lock（18.4 以降）で自動消灯を止め、復帰の時に `getUserMedia` を取り直し、ICE の再接続を行う。許可が保持されない不具合に備え、通話の開始のたびに許可を求める導線を置く。
- 共有の受け手（share_target）は使わず、本システムの「写真を選ぶ」で受ける。
- 写真は、フォトライブラリから選ぶと JPEG に変換されて来ることを前提としつつ、「ファイルを選択」経由の HEIC と、動画の MOV/HEVC を家族のサーバーで変換できるものとする（調査 I-08）。
- 保存領域は、起動の時に `navigator.storage.persist()` を呼ぶ。いつプロセスが終了しても IndexedDB の状態から再開できるものとし、サーバーを正本とする。鍵その他の失ってはならないものの唯一のコピーを端末の保存領域に置かない。
- 画面の共有（`getDisplayMedia`）は iOS で使えない。iPhone は見る側だけとする（設計計画書 D-9-4）。
- Safari 26 以降は manifest がなくてもウェブアプリとして開くが、本システムは manifest（`display: standalone`、`id`）を置く（Web Push の条件のため）。
- 既知の不具合は、設計の検証の章で既知の制約として宣言し、実装の初期に［要実測］の項目を確かめる。

## 調査 I-02：Android の通知の経路と鍵の持ち主（2026-10-13）

### 1. 確認した事実（出典つき）

#### 1.1 OS の提供者のプッシュ配信サービス（FCM）の鍵のモデル

- アプリに焼き込む値（プロジェクトの識別子、送信者の番号、アプリの識別子、API キー）は、提供者の文書で「公開情報と見なされる」「API キーは識別のためで認可には使われない」と明記されている。プログラムからの初期化（識別子と API キーを実行時に与える）は公式に支持される。［E1］［E2］［E3］
- 送る側（HTTP v1 API）は、サービスアカウントの秘密鍵による OAuth2 のトークンが必須で、API キーで送る経路は存在しない。［E4］
- 提供者の鍵の指針：「バイナリに埋め込んだ鍵は取り出せる」「鍵は削除するまで無期限に有効」「アプリごとに専用のサービスアカウントを作る」。利用規約は、鍵の安全と使用の責任を顧客に置き、サービスの再販・再許諾・譲渡・配布を禁じる。［E5］［E6］
- メッセージの仕様：本文 4,096 バイト。優先度 high は省電力の状態（Doze）でも即時に配信を試み、normal は保守の時間帯まで保留。通知の表示に結び付かない high を繰り返すと normal に降格される（端末ごとに7日間の判定）。TTL は 0〜28日（既定4週）、TTL 0 は即時に配信できなければ破棄。折りたたみの鍵は1端末に同時4つ。端末ごとの速度は 240件/分、5,000件/時。料金は無料。受信の処理は10秒以内。端から端の暗号化は提供されず、「サーバーで暗号化してアプリで復号」または「空のメッセージで起こしてアプリが自分のサーバーから取りに行く」が推奨される。［E7］［E8］［E9］［E10］［E11］
- 登録トークンは 270日の不活性で失効する。端末の要件は Android 7.0 以上かつ OS の提供者のストアのアプリがあること。［E12］［E13］

#### 1.2 同種のソフトウェアの解き方

- 公開のメッセージングのプロトコルの push gateway、一般的な通信アプリの複数、同種のオープンソースのサーバーのいずれも、ストアで配布するアプリの発行者が FCM と APNs の鍵を保持し、発行者が運営する中継を経由する。中継へは本文を送らず、イベントの識別子と未読の数（`event_id_only`）、起動の合図だけ、または端末の公開鍵で暗号化した小さな本文（RSA-2048 の鍵対を端末が作り、サーバーが暗号化して署名し、中継は署名だけを検証して転送する方式）を送る。中継が見るのは、端末のトークン、送信の時刻、サーバーの IP アドレス、暗号文の長さである（調査 A の 9、調査 E の 1.4）。
- 自分で立てる同種のサーバーが、発行者の中継に依らずに通知を届ける手段は2つに収斂している：(1) 自分で組み直したアプリと自分の鍵と自分の中継、(2) UnifiedPush（Android の通知の配布元の公開の仕様。オープンソースのメッセンジャーの複数が対応）。

#### 1.3 UnifiedPush

- Android の仕様 AND_3.1.0：配布元（distributor）とアプリ（connector）の間の Intent の約束。メッセージは RFC 8291 で暗号化されていなければならない（MUST）。本文は 1〜4,096 バイト（平文は最大 3,993 バイト）。配布元の選択は `unifiedpush://link` のリンク（OS の選択画面）。［E14］
- 部品：connector 3.3.5（2026年8月22日、minSdk 16、Apache-2.0、Web Push の復号を内蔵）、embedded FCM distributor 3.1.0（2026年6月23日。配布元のアプリが無い時の代わりとして、FCM の Web Push のエンドポイントを得る。FCM では VAPID が必須）、distributor 0.7.6（配布元を作る部品）。［E15］［E16］［E17］
- 配布元：自分で立てられる通知のサーバーの Android アプリ（Apache-2.0、minSdk 26。WebSocket の常時接続をフォアグラウンドサービス `specialUse` で保持し、受信ごとに wakelock、再起動と起動時の復帰を持つ。FAQ「17時間の常時接続で電池は約0〜1%」。遅延の公式の数値は無い）、Mozilla の push サーバーの実装を用いた配布元、XMPP 経由の配布元ほか。［E18］［E19］

#### 1.4 OS の省電力と常時接続

- 「アプリのプロセスがフォアグラウンドサービスを実行中：ネットワークの制限なし」。Doze 中は FCM の high 優先度のみ制限なし。［E20］
- フォアグラウンドサービスの型：`dataSync` は Android 15 で24時間に合計6時間の上限が付き、常時接続に使えない。`specialUse` は上限なし。Android 15 では起動時（BOOT_COMPLETED）から `dataSync`、`camera`、`mediaPlayback`、`phoneCall`、`microphone` の型を起動できないが、`specialUse` は起動できる。［E21］
- 電池の最適化の除外の「許容される用途」の表に「IM・チャット・通話のアプリで、技術的な依存により FCM を使えない場合」が挙げられている。［E22］
- バックグラウンドからフォアグラウンドサービスを起動できる免除：FCM の high の受信、通知等の UI の操作、起動時、利用者が電池の最適化を切った、など。［E23］
- 端末の製造者による強制終了の傾向は、公開の集計で製造者ごとに差があり、国内で多い製造者の一部は掲載がない［要実測］。［E24］

### 2. 設計への帰結（第10章、D-10-2 へ）

- 設計計画書 10.2 の3案の評価：
  - (a) NRSD のサービスアカウントの鍵を各家族のサーバーに配る：退ける。鍵は無期限で、取り消せば全家族が止まり、提供者の規約と指針に反する。
  - (b) NRSD が中継を運営する：本文を暗号化しても、端末のトークン、時刻、家族のサーバーの IP アドレスを NRSD が見ることになり、D-3-7 に反する。退ける。
  - (c) 各家族が自分の FCM のプロジェクトを作り、アプリが実行時に値を読む：技術的に成立し費用もかからないが、管理者に提供者のコンソールの操作（プロジェクトの作成、アプリの登録、値の転記、鍵の配置）を課す。同じパッケージ名を複数のプロジェクトに登録することの規約上の扱いは未確認。
  - (d) UnifiedPush：家族のサーバーは Web Push（RFC 8030、8291、8292）の送信路を1本持ち（iPhone と PC と同じ）、Android のアプリは connector で受ける。配布元はアプリに内蔵し、(i) 家族のサーバーで動かす通知のサーバーへの WebSocket の常時接続（`specialUse`）、(ii) embedded FCM distributor（NRSD の FCM のプロジェクトの公開の値だけをアプリに入れ、FCM の Web Push のエンドポイントを得る。秘密の鍵は誰にも配らない）の2系統を持つ。
- 本システムは (d) を採る方向で基本設計を行う。(ii) は手順が非公式で、`Urgency: high` が Doze 中の即時配信に写イメージされるか、NRSD のコンソールに見える集計の範囲、降格の規則の適用が未確認［要実測］。(i) は常時接続の遅延と電池を国内の主な端末で［要実測］。
- 通知の中身は、本文を含めない（トークの識別子、イベントの識別子、未読の数、汎用の本文）。high 優先度は必ず通知の表示に結び付ける。着信は TTL を短く、新着は折りたたむ。
- 初回に、通知の許可、電池の最適化の除外、起動時の復帰を案内する。

## 調査 I-03：Android のストアを通さない配布（2026-10-13）

### 1. 確認した事実（出典つき）

#### 1.1 開発者の確認の制度

- 時期：2025年10月に早期アクセス、2026年3月に全開発者に開放、2026年4月から端末に確認の仕組みが入り、2026年6〜8月に限定配布の口座の提供と「advanced flow」、2026年9月30日にブラジル、インドネシア、シンガポール、タイで施行、2027年以降に全世界（日本の日付は未公表）。［F1］［F2］
- 対象：認定された Android 端末の Android 7 以上。OS の提供者のサービス経由で判定する。施行後は、未登録のパッケージ名はインストールできず、更新も advanced flow か ADB でなければ失敗する。既存のインストールの再確認は不要。［F3］
- 完全配布の口座：25 ドル、政府発行の身分証（組織は D-U-N-S を要する旨が2025年8月の発表にある。現行の案内では未確認）。
- 限定配布の口座：無料、身分証不要。「学生、趣味、家族や友人との共有」向け。利用者が明示的に許可した 20台まで（QR コードかリンクと端末上の同意）。20台がアプリ単位か口座単位か、完全配布への移行の可否は未確認。［F4］
- 登録：パッケージ名と署名証明書の SHA-256。既存のパッケージ名は、秘密鍵で署名した APK を upload し、コンソールが示す断片を assets に入れて所有を証明する。1つのパッケージ名に複数の鍵を登録できる。失った鍵は回復も登録もできない。［F5］
- advanced flow（利用者側）：開発者モード → 「誰にも指示されていない」の確認 → 再起動と再認証 → 24時間の待機 → 生体認証または PIN → 未確認の開発者のアプリを7日間または無期限で入れられる。ADB は影響を受けない。［F3］

#### 1.2 署名

- 方式：v1（JAR）、v2（Android 7.0）、v3（Android 9、鍵の交代の系譜）、v3.1（Android 13 以上を対象とする交代）、v4（Android 11、ADB の増分インストール用。v2 または v3 が必須）。Android 11 を対象とするアプリは v2 以上で署名しなければならない。［F6］［F7］
- 鍵：「25年以上有効にする」「失うと更新を公開できない。再生成できない」。署名の道具は PKCS#11 によりハードウェアのトークンや HSM を使える。［F8］［F9］

#### 1.3 自己更新

- Android 8.0 以降、「不明なアプリのインストール」はアプリごとの許可（`REQUEST_INSTALL_PACKAGES`）。［F10］
- インストールの API：`PackageInstaller` のセッション。Android 12 の `setRequireUserAction(USER_ACTION_NOT_REQUIRED)` により、条件を満たせば確認なしに更新できる（条件の正確な文面は未確認）。Android 14 の更新の所有権（`setRequestUpdateOwnership`）。［F11］［F12］
- 一般的な通信アプリのストアを通さない版は、ダウンロードした APK のダイジェストを二度検証し、セッションで更新し、条件を満たさなければ通知で促す。オープンソースの更新の道具（GPL-3.0）は、公開リポジトリのリリースや APK へのリンクを含むページから新版を追う。
- Android 14 は targetSdk 23 未満、Android 15 は 24 未満のアプリを入れない。［F13］

#### 1.4 その他

- OS の提供者の保護の仕組みは、ストア外のアプリをインストール時に走査し、「確認されていないアプリで、金銭詐欺に悪用されがちな機微な権限を使うものはインストールを妨げることがある」。対象の権限の一覧は未確認（SMS、通知のリスナー、アクセシビリティとの一般的な理解。本システムの権限はこれに含まれない）。［F14］
- Android 15 以降の 16KB ページの端末では、ネイティブのライブラリ（WebRTC 等）を 16KB 境界で組み直す必要がある。Android 16 には互換モードがある。［F13］
- 日本の Android の版の構成（2026年9月）：16 が 38%、17 が 15%、14 が 11%、15 が 10%、12 が 8%、13 が 8%。11 以下は約 10%。［F15］

### 2. 設計への帰結（第5章、第15章、D-15-4 へ）

- NRSD は、2027年の日本での施行の前に、完全配布の口座（25 ドル。NRSD の法人の確認）でパッケージ名と署名鍵の SHA-256 を登録する。これが、家族の構成員に手順（advanced flow の24時間の待機）を課さない唯一の道である。限定配布の20台は家族1つ分にしかならず、NRSD が多数の家族に配る形に合わない。【要確認：お金・身元・外部】
- 署名は v1、v2、v3 で行う（v4 は配布に不要）。鍵は NRSD が1つ持ち（RSA 4096 または EC P-256、有効30年）、ハードウェアのトークン（PKCS#11）に置き、暗号化したバックアップを2か所以上に分散して保管する。鍵の SHA-256 を公開リポジトリに載せる。家族が自分で組み直す案は、更新と確認の制度の両方に合わないので採らない。
- 自己更新：家族のサーバーが版の情報（versionCode、URL、SHA-256、鍵の指紋）を配り、アプリが `PackageInstaller` のセッションで更新する。初回に「不明なアプリのインストール」の許可を案内する。公開リポジトリのリリースにも同じ APK を置く。更新は同じ鍵と単調に増える versionCode が前提。
- minSdk は 26（Android 8.0）。APK は ABI ごと（arm64-v8a、armeabi-v7a）。16KB ページに対応する。
- 本システムの権限（録音、カメラ、通知、全画面の着信、フォアグラウンドサービス、自分の通話の管理、インストール）は、保護の仕組みが止める対象の一般的な理解に含まれないが、対象の一覧は未確認である。

## 調査 I-04：Android の着信の画面（2026-10-13）

### 1. 確認した事実（出典つき）

- 全画面の着信の許可（`USE_FULL_SCREEN_INTENT`）：Android 14 の変更は「Android 14 を対象とするアプリでこの権限を使えるのは通話とアラームを提供するものに限る。OS の提供者のストアが、該当しないアプリの既定の許可を取り消す」と述べる。AOSP の文書は「Android 14 にインストールされるすべてのアプリで既定で有効」「インストール時にストアが取り消す」「製造者は、第三者のストアが `PackageInstaller.SessionParams` で初期状態を設定できるようにしなければならない」と述べる。すなわち、取り消す主体は OS ではなくインストーラである。ストアを通さず OS の標準のインストーラで入れる場合に既定で有効かは、明文がなく［要実測］。［G1］［G2］
- API：`NotificationManager.canUseFullScreenIntent()`（API 34。拒否されている場合、通知はロック画面で展開されたヘッドアップ通知として表示される）、`Settings.ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT`（設定画面へ）。全画面の表示は画面のロック中または消灯中のみで、それ以外はヘッドアップ通知。［G1］
- CallStyle の通知：API 31 以上で通知の最上位。`forIncomingCall(person, decline, answer)`、`forOngoingCall`。`addPerson()` が必須。Android 14 以上では `setOngoing(true)` で消せない通知になる。［G3］
- OS の通話の統合（Core-Telecom、androidx.core:core-telecom 1.0.1、1.1.0-rc01 が2026年10月7日）：`MANAGE_OWN_CALLS`（通常の権限）、フォアグラウンドサービスの型 `phoneCall`（映像なら `camera`、`microphone` も）、`CallsManager.registerAppWithTelecom`、`addCall` の4つのコールバック（応答、切断、アクティブ化、非アクティブ化）は5秒以内に完了、音声の経路は Telecom のエンドポイントの API を使う（`AudioManager` の直接の操作を使わない）、通話を加えてから5秒以内に CallStyle の通知で `startForeground`。時計、Bluetooth のヘッドセット、車載からの応答はコールバックで届く。Core-Telecom は着信の画面を出さず、見せ方はアプリの責任。［G4］
- おやすみモードの判定（AOSP）：既定の電話アプリでなくても、通知の category が `CATEGORY_CALL` なら通話として扱われ、「連絡先からの通話を許可」は通知の Person と端末の連絡先の一致で判定される。［G5］
- 同種のオープンソースのアプリ（一般的な通信アプリのオープンソース版、公開のメッセージングのプロトコルのネイティブのクライアント、SIP の電話アプリ）は、いずれも CallStyle と全画面の着信と `setOngoing` を組み合わせ、着信音は OS の既定の着信音を `FLAG_INSISTENT`（繰り返し）で鳴らし、時間で自動停止し、ロック中の着信画面に `showWhenLocked` と `turnScreenOn` を付ける。OS の通話の統合は、採るもの（Core-Telecom）と採らないもの（マイク型のフォアグラウンドサービスのみ）がある。公開のメッセージングのプロトコルのクライアントは、通話を WebView の中の WebRTC で行い、WebView の許可の要求をネイティブの権限に橋渡しし、通話の音声モードと PiP をネイティブで扱う（調査 E の 3.5）。

### 2. 設計への帰結（第9章、D-9-2 へ）

ストアを通さないアプリの着信の手順を次のとおり定める。

1. マニフェスト：`USE_FULL_SCREEN_INTENT`、`MANAGE_OWN_CALLS`、`POST_NOTIFICATIONS`、`RECORD_AUDIO`、`CAMERA`、`FOREGROUND_SERVICE` と型（`PHONE_CALL`、`MICROPHONE`、`CAMERA`、`SPECIAL_USE`）、`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`、`RECEIVE_BOOT_COMPLETED`、`WAKE_LOCK`。
2. 初回：通知の許可 → `canUseFullScreenIntent()` が偽なら設定画面へ誘導 → 電池の最適化の除外 → OS の通話の統合の登録。
3. 着信の合図（通知の経路、または常時接続）を受けたら、CallStyle の着信の通知（全画面の Intent、`CATEGORY_CALL`、Person、`setOngoing`、時間での自動停止、OS の既定の着信音を繰り返し）を出し、同時に OS の通話に加える。フォアグラウンドサービスの新規の起動は要らない。
4. 応答（通知の操作）で `phoneCall|microphone|camera` 型のフォアグラウンドサービスを起動し、5秒以内に CallStyle の通話中の通知で `startForeground`。音声の経路は Telecom のエンドポイントの API。
5. ロック中の着信の画面は `showWhenLocked` と `turnScreenOn`。
6. Android 15 では、起動時から起こすのは `specialUse` の常時接続だけ。

全画面の着信の許可の既定値は、国内の主な端末で［要実測］。拒否されていれば設定へ誘導する。

## 調査 I-05：家庭の回線と通話の到達性（2026-10-13）

### 1. 確認した事実（出典つき）

#### 1.1 国内の家庭の回線の IPv4 の方式

|方式|着信|1契約のポート数|使える範囲|
|---|---|---|---|
|MAP-E（RFC 7597）による IPv4 over IPv6|割り当てられたポートのみ|事業者により 240 個（16 ポート×15 ブロック。256 契約で1つの IPv4 を共有）または 1,008 個（64 契約で共有）|4096〜65535、または 1024〜65535。**80 と 443 は使えない**|
|DS-Lite（RFC 6333）による IPv4 over IPv6|**着信は一切できない**（事業者側で NAT）|—|—|
|PPPoE の IPv4|全ポート（動的なグローバル IP）|全部|新しい回線（10G）では提供されず、縮退している|

- MAP-E のポートの割り当ては RFC 7597 の規則による（既定で 0〜1023 を除く）。事業者の公式の案内は「ウェルノウンポート以外の 1,008 ポート」「TV 会議や Web カメラなど特定のポートを指定するものは利用できない」「固定 IP のプランはポートの制限なし」と述べる。［H1］［H2］
- 割り当てられたポートの中でのポートの転送に対応するルーターは、国内の主な製造者のものにある（「利用可能ポート」を表示するもの）。回線の事業者が貸すホームゲートウェイの内蔵の MAP-E での静的な NAT の可否は未確認。
- 固定の IPv4 のオプションは、事業者により月額 770〜3,245 円。

#### 1.2 IPv6 の着信

- プレフィックスは、ひかり電話なしで /64、ありで /56。ホームゲートウェイの IPv6 のフィルタは既定で外部からの着信を遮断し、許可の規則を加える必要がある。ひかり電話なしでホームゲートウェイを使う場合はフィルタ自体が無効なので、ホスト側のファイアウォールが必須。プレフィックスは半固定で変わり得るため、AAAA は DDNS が前提。
- 携帯電話の4事業者はいずれも IPv6 で発信できる（うち2社は IPv6 のみ + 464XLAT）。ただし、IPv4 のみの Wi-Fi（据え置きのホームルーター等）にいる家族がいるので、IPv6 のみの公開は単独の解にならない。［H3］［H4］

#### 1.3 その他の回線

- 一部の光回線は、2024年以降の新規や機器の交換で MAP-E が適用される場合があり、公式に「サーバーの公開には利用できない」と述べる。
- ケーブルテレビ系の回線は、1つのグローバル IP が付き、80 と 443 は遮断の対象外（遮断されるのは 53、135、137〜139、445 等）。ただし 100.64.0.0/10（RFC 6598、事業者の NAT）が付く事例がある。
- 携帯電話網のホームルーターの多くはプライベートの IPv4 でポートを開けられない。グローバル IP のオプションを持つものが1種ある（月額 105 円）。

#### 1.4 経路

- (a) IPv4 で直接：グローバル IP のある回線。80 と 443 を転送し、証明書は HTTP-01 で取れる。
- (b) IPv6 のみで公開：AAAA と DDNS、ホームゲートウェイの許可、ホストのファイアウォール。IPv4 のみのクライアントには (d) または (e) を併用。
- (c) MAP-E の割り当てポート：HTTPS を割り当てられたポート（例：41791）で待ち受け、URL にポート番号が付く。証明書は HTTP-01 が使えないので DNS-01 が必須（調査 I-06）。通話の UDP と TCP のポートも割り当ての中に置く。
- (d) VPS 経由の中継：WireGuard、SSH の逆方向の転送、frp、rathole（UDP も通る）。商用の無料のトンネル（HTTP と WebSocket のみ、UDP 不可、アップロード 100MB、動画の配信は規約で制限）と、商用のメッシュ VPN の公開機能（443 等の TCP のみ、帯域の制限）は、いずれもシグナリング専用で WebRTC のメディアには使えない。［H5］［H6］
- (e) VPS 上の TURN：通話の部品の内蔵の TURN（TLS 443、UDP 3478）か coturn。MAP-E でも DS-Lite でも UDP の発信はできるので、SFU は自宅、メディアは TURN 経由で成立する。帯域は VPS に全量乗る。

#### 1.5 通話の部品のポートと NAT

- 既定のポート：7880（WebSocket と API）、7881（TCP の ICE）、UDP 50000〜60000 または1ポートへの多重化（7882）、TURN の TLS 5349（負荷分散なしなら 443 が必須）、TURN の UDP 3478。NAT の設定は `use_external_ip`（STUN で公開 IP を発見）、`node_ip`（手動）、`use_ice_lite`。自己署名の証明書は非対応と明記。［H7］［H8］［H9］
- MAP-E の下では、UDP のポートを割り当ての中の1つに固定して同じ番号を転送し、`node_ip` を共有の IPv4 にする。外部 IP の置換でポート番号が維持されるか、MAP-E のルーターの NAT の型、IPv6 の候補の扱いは未確認［要実測］。DS-Lite は UDP の着信も不可。

### 2. 設計への帰結（第9章、第14章、D-14-3 へ）

設置の手順書と設置の道具は、次を検出し、分岐する。

1. WAN の IPv4 の種別：グローバル / 100.64.0.0/10（事業者の NAT） / RFC 1918（二重の NAT、ホームルーター）。
2. IPv4 over IPv6 の方式：MAP-E（割り当てポートの範囲）/ DS-Lite / 固定 IP / PPPoE。外から 80 が通らず割り当てポートだけが通れば MAP-E。

4. IPv6 の到達性：IPv6 で発信できるか、外から AAAA へ TCP が届くか、ホームゲートウェイのフィルタ、プレフィックスの変動（DDNS）。

- 「家庭の回線に置けば必ず動く」とは書かず、回線の方式ごとの成否と費用を手順書に明示する。DS-Lite と事業者の NAT の家庭は、VPS（または固定 IP）なしには成立しない。これは設計の検証で既知の制約として宣言する。

## 調査 I-06：ドメイン名と証明書（2026-10-13）

### 1. 確認した事実（出典つき）

#### 1.1 ドメイン名

- 有料のドメイン（2026年10月）：.com は更新が年 1,700〜2,000 円または 11 ドル程度、.jp は年 1,300〜3,900 円。初年 0〜1 円で更新が高いものがあり、更新の額で比べる必要がある。無料の権威 DNS と API を提供する事業者に NS を向ければ、他社で買ったドメインでも DNS-01 の自動化に使える（ゾーン限定のトークン）。
- 無料の DDNS：Public Suffix List に収録されているものが複数あり（収録されていれば、自分のサブドメインが独立した登録ドメインとして扱われ、証明書の発行のレート制限を他の利用者と取り合わない）。DNS-01 の API を持つもの、TTL が固定のもの、一定期間の無通知で停止・削除されるもの（1週間で停止、1か月で削除）、Caddy の DNS プラグインがあるものとないものがある。IP アドレスをホスト名に埋め込む方式は、IP が変わるとホスト名も変わる。［I1］［I2］

#### 1.2 証明書

- Let's Encrypt の検証：HTTP-01 は 80 が必須（多視点の検証）、TLS-ALPN-01 は 443 が必須、DNS-01 は着信ポートが不要でワイルドカードが可。［I3］
- プロファイル：`classic` 90日（既定）、`tlsserver` 45日、`shortlived` 160時間。既定の有効期間は 2027年2月10日に 64日、2028年2月16日に 45日に短縮される。ARI 経由の更新はレート制限を免除される。［I4］［I5］［I6］
- IP アドレスの証明書：2026年1月15日に一般提供。`shortlived`（6日）限定、HTTP-01 と TLS-ALPN-01 のみ（DNS-01 不可）。［I7］
- OCSP の応答は 2025年8月6日に停止、期限の通知メールは 2025年6月4日に終了。［I8］
- 別の無料の CA（ACME、90日）があり、Caddy 2.8 以降では `email` のグローバルオプションを設定した時だけ自動の代替になる。［I9］

#### 1.3 Caddy

- 既定で HTTP-01 と TLS-ALPN-01。DNS チャレンジを有効にすると他が無効。`tls { dns <provider> {env.TOKEN} }`、`propagation_timeout`。グローバルの `acme_dns`、`local_certs`、`https_port`。DNS のプラグインは builder のイメージで `xcaddy build --with` により組む。対応する DNS の提供者は 100 を超える。［I10］［I11］
- MAP-E の典型：`https_port <割り当てポート>` と DNS-01。

#### 1.4 ブラウザの要件

- Service Worker と `getUserMedia` は secure context（HTTPS または localhost）限定。LAN の `http://192.168.x.x` では動かない。［I12］
- 自己署名の証明書：iOS は手動で入れたプロファイルを既定で信頼せず、「証明書信頼設定」で全面的に信頼する操作が別途要る。その状態で Service Worker と Push が完全に動くかは未確認。家族の端末ごとの手作業と更新時の再配布を要するので、採らない。［I13］

#### 1.5 DDNS の更新

- ルーター側の DDNS は、MAP-E でルーターがグローバルの IPv4 を持たない場合に AAAA と TXT を書き換えられないことがある。コンテナ側で更新する（A と AAAA を同時に、5分ごと）。
- IPv6 では、サーバーの一時アドレス（RFC 4941）を無効にし、安定したアドレス（EUI-64）にする。

### 2. 設計への帰結（第14章、D-14-2 へ）

- 家族のサーバーの名前は、独自のドメイン1つ（年 1,300〜2,000 円程度）か、Public Suffix List に収録された無料の DDNS のサブドメインとする。手順書は両方を示し、費用を明記する。「0 円」の道を残す（D-2-6）。

## 調査 I-07：通話の基盤（2026-10-13）

### 1. 確認した事実

- 自分で立てる同種のサーバーの通話の形は2つに分かれる：(a) 外部の会議サービスへのリンク（メディアを持たない）、(b) 内蔵の P2P と任意の SFU。少人数（2人、または4〜5人まで）は P2P と TURN、それ以上は SFU という線引きが共通する（調査 A の 10）。
- TURN は coturn と TURN REST API（共有の秘密と TTL による一時の資格情報）が事実上の標準で、静的なユーザー名とパスワードは非推奨。TTL は 1〜24時間。ポートは 3478（UDP、TCP）、5349（TLS）、中継は 49152〜65535/udp。企業のファイアウォール対策として 443 で TURNS を提供することが推奨される。TURN はプロキシを通せず、ホストのネットワークで直接公開し、公開 IP を要する。［J1］
- 公開のメッセージングのプロトコルのグループ通話は、SFU（本システムの候補と同じ部品）と、トークンを発行する小さなサービスで組まれている。
- 本システムの候補の SFU：Apache-2.0。1台で動き、Redis を要しない。TURN を内蔵する（TLS 443、UDP 3478）。ウェブ、Android、iOS、クロスプラットフォームの UI のフレームワーク向けの SDK。公式のベンチマーク（16コア）は 720p で 150 の送信と 150 の受信を CPU 85% で処理。参加者あたりの CPU と RAM の数値は公開されていない。SDK の既定の画質は h360 450kbps、h720 1.7Mbps、h1080 3.0Mbps。［J2］［J3］［J4］
- 代替：部品のライブラリ（クライアントとシグナリングを自作する）、C で書かれた GPL のサーバー（SIP が要る時以外に利点がない）、P2P と coturn のみ（1対1は足りるが、10人のグループは端末の上りと処理が足りない）。

### 2. 設計への帰結（第6章、第9章、D-9-5 へ）

- 通話の基盤は、候補の SFU（TURN 内蔵）を採り、1対1もグループも同じ仕組み（SFU 経由）で扱う。P2P の経路は設けない（iPhone のホーム画面のウェブアプリの制約と NAT の多様性のもとで、経路を2つ持つ負担に見合わない）。
- TURN は SFU の内蔵のものを使い、TLS を 443（または MAP-E の割り当てポート）で提供する。資格情報は共有の秘密と TTL（24時間）による一時のもの。
- グループ通話の人数の上限は、家族のサーバーの上りの帯域で決まる（調査 I-12）。既定の上限は基本設計で定める。
- 通話の映像は、サイマルキャストと adaptive stream により、受け手の画面の大きさと回線に応じて落とす。

## 調査 I-08：写真と動画の形式の互換（2026-10-13）

### 1. 確認した事実（出典つき）

- iPhone の既定：設定 > カメラ > フォーマットは「高効率」（HEIF、HEVC）が既定で、「互換性優先」（JPEG、H.264）を選べる。共有の時に受信側が非対応なら JPEG と H.264 に自動で変換する。4K60 等の高いフレームレートは高効率が必須（設定画面の表示。公式のガイドは未確認）。［K1］

- HDR：iPhone 12 以降は Dolby Vision（HLG ベース、10ビットの HEVC）で録画する（未確認）。8ビットの H.264 に素朴に変換すると灰色に浮くため、トーンマップが必須。iPhone 15 以降の写真は ISO 21496-1 のゲインマップ（未確認）。

- ブラウザの対応（2026年10月）：HEIC は Safari 17 以降のみで、Chrome と Firefox は非対応。AVIF は全主要ブラウザ。HEVC の動画は Safari 11 以降（HDR を含む）、Chrome 107 以降はハードウェアのデコーダがある端末のみ、Firefox は 2025年以降ハードウェアの再生のみ。H.264 と AAC の MP4 は全ブラウザ。WebCodecs は Safari 26 以降で完全。［K3］
- ffmpeg：`-autorotate` が既定で有効で、回転の情報に従う。トーンマップのフィルタ（hable 等）と、GPU 用の `tonemap_vaapi`、`tonemap_opencl`。進捗は `-progress pipe:1 -nostats` で `out_time_us` 等が 0.5 秒ごとに出る（6.1.1 で実測）。Node.js の包みのライブラリの `percent` は「非常に不正確」と明記されている。［K4］
- 画像の部品：libheif（HEIC のデコード。2026年だけで 73件のセキュリティの勧告があり、更新の運用が必須）。Node.js の画像の部品の既製のバイナリは HEIC に非対応（特許の都合で、libheif、libde265、x265 を組み込んだ libvips が要る）。同部品は既定で全メタデータ（EXIF の向きを含む）を除去し、`rotate()` を引数なしで呼ぶと向きを適用してから Orientation を除く。［K5］［K6］

### 2. 設計への帰結（第8章、D-8-2、D-8-3 へ）

- 配信の形式：動画は MP4（H.264 High、yuv420p 8ビット、AAC-LC 128kbps、`+faststart`、1080p 上限、fps 60 上限、CRF 23 または 4〜6Mbps）。画像は JPEG（品質 82〜85、EXIF を除き向きを適用）とサムネイル（320px、1280px）。AVIF と WebP は任意。原本は保持する（調査 I-12 の容量の試算に含める）。
- HEIC は、`heif-dec` または ImageMagick（libheif）で JPEG にしてから画像の部品に渡す。HDR の動画はトーンマップ（hable）を通す。回転は ffmpeg の既定に従う。
- EXIF の除去と向きの保持は、画像の部品の `rotate()` で同時に成立する。
- 変換の進捗は `out_time_us` と ffprobe の duration から自前で算出し、変換中はトークに「処理中」と示す。
- 端末側の変換（WebCodecs）は、Safari 26 以降で可能だが、コンテナ化と電池の負担が未確認であり、v1 ではサーバー側の変換を正とする。

## 調査 I-09：日本語の全文の検索（2026-10-13）

### 1. 確認した事実（出典つき）

- PostgreSQL の標準の全文検索の既定のパーサーは空白と句読点で区切るため、日本語を分かち書きしない。pg_trgm は2文字の日本語の語に trigram を作れず全スキャンに落ちる。pg_bigm は2-gram の GIN で1〜2文字の検索が速いが、Recheck が要り、更新が緩やか。［L1］［L2］
- PGroonga：Groonga ベース。「Recheck なしで索引だけで正確に絞れる」「結果が多い時に pg_bigm より速い」。PostgreSQL 12〜18、Ubuntu 22.04 と 24.04、Docker のイメージがある（4.1.0）。既定のトークナイザは TokenBigram、正規化は NormalizerAuto（NFKC で全角と半角、大小を同一視）。形態素解析（TokenMecab）も選べる（Docker のイメージでの辞書の同梱は未確認）。弱点：クラッシュセーフではない（プロセスの異常終了で REINDEX）。`pgroonga_crash_safer` で緩和できる（書き込みの性能が落ちる）。バックアップは pg_dump で索引を再作成する。［L3］［L4］
- 同種のソフトウェアの先例：公開のメッセージングのプロトコルの参照実装は `to_tsvector('english')` で、日本語は LIKE 相当の品質。自分で立てる同種のサーバーの1つは PGroonga を選択肢として持ち、「日本語と中国語を含む全言語を同時に検索」「十分に試験でき次第、常時使用に切り替える予定」と述べる（最良の先例）。別のオープンソースの SNS は、検索の提供者を sqlLike、sqlPgroonga、外部のエンジンから選べる。［L5］
- 外部の検索エンジン（Rust 製、C++ 製、JVM 製）は、日本語の分かち書きに対応するが、ディスクが生データの10倍、または RAM が 1〜2GB（未確認）で、家族の規模では過剰。
- 端から端の暗号化を採る場合の端末側の検索：ブラウザの SQLite（WebAssembly）の OPFS の VFS（COOP と COEP が必須の方式と、不要で高速だが単一スレッドの方式）。FTS5 の trigram は3文字未満のクエリに一致しない（「遠足」が引けない）。2文字の対策は、bigram を自前で作るか、`Intl.Segmenter`（iOS 14.5 以降、Chrome 87 以降、Firefox 125 以降）で分かち書きした語を索引にする。［L6］［L7］

### 2. 設計への帰結（第7章へ）

- 端から端の暗号化を採らない場合（調査 I-10 の設計3）、検索は家族のサーバーの PostgreSQL に PGroonga（TokenBigram、NormalizerAuto、`pgroonga_crash_safer` を有効）で行う。検索の演算子は `&@~`（ウェブの検索風のクエリ）。バックアップは pg_dump で取り、戻す時に索引を再作成する。
- 採る場合（設計1）、検索は端末の中で、ブラウザの SQLite（OPFS）の FTS5 の trigram を基本に、2文字の語を bigram の補助の索引で補う。
- O-01 の結論により、どちらかを基本設計で確定する。

## 調査 I-10：端から端の暗号化の実現性（2026-10-13）

### 1. 確認した事実（出典つき）

#### 1.1 ウェブのクライアントで端から端の暗号化を行っている実装の形

- ブラウザの中で自分の鍵を持ち、端から端の暗号化を行うウェブのクライアントは、公開されているものでは少数である。確認できた形は次の3種である（製品名は記さない）。
  - 公開のメッセージングのプロトコルの参照実装（Rust で書いた暗号の部品を WebAssembly にしたもの）：鍵は IndexedDB に置く。保存の鍵（32 バイト）またはパスフレーズを与えると値を暗号化（XChaCha20-Poly1305）し、与えなければ暗号化しない。暗号化の鍵も同じ IndexedDB にあるため、同じオリジンの保存領域を読める者は鍵を復元できる。［B1］［B2］
  - MLS（RFC 9420）の実装を WebAssembly にしたもの（GPL-3.0）：暗号化した永続の保存領域を内蔵する。本番で MLS が既定かは未確認。［B3］
  - 電子メールの暗号化のウェブクライアント：秘密鍵をブラウザで生成し、パスワード由来の鍵で暗号化してサーバーに保管する。脅威モデルの文書に「サーバーが侵害されると不正な JavaScript を配られ得る」と明記している。［B4］
- 一般的な通信アプリのウェブ版の多くは、ブラウザに独自の鍵を持たず、主端末のスマートフォンに鍵を置き、QR により端末を結び付ける形（最大4台等）か、スマートフォンを経由する中継である。ブラウザ版を持たないものも多い。［B5］
- 配られる JavaScript の完全性：ある通信アプリのウェブ版は、第三者が公開するハッシュとブラウザの拡張機能により JavaScript を照合する仕組みを設けている（Chrome、Edge、Firefox の拡張のみ）。iOS の Safari では拡張を使えない。Isolated Web Apps は WebKit が「Blocked」の立場（2023年5月9日）であり、iOS では使えない。Subresource Integrity は HTML 自体が同じサーバーから来るため効かない。［B6］［B7］

#### 1.2 ブラウザの基礎の部品

- WebCrypto の抽出不可の鍵（`extractable: false`）は `exportKey` を禁じるだけで、structured clone により IndexedDB に保存できる。W3C の仕様自身が「端末の保存領域を読める者は鍵の素材を回収し得る」と明記している。［B8］
- iOS の保存領域の消え方は調査 I-01 の 1.8 のとおり。鍵の唯一のコピーを端末に置くと、アプリの削除、Safari のデータの消去、容量の逼迫で失われる。
- WebAuthn の PRF 拡張（パスキーから対称鍵を導く）：Safari 18.0（2024年9月16日）で追加された。MDN の互換性データでは、登録（`create()`）側は Chrome 116、Edge 116、Firefox 139、Safari 18 で対応、認証（`get()`）側は Safari が非対応と記載され、WebKit の発表と食い違う。鍵の導出は毎回 `get()` で行うため、iOS で実用になるかは［要実測］。WebKit の記録に、クロスデバイス（hybrid）の流れで PRF が使えない（2025年4月27日、未解決）、セキュリティキーで PRF の出力が null になる（2026年）がある。ホーム画面のウェブアプリの中での動作、iCloud キーチェーンの同期での再現性は未確認。［B9］［B10］［B11］

#### 1.3 MLS（RFC 9420）のブラウザでの実装の成熟度

- MLS の実装は複数あり、WebAssembly の対象を持つものがある（Rust の実装 0.9.1、2026年10月7日。別の Rust の実装 0.56.0、2026年8月19日。TypeScript の実装 1.6.4）。いずれも第三者の監査を受けたことを明記していない。［B12］［B13］［B14］
- IETF の MIMI ワーキンググループの文書（プロトコル、内容の形式、ルームの方針）は、すべて Internet-Draft であり RFC になっていない。［B15］
- 公開のメッセージングのプロトコルにおける MLS の取り組みは、2025年6月の時点で「状態を永続化しない、試験用のアカウント専用」の試作にとどまる。［B16］
- 帰結：部品は動くが、配送サービス（順序付け、epoch の直列化）、KeyPackage の配布、履歴（MLS は過去の epoch を新規の参加者に読ませない）、複数の端末を自分で設計する必要がある。

#### 1.4 主端末なしでの鍵の受け渡しと復旧

- 公開のメッセージングのプロトコルは、クロス署名の鍵とバックアップの鍵を Secret Storage（`m.secret_storage.v1.aes-hmac-sha2`、パスフレーズは PBKDF2、リカバリーキーは base58）に置き、新しい端末はリカバリーキーの入力か、既存の端末からの検証（絵文字の照合または QR）で信頼を得る。リカバリーキーは48文字。すべての端末とリカバリーキーを失うと、身元を作り直すほかなく、過去のメッセージは復号できない。［B17］［B18］
- 一般的な通信アプリの「PIN による復旧」や「端から端の暗号化したバックアップ」は、試行回数を制限する信頼できる実行環境（TEE、HSM）を事業者が運用することを前提とする。個人が運用するサーバーでは、低エントロピーの PIN を安全にできない。［B19］［B20］
- 公開のメッセージングのプロトコルの参照実装は、既定で「初回に検証（バックアップの設定）を強制する」設定を持つ。［B21］

#### 1.5 端から端の暗号化のもとでのサーバー側の機能

- 検索：クライアントの索引のみ。参照実装の検索の部品はデスクトップ向けであり、ブラウザの IndexedDB 向けではない。
- URL のプレビュー：クライアントが直接取得する（閲覧者の IP アドレスが相手に見える、CORS の制約）、URL だけをサーバーの取得専用のプロキシに送る（URL が漏れる）、または無効にする、の3択。
- 通知：公開のメッセージングのプロトコルの push gateway は `event_id_only` により本文なしの通知を送れる。ネイティブのアプリは通知の拡張（iOS の Notification Service Extension）で復号するが、ホーム画面のウェブアプリにそれはない。iOS の Web Push は Service Worker の push のイベントを起動するので、Service Worker の中で取得と復号と表示を行うことは仕様上可能（WebKit の明文は未確認）。宣言型の Web Push（iOS 18.4 以降）では、Service Worker が復号して置き換えの通知を出せばそれが採用され、できなければ宣言型の汎用の本文が表示される（調査 I-01 の 1.2）。［B22］

### 2. 設計への帰結（第11章、第13章、O-01 へ）

採り得る設計は3つであり、それぞれの限界は次のとおりである。O-01 の結論は、これを基礎として基本設計で定める。

|設計|内容|限界|
|---|---|---|
|設計1：送信者鍵の方式（公開のメッセージングのプロトコルの参照実装を WebAssembly で用いる）+ サーバーに置く暗号化したバックアップ（リカバリーキー必須）|参照実装が本番で用いている構成。端末の鍵、使い捨ての鍵、端末間のメッセージ、鍵のバックアップ、Secret Storage のサーバー API が要る|配られる JavaScript の信頼はサーバー任せ。通知の本文は復号できた時だけ具体化。検索は端末の中のみ。リカバリーキーを失えば履歴を失う。サーバー API は事実上そのプロトコルの互換となる|
|設計2：MLS（RFC 9420）|配送サービス、履歴、複数の端末を自分で設計する|部品は未監査、関連の標準は草案。小規模の自己ホストには時期尚早|
|設計3：端から端の暗号化なし（TLS + 家族のサーバー + 保存時の暗号化）|検索、URL のプレビュー、通知の本文、履歴の復旧が素直に成立する|管理者（サーバーを操作できる者）が記録を読める。設計1との実際の差は「サーバーが侵害された時に過去の記録が読めるか」である|

- どの設計でも、iOS で改竄された JavaScript を検知する仕組みは作れない。配信の完全性は家族のサーバーと TLS に依存する。
- どの設計でも、PIN だけでの安全な鍵の復旧は作れない。端から端の暗号化を採るなら、高エントロピーのリカバリーキー（紙またはパスワードマネージャに保管）を主とし、パスキーの PRF による補助は［要実測］の結果により加える。バックアップの設定を初回に必須とする。
- 設計1と設計3の差が「サーバー侵害時の過去の記録」に限られる一方、設計1は検索・プレビュー・通知・機種変更・高齢者の鍵の管理のすべてに負担を生む。本システムの脅威モデル（家族のサーバーを家族が運用する）における比較を、基本設計の該当の章で行い、O-01 を解消する。

## 調査 I-12：家族のサーバーの機械の目安（2026-10-13）

### 1. 確認した事実（出典つき）

- 通話：候補の SFU の SDK の既定の画質（h360 450kbps、h720 1.7Mbps）から、家族のサーバーの上りの帯域を試算すると、5人が全員 720p を受ける場合 5×4×1.7 ≈ 34Mbps（360p の層なら 9Mbps）、8人が 720p で ≈ 95Mbps（360p なら 25Mbps）。実効の上りが 30〜50Mbps の回線で5人の 720p は成立し、8〜10人は受け手の画質を 360p に落とす前提になる。SFU の CPU と RAM の参加者あたりの数値は公開されていない（10人のルームで低消費電力の4コアの CPU の1コア未満、RAM 100〜300MB と推定。未確認）。
- 動画の変換：低消費電力の4コアの CPU（6W 級、2023年）は、ハードウェアの変換（HEVC 10ビットのデコードとエンコード、AV1 のデコード）に対応し、Docker では `/dev/dri/renderD128` の受け渡しと render グループが要る。HDR から SDR へのトーンマップは OpenCL が要る。消費電力はアイドル 6W、負荷 22〜25W。速度（未確認・推定）：ソフトウェアの 1080p のエンコードが実時間の 0.7〜1.2 倍、ハードウェアなら 4K の HEVC 10ビットから 1080p の H.264 へ実時間の 2〜3倍。単板のコンピュータ（最新版）は、4K60 の HEVC のハードウェアのデコードのみでエンコーダを持たず、1080p30 の H.264 のソフトウェアのエンコードで CPU の 30〜40%。［M1］［M2］［M3］
- メモリ：PostgreSQL の `shared_buffers` は既定 128MB、1GB 以上なら 25%。PGroonga は mmap で OS のキャッシュに乗る。予算：OS と Docker 600〜900MB、Caddy 30〜50MB、アプリ 150〜400MB、PostgreSQL 250〜400MB、SFU 100〜300MB、ffmpeg 1本 300〜600MB（1080p）または 1〜1.5GB（4K の HEVC 10ビットとトーンマップ。未確認）。常駐 1.5〜2GB、ピーク 4〜5GB。［M4］
- 容量：iPhone の動画は 1080p30 の HEVC で 60MB/分、4K30 で 170MB/分、4K60 で 400MB/分（設定画面の表記。未確認）。写真は HEIF 12MP で 1.5〜3MB、ProRAW で 25〜75MB。配信用の H.264 1080p 5Mbps は 37.5MB/分。家族6人、写真 30枚/日、動画 5分/日で、写真の原本 27GB/年（サムネイル込み 34GB）、動画の原本 110GB/年（1080p）または 310GB/年（4K）、配信用 68GB/年。合計で年に約 210GB（1080p）〜410GB（4K）。2TB で 5〜10年。
- 価格（2026年10月13日）：単板のコンピュータの 8GB は本体 約 36,000 円で、一式（ケース、冷却、電源、NVMe）で 52,000〜55,000 円。低消費電力の4コアの小型 PC（16GB、512GB）は 25,000〜60,000 円（セールの実勢は未確認）。中古の企業向けの小型 PC（第8世代、16GB）は 36,000 円程度。国内の VPS（2GB）は月 770〜2,033 円で、GPU がなく、ディスクが 100〜200GB。電気代は 31 円/kWh で、8W の機械が月 180 円、15W で 340 円。3年の総額は小型 PC が約 41,500 円、VPS（2GB）が約 62,500 円。

## 調査 I-13：PC のブラウザにおける通知と通話（2026-10-13）

### 1. 確認した事実（出典つき）

#### 1.1 Web Push

- 対応の版：Chrome 42、Edge 79 以降（Chromium 版）、Firefox 44（72 以降はユーザーの操作が必須）、Safari 16（macOS Ventura 以降。Safari が起動していなくても配送される）。［C1］［C2］
- Chrome と Edge は `applicationServerKey`（VAPID）が必須。Edge は `userVisibleOnly: true` が必須で、Service Worker が通知を出さないと Edge が汎用の通知を表示する。［C1］［C3］
- 本文の大きさ：RFC 8030 は 4096 バイト以下の本文に 413 を返してはならないと定め、`TTL` ヘッダを必須とし、`Urgency` と `Topic` を定める。Mozilla の push サービスは 4096 バイト、FCM を橋渡しする経路は 2744 バイト、`Topic` は32バイトの英数字。［C4］［C5］

#### 1.2 ブラウザを閉じている時の通知

- Chrome：バックグラウンドモードは Windows と Linux のみで、既定は無効。ユーザーが設定で切り替える。［C6］
- Edge：バックグラウンドモードは Windows のみで、既定は無効。［C7］
- Firefox：バックグラウンドモードはなく、起動中のみ受信する。Firefox 142（2025年8月19日）で、Windows で終了後に persistent な通知をクリックすると該当のページで起動するようになった。［C8］
- Safari（macOS）：Safari が起動していなくても配送される。［C2］

#### 1.3 インストール（PWA）

- Chrome と Edge はデスクトップの全 OS でインストールできる。
- Firefox は PWA 相当の機能を 86 で削除し、143（2025年9月16日）で Windows 限定の「Taskbar web apps」を加えた（Microsoft Store 版は不可）。［C9］［C10］
- Safari（macOS 14 以降）は「Dock に追加」で、Web Push とバッジに対応する。追加の時に Cookie は写されるが、他のローカルの保存領域は写されない。macOS Sequoia（Safari 18）では、scope に一致するリンクをウェブアプリで開く。［C11］［C12］

#### 1.4 画面の共有（`getDisplayMedia`）

- Chrome 72、Edge 79、Firefox 66、Safari 13（macOS）。iOS の Safari、Android の Chrome と Firefox は非対応。音声の取得は Chrome 74 以降のみ。Linux の Wayland（PipeWire）は未確認。［C1］

#### 1.5 背景のぼかし

- `MediaStreamTrackProcessor`：Chrome と Edge 94、Safari 18（dedicated worker のみ）、Firefox は非対応。Firefox では `<video>` から canvas に描き `captureStream()` で取り出す代わりの経路が要る。［C1］
- OS 側のぼかし（`backgroundBlur` 制約）は、仕様が非公式の草案で、Chrome は origin trial 止まり。採用できない。［C13］［C14］
- 推論の部品として、ウェブ向けの画像の分割の部品がある（サンプルは Apache-2.0。モデルのライセンスと GPU の委譲の明記は未確認）。［C15］

#### 1.6 バッジ、通知のオプション、スロットリング

- バッジ：Chrome と Edge 81（インストール済みの PWA）、Safari 17（macOS のウェブアプリ）、Firefox 非対応。［C1］
- 通知の `actions`：Chrome 53、Edge 18、Firefox 152、Safari 非対応。`image` は Chrome 56 のみ。［C1］
- Chrome 88 のタイマーの制限は、WebRTC を使っている間（RTCDataChannel か MediaStreamTrack が生きている）は免除される。Memory Saver は通話中のタブを破棄しない。［C16］［C17］

#### 1.7 対応表

|機能|Chrome|Edge|Firefox|Safari（macOS）|
|---|---|---|---|---|
|Web Push|42 以降（VAPID 必須）|79 以降|44 以降（72 以降は操作必須）|16 以降|
|閉じていても通知|Windows と Linux の背景モード（既定は無効）|Windows のみ|不可|可|
|PWA のインストール|可|可|Windows の 143 以降|14 以降|
|バッジ|81 以降|81 以降|不可|17 以降|
|画面の共有|72 以降（音声は 74 以降）|79 以降|66 以降（音声は不可）|13 以降（音声は不可）|
|映像の加工（MediaStreamTrackProcessor）|94 以降|94 以降|不可|18 以降（worker）|
|通知のボタン|53 以降|18 以降|152 以降|不可|

### 2. 設計への帰結（第5章、第9章、第10章へ）

- PC の通知は、ブラウザが起動している間の受信を基本とし、「閉じていても届く」は Safari（macOS）とバックグラウンドモードを有効にした Chrome と Edge（Windows、Linux）に限ると案内する。
- 画面の共有は PC（全ブラウザ）と Android から行え、音声の共有は Chrome と Edge に限る。
- 背景のぼかしは、ブラウザの中で映像を加工する方式で実現し、Firefox には canvas 経由の代わりの経路を用いる。OS 側のぼかしの API には依存しない。
- 通知のボタン（返信）は、対応するブラウザでのみ出す。
- 通話中はブラウザのスロットリングが免除されるため、通話の画面はタブを背景にしても続く前提で設計できる。

#### 1.2 JIS と法

- JIS X 8341-3:2016 が現行で、ISO/IEC 40500:2012（WCAG 2.0）と技術的に同一。ウェブアクセシビリティ基盤委員会（WAIC）が解説、方針の策定、試験の実施のガイドラインを提供する。WCAG 2.1 または 2.2 に対応する改正の公示は未確認。［D5］
- 改正障害者差別解消法（2024年4月1日施行）により、事業者の合理的配慮の提供が義務となった。家族の自己利用のアプリは「事業者が不特定の者に提供する」ものではなく、直接の義務の対象にはならないと見込むが、本システムは WCAG 2.2 AA を自主的な基準として採る。［D6］
- デジタル庁「ウェブアクセシビリティ導入ガイドブック」（2025年10月16日更新）は JIS X 8341-3:2016 を参照する。［D7］

#### 1.3 数値の指針（日本と各 OS）

- デジタル庁デザインシステム（タイポグラフィ）：本文と UI の文字は 16 CSS px 以上、14 px 未満は原則不可。行間は本文 160〜170%（最低 150%）、見出し 140%。フォントは Noto Sans JP（SIL Open Font License 1.1）。色：テキスト 4.5:1、非テキスト 3:1。［D8］［D9］
- Apple Human Interface Guidelines：コントロールの既定の大きさ 44×44 pt（最小 28×28）、文字の拡大は 200% まで想定、iOS の本文（Body）は 17pt、行送り 22（最小の設定で 14pt、アクセシビリティの最大で 53pt）、最小 11pt。コントラストは 17pt 以下 4.5:1、18pt 以上 3:1。Reduce Motion で拡大縮小、奥行き、ぼかしの動きを抑える。［D10］［D11］
- Android：タッチの領域 48×48 dp、18sp 未満（太字は 14sp 未満）は 4.5:1、それ以外 3:1。Android 14 で非線形の文字の拡大、最大 200%。［D12］［D13］

#### 1.4 端末の文字の大きさの設定との連動

- iOS：`font: -apple-system-body` 等の `-apple-system-*` のキーワード（iOS 9 以降）はシステムのフォントのスタイル全体を表す。これが「文字サイズ」の設定（Dynamic Type）に追随するかの WebKit の明文は未確認［要実測］。`rem` と `px` は追随しない。入力欄の文字が 16px 未満だと iOS の Safari が自動で拡大する（広く知られた振る舞い。一次資料は未確認）。［D14］
- Android の WebView：`setTextZoom` の既定は 100、`setDefaultFontSize` は 16、`setMinimumFontSize` は 8。システムのフォントの拡大率を WebView が自動で適用するかは文書に記述がなく未確認［要実測］。［D15］
- メディアクエリの対応：`prefers-color-scheme` は Chrome 76、Firefox 67、Safari 12.1、iOS 13。`prefers-reduced-motion` は Chrome 74、Firefox 63、Safari 10.1。`prefers-contrast` は Chrome 96、Firefox 101、Safari 14.1。`forced-colors` は Chrome 89、Firefox 89、Safari 16。［D16］

#### 1.5 スクリーンリーダーとトークの流れ

- WAI-ARIA 1.2：`log` はライブ領域（既定は polite）、`status` はバックアップめな通知、`alert` は重要で時間的、`feed` は記事の連なり。［D17］

## 調査 I-15：地図の取得（2026-10-13）

### 1. 確認した事実（出典つき）

- 公開の地図の共同プロジェクトのタイルの利用方針：アプリは自分を名乗る固有の User-Agent を送ること（汎用の既定値は遮断される）、地図の上に帰属の表示（© OpenStreetMap contributors）を隠さずに置くこと、サーバーのキャッシュのヘッダに従う（読めなければ各タイルを7日以上キャッシュする）こと。一括のダウンロード（利用者が見ているタイル以外の先読み、領域の事前取得、オフラインの保存）は禁止。利用がサービスを劣化させれば予告なく遮断される。「オフラインの地図が要るなら、自分でタイルを配信するか、それを明示的に許す提供者を使う」。［N1］
- 地図のデータのライセンスは Open Database License 1.0 で、帰属の表示が要る。タイルについては「第三者に無償の地図の API やタイルを提供することはできない」と述べ、別の利用方針を置く。［N2］
- 自分のサーバーで地図を持つ方式：ベクトルのタイルを1つのファイルにまとめた形式（PMTiles。HTTP の Range 要求で必要なタイルだけを取り、タイルのサーバーが要らない。形式と道具は BSD。内部でタイルを重複排除し、全球のベクトルの地図で 70% 以上小さくなる）。全球の日次のビルド（ズーム 0〜15）は約 120GB で、領域を切り出す道具（`pmtiles extract`、`--maxzoom` でズームを1段減らすごとに約半分）がある。データは Open Database License の Produced Work で帰属の表示が要る。ビルドの URL は変わり得るので、自分の置き場に移すことが求められる。［N3］［N4］
- 描画の部品：ベクトルの地図をブラウザで描く部品は BSD-3-Clause（内部に MIT と BSD-3-Clause の部品を含む）。［N5］

### 2. 設計への帰結（第7章の位置情報、第13章の外へ送る情報 へ）

- 位置情報の送信と表示の地図は、公開の共同プロジェクトのタイルのサーバーを直接に使わない。利用方針が許すのはブラウザからの逐次の取得だけで、家族の端末の閲覧の様子が外部に見え、キャッシュと User-Agent の規則を各端末で守る負担があるためである。
- 家族のサーバーに、日本（または管理者が選ぶ領域）のベクトルの地図を PMTiles の1ファイルで置き、家族のサーバーから Range 要求で配る。設置の道具が領域を切り出して置く。日本の全域をズーム 14 まで切り出した大きさは［要実測］。帰属の表示（© OpenStreetMap contributors）を地図の上に置く。
- これにより、地図の取得は家族のサーバーの外へ出ない。設計計画書 第13.4節の「地図の取得先」の行は、家族のサーバーの中で閉じることになる（設計計画書の改訂で反映する）。地図のデータの更新は、管理者が任意に行う（設置の道具に更新の機能を持たせる）。

## 調査 O-03：Android のアプリの形（2026-10-13）

### 1. 確認した事実

- ウェブの画面を包む部品（設計計画書 第6.2節の候補）：最新の大版（2025年12月8日）は minSdk 24、WebView は Chrome 60 以上。WebView の `getUserMedia` の許可の要求をネイティブの実行時権限に橋渡しする仕組みを持つ。通知の公式の部品は、データのみの通知をアプリが終了している時に受け取れず、独自のサービスが要る。全画面の着信、OS の通話の統合、UnifiedPush の部品は見つからず、独自の Kotlin の部品が要る（調査 E の 5.1）。
- Trusted Web Activity：JavaScript の JS ブリッジがなく、着信と通話の統合の受け口を作れない。
- 公開のメッセージングのプロトコルのネイティブのクライアント（先例）：ネイティブのシェル（Compose）の中の WebView で通話（WebRTC）を行い、着信と通知と音声の経路をネイティブで扱う。

### 2. 設計への帰結（O-03 の解消）

- Android のアプリは、Kotlin のネイティブのシェル（Jetpack Compose）の中に `android.webkit.WebView` でトークの画面を置き、着信（調査 I-04）、通知の受信（調査 I-02）、OS の通話の統合、音声の経路、常時接続、自己更新（調査 I-03）をネイティブで書く形とする。
- 退ける案：ウェブの画面を包む部品（Android 固有の要件のすべてに既製の部品がなく、代わりに版の周期に縛られる）、Trusted Web Activity（JS ブリッジがない）、クロスプラットフォームの UI のフレームワーク2種（iPhone 側がホーム画面のウェブアプリである本システムでは画面を共有できない）。
- 通話の媒体は、まず WebView の中の通話の部品の JavaScript 版（先例と同じ。許可の橋渡し、通話の音声モード、`microphone|camera` 型のフォアグラウンドサービス）で組み、Bluetooth と車載の音声のエンドポイントの切り替えが WebView から制御できなければ［要実測］、通話の部品の Android 版（Apache-2.0）に切り替える。通話の部品の JavaScript 版の WebView での対応は未確認。

### 1. メッセージの語彙（公開のメッセージングのプロトコルの仕様）

- 公開のメッセージングのプロトコルの仕様（クライアントとサーバーの API、push gateway の API、メディアの API）の最新版（v1.19、2026年7月8日）から、次の語彙と形を再利用する。［S1］
  - 「イベント = 不変の記録、状態 = 最新の (type, state_key)」。イベントは type、sender、サーバーが付ける時刻、content、識別子を持つ。
  - 送信の冪等性はクライアントが付ける transaction id で担保し、サーバーは unsigned.transaction_id でエコーを返す。
  - 関係：編集は `rel_type: m.replace` + `m.new_content`（サーバーは本文を書き換えず、クライアントが適用）、リアクションは `m.annotation` + key、返信は `m.in_reply_to`、スレッドは `m.thread`。
  - メンションは本文の一致ではなく、`m.mentions{user_ids[], room}` の欄で判定する（意図的メンション）。
  - 既読は3種：公開の既読 `m.read`、自分だけの既読 `m.read.private`、読み終えた位置 `m.fully_read`。
  - 入力中は ephemeral の `m.typing` で、timeout を持つ。
  - 削除（redaction）は、保持する欄以外を剥がす。
  - push：pusher の登録（app_id、pushkey、format `event_id_only`）、push gateway への `notify`（event_id、room_id、counts{unread, missed_calls}、devices[]）、応答の `rejected[]`（無効な pushkey の削除）。push の規則の種類（override、content、room、sender、underride）と条件。
  - メディア：場所に依存しない識別子（`mxc://{server}/{mediaId}`）、認証付きのダウンロードとサムネイル（width、height、method crop|scale、animated）、`/config` による上限の公開（`m.upload.size`）、非同期のアップロード（識別子を先に発行し、後から中身を置く）、サムネイルの推奨の大きさ（32×32、96×96、320×240、640×480、800×600）。
  - URL のプレビュー：サーバーが OpenGraph 風に `og:title`、`og:description`、`og:image` と大きさを返す。端から端の暗号化のルームではクライアントの設定で選ぶ。
  - 同期：`/sync` のロングポーリング（since、timeout、filter）と、ウィンドウ、必要な状態、timeline_limit を持つ簡略化した同期（2026年6月に提案が受理）。家族の規模では単一のロングポールまたは WebSocket で足りる。
  - 端末：ユーザーと端末を分け、ログインのたびに device_id を払い出し、アクセストークンは端末に紐づく。refresh token と soft logout。端末の一覧、名前の変更、削除（再認証を要する）。
- XMPP の拡張から次の概念を再利用する。［S2］
  - サーバー側のアーカイブの照会（with、start、end、before-id、after-id）と、サーバーが付ける安定した識別子（XEP-0313、XEP-0359）。
  - 自分の他の端末への送受信のコピー（XEP-0280）。
  - ファイルのアップロードの「スロットの先行発行」（ファイル名、大きさ、種類を申告し、PUT の URL と GET の URL の対を得る。XEP-0363）。
  - 権限の2層（永続の affiliation：owner、admin、member、outcast。セッションの role：moderator、participant、visitor。XEP-0045）。
- IETF の MIMI の内容の形式の草案から、編集 `replaces`、返信 `inReplyTo`、スレッド `topicId`、期限 `expires` の4つの欄の名前を揃える。［S3］

## 調査 H：安全と運用の標準（2026-10-13）

基本設計 第1章「全体構成」、第3章「認証、構成員、端末」、第11章「設置と運用」、第12章「データと暗号化」が準拠する、安全と運用の標準の版と要点。2026年10月13日に一次資料で確かめた。

### 1. 確認した事実（出典つき）

#### 1.1 アプリケーションの安全の検証（OWASP ASVS 5.0.0）

- 版：5.0.0（2025年5月。公開リポジトリのリリースは 2025年5月30日）。章は V1 エンコードとサニタイズ、V2 検証と業務ロジック、V3 ウェブのフロントエンド、V4 API と Web サービス（4.4 に WebSocket）、V5 ファイルの扱い、V6 認証、V7 セッション、V8 認可、V9 自己完結のトークン、V10 OAuth と OIDC、V11 暗号、V12 安全な通信、V13 設定、V14 データの保護、V15 安全なコーディングと構成、V16 ログとエラー、V17 WebRTC。約 350 の要件。［H1］
- 水準：L1 は最小（約 20%）、L2 は「ほとんどのアプリケーションが目指すべき水準」（L1 と合わせて約 70%）、L3 は最高。どの水準にすべきかは規定しない。V6 の本文は「L2 のアプリケーションは多要素認証を強制しなければならない」と述べる。［H1］
- 設計に関わる要件：6.2.1 パスワードは 8 文字以上（15 文字を強く推奨）、6.2.9 64 文字以上を許容、6.2.12 漏洩したパスワードとの照合、7.1.1 無操作と絶対のセッションの寿命を文書化し NIST SP 800-63B からの逸脱の理由を記す、7.2.4 認証の時に新しいセッションのトークンを発行、7.3.1〜7.3.2 無操作と絶対のタイムアウト、7.5.1 認証の手段の変更の前に完全な再認証、4.4.1 WebSocket は TLS、4.4.2 ハンドシェイクで Origin を許可リストと照合、4.4.4 既存の HTTPS のセッションから WebSocket 専用のトークンを取得して検証。

#### 1.2 OWASP Top 10:2025、API Security Top 10 2023、Cheat Sheets

- Top 10:2025（最終版。正確な公開日は未確認）：A01 アクセス制御の不備（SSRF を統合）、A02 設定の不備、A03 ソフトウェアのサプライチェーンの失敗（新）、A04 暗号の失敗、A05 インジェクション、A06 安全でない設計、A07 認証の失敗、A08 ソフトウェアとデータの完全性の失敗、A09 ログと警報の失敗、A10 例外の条件の誤った扱い（新）。［H2］
- API Security Top 10 2023：API1 オブジェクト単位の認可の不備、API3 プロパティ単位の認可の不備、API4 資源の消費の制限なし、API7 SSRF など。［H3］
- Cheat Sheets（随時更新。2026年10月13日取得）：
  - Password Storage：Argon2id の推奨は m=47104（46MiB）t=1 p=1、または m=19456（19MiB）t=2 p=1（最小の推奨）。pepper はハッシュと分けて保管。
  - Session Management：セッション識別子は 64 ビット以上（128 ビットを推奨）、Cookie は Secure、HttpOnly、SameSite、`__Host-`、認証と権限の変更で識別子を再生成、タイムアウトは無操作 15〜30 分、絶対 4〜8 時間をサーバー側で強制、ログにはセッション識別子のハッシュのみ。

  - Secrets Management：Docker の ENV と ARG に秘密を書かない、環境変数は全プロセスから読めログに出得る、ファイルのマウントで注入、ローテーション、監査、ログでマスク。

  - Logging：記録する対象（入力の検証の失敗、認証の成否、認可の失敗、セッションの異常、起動と停止と設定の変更、利用者の管理と権限の変更とファイルのアップロード）、記録してはならないもの（パスワード、セッションの識別子、アクセストークン、鍵、口座、DB の接続文字列、機微な個人情報）、改行の除去によるログの注入の防止、保持は法令に従い期限で破棄。
  - WebSocket Security：TLS、permessage-deflate は原則無効、すべてのハンドシェイクで Origin を許可リストと照合、トークンは URL でなく接続後の最初のメッセージで送る、Cookie なら SameSite、約 30 分ごとの再検証、ログアウトで全接続を切る、メッセージごとの認可、JSON Schema の検証、大きさの上限（目安 64KB）、接続数とレート（目安 100 件/分）、ハートビート、本文とトークンをログに残さない。［H4］

#### 1.3 デジタルの身元（NIST SP 800-63-4）

- 版：最終版 2025年7月（63B の HTML の日付は 2025年8月26日）。4 分冊（本体、A 身元の確認、B 認証、C フェデレーション）。［H5］
- パスワード：単要素では 15 文字以上、多要素と併用なら 8 文字以上、64 文字以上を許容、構成の規則を課さない、ブロックリストと照合、定期の変更を強いない。
- 同期できる認証器（パスキー）：AAL1 と AAL2 で使える。AAL3 では使えない。WebAuthn はフィッシングに耐える暗号の認証として AAL2 に適う。
- セッションと再認証：AAL2 は全体 24 時間以内、無操作 1 時間以内（SHOULD）。AAL1 は全体 30 日以内。回復は保存型または発行型の回復のコード、代わりの認証器。

#### 1.4 コンテナの安全（CIS Docker Benchmark v1.9.0、Docker の公式文書）

- CIS Docker Benchmark の最新は v1.9.0（公開日は未確認。入手に登録が要る）。［H6］
- Docker の既定の capability は 14 個（AUDIT_WRITE、CHOWN、DAC_OVERRIDE、FOWNER、FSETID、KILL、MKNOD、NET_BIND_SERVICE、NET_RAW、SETFCAP、SETGID、SETPCAP、SETUID、SYS_CHROOT）。SYS_TIME は含まれず、コンテナは時計を変えられない（ホストの時計に依存する）。`--read-only`、`--security-opt no-new-privileges`、`--cap-drop`、`--tmpfs`、`--user`、`--pids-limit`、`--memory`。HEALTHCHECK の既定は interval 30 秒、timeout 30 秒、start-period 0 秒、start-interval 5 秒、retries 3。終了コード 0 が健全、1 が不健全。［H7］
- Compose の `secrets` は `/run/secrets/<名前>` に読み取り専用のファイルとして置かれ、環境に露出しない。`read_only`、`security_opt`、`cap_drop`、`user`、`healthcheck`、`tmpfs` を Compose で指定できる。［H8］
- rootless の制限：uidmap と subuid/subgid（65,536 以上）、overlay2 はカーネル 5.11 以上、cgroup v2、1024 未満のポートは `setcap cap_net_bind_service` が要る。［H7］
- OCI のイメージの注釈：`org.opencontainers.image.created`、`.source`、`.version`、`.revision`、`.licenses`（SPDX）、`.base.digest`。［H9］

#### 1.5 バックアップ（3-2-1、restic と borg、PostgreSQL）

- 3-2-1 の出典：US-CERT「Data Backup Options」（2012年10月1日）：「重要なファイルのコピーを 3 つ（1 つの正本と 2 つのバックアップ）」「2 種類の媒体」「1 つは別の場所」。［H10］
- restic：`forget` の `--keep-daily` 等は OR で評価（いずれかに該当すれば保持）。`forget` の後に `prune`。暗号化は AES-256-CTR と Poly1305-AES、鍵の導出は scrypt、複数のパスワードを持てる。脅威モデルではバックアップの元の機械は信頼し、保存先の管理者による削除は防げない。［H11］
- borg 1.4.5：`prune` の規則は秒から年の順に適用し、前の規則で選ばれたものは後の規則の数に数えない（restic と異なる）。`repokey` を強いパスフレーズで使い、鍵は保存先と元の機械の外にバックアップる（`borg key export`。紙に印刷も可）。［H12］
- PostgreSQL 18：`pg_dump` は同時に使われていても一貫した書き出しをし、他の利用者を止めない。形式は plain、custom（`-Fc`）、directory（`-Fd`。並列）、tar。PITR は `wal_level=replica`、`archive_mode=on`、`archive_command`、`pg_basebackup`、`restore_command` と `recovery_target_time`。17 以降は増分のバックアップ。［H13］

- JSON Lines：UTF-8（BOM なし）、1 行 1 件、`\n` 区切り、拡張子 `.jsonl`。MIME は未標準。［H14］

#### 1.8 構成の文書と品質の特性

- arc42：最新のテンプレートは 2026.10.2（2026年10月2日）。12 の節。［H19］
- C4 model：Software System、Container、Component、Code の 4 段と対応する図。版番号はない。［H20］

#### 1.9 時刻

- RFC 3339（2002年7月）：`date-time`、`Z` または `±HH:MM`、小数秒。［H22］
- 端末とサーバーの時計のずれの許容に標準はない。RFC 7519 §4.1.4 は「数分を超えない小さな猶予」、RFC 9110 §6.6.1 は「適度な間隔を超える未来の日付は疑わしいとして扱う」。［H23］
- NTP は RFC 5905（2010年6月）。コンテナは SYS_TIME を持たず時計を変えられないため、Ubuntu のホスト側（systemd-timesyncd または chrony）で同期する。［H24］
- IANA の tz データベースの最新は 2026e（2026年9月29日）。［H25］

#### 1.10 レート制限とエラーの形

- RFC 6585（2012年4月）：429 Too Many Requests。条件の説明を含めるべきで、Retry-After を含めてよく、キャッシュしてはならない。［H26］
- draft-ietf-httpapi-ratelimit-headers-11（2026年5月23日。RFC になっていない）：`RateLimit-Policy` と `RateLimit` のヘッダ（RFC 9651 の構造化フィールド）。［H27］
- RFC 9457（2023年7月。RFC 7807 を置き換え）：`application/problem+json`、`type`（既定 `about:blank`）、`status`、`title`、`detail`、`instance`、拡張のメンバー（未知は無視）。［H28］

#### 1.11 WebSocket と常時の接続

- RFC 6455（2011年12月）§10.2：Origin ヘッダはブラウザのスクリプトによる無断の cross-origin の利用からサーバーを守るためのもの。§4.2.2：サーバーは Origin を受け入れの判断に使ってよく、拒むなら 403 等。§10.5：WebSocket 自体は認証の仕組みを定めず、HTTP の認証、TLS、Cookie 等に委ねる。［H29］
- Cross-Site WebSocket Hijacking：ハンドシェイクが Cookie だけに依存し、予測できないトークンがない場合、攻撃者のサイトから被害者のセッションで WebSocket を張り双方向に操作できる。対策は Origin の許可リスト、Cookie 以外のトークン（ASVS 4.4.4）、SameSite。［H30］
- RFC 6202（2011年4月。参考）：ロングポーリングと HTTP のストリーミングの問題と推奨（タイムアウト 30〜120 秒、接続数の制限）。電池への言及はない。［H31］
- WHATWG の Server-Sent Events：`retry`、`Last-Event-ID` による再開、モバイルでは push のプロキシに接続を委ねる「connectionless push」の想定。［H32］
- Android の公式の指針：Doze 中はネットワークが止まる。FCM は共有の持続する TCP の接続であり、各アプリが自分の持続する接続を保つ必要をなくし電池を大きく節約する。15 秒ごとの要求でも無線を常時オンにして電池を急速に消耗する。時刻に敏感な通知は高い優先度の push を使う。［H33］
- SSE、WebSocket、ロングポーリングの電池への影響を直接に比べた権威ある文書はない（未確認）。設計の根拠は「前面の間は WebSocket 1 本、背面では OS の push に委ね、自前の持続する接続を背面で保たない（Android の常時接続は例外として specialUse で保つ。調査 I-02）」という Android の指針になる。

### 2. 設計への帰結（第1章、第3章、第11章、第12章へ）

- 本システムは OWASP ASVS 5.0.0 の L2 を設計の目標とする（個人のメッセージを扱う。「ほとんどのアプリケーションが目指すべき水準」）。L2 が求める多要素認証は、パスキー（所持と生体または PIN）で満たす。
- 認証とセッションは NIST SP 800-63B-4 の AAL2 を基準とし、全体 24 時間・無操作 1 時間の再認証の値を既定とせず、家族の利用（高齢者が長期間ログインし直さずに使う。設計計画書 D-11-3）のために長い寿命（絶対 90 日、無操作 30 日。初期値）を置き、ASVS 7.1.1 に従って逸脱の理由を第3章に文書化する。パスワードを補助で使う場合は 15 文字以上、構成の規則なし、ブロックリスト、Argon2id（m=19456 t=2 p=1 以上）。
- WebSocket は TLS、Origin の許可リスト、接続後の最初のメッセージでセッションから得た専用のトークンを送る、メッセージごとの認可、大きさとレートの上限、ログアウトで切断（ASVS 4.4.x、Cheat Sheet）。
- コンテナは CIS Docker Benchmark と Cheat Sheet の規則（非 root の固定 UID、cap-drop all、no-new-privileges、read-only と tmpfs、公開ポートの限定、secrets はファイル、イメージの固定の digest、スキャン、SBOM）に従う。SFU だけは host のネットワークとし、理由を書く。
- バックアップは 3-2-1（US-CERT）を手順書で勧め、形式は restic または borg（暗号化、保持の規則の意味の違いに注意）、DB は `pg_dump -Fc`（オンラインで一貫）。PITR は家族の規模では採らない（日次で足りる。将来の課題）。
- ログは JSON Lines、OWASP の「記録してはならないもの」を守る。保持の日数は自前で決めて文書化する（初期値 7 日・100MB × 7）。
- エラーは RFC 9457。レート制限は 429 と Retry-After、ヘッダは draft-ietf-httpapi-ratelimit-headers に「ドラフト準拠」と注記して採る。
- 脅威は STRIDE と LINDDUN で要素ごとに当て、Threat Modeling Manifesto の 4 つの問いで章ごとに見直す。
- 時刻はホストの NTP、サーバーが付ける。端末とのずれは 5 分（初期値。RFC 7519 の「数分」に倣う）を超えたら知らせる。

## 準拠の調査 1：自分で立てる同種のサーバーの慣行（2026-10-13）

NRSD の指示（2026-10-13）により、設置、初回、構成員の管理、設定、バックアップ、更新、運用、メディア、通知、通話の各領域について、自分で立てる同種のサーバー（オープンソースで広く使われているメッセージング、会話、会議のサーバー 9 種。製品名は記さない）の公式文書を調べた。以下は、大半が採っている慣行（本システムが準拠するもの）と、割れている点（本システムが選ぶもの）である。

### 1. 設置

- 準拠する慣行：
  - Compose の構成は「アプリ + DB（+ キャッシュ）」の最小を公式が提供し、リバースプロキシは別のファイルか外部。
  - `env.example` を `.env` に写して編集する。`.env` に置くのは、ドメイン、イメージのタグ、DB のパスワード、ポート、タイムゾーン、再起動の方針。
  - 秘密の値（署名の鍵、共有の秘密、TURN の秘密）は、初回の起動または専用のサブコマンドで自動で生成してファイルに書き出す。利用者に手で入れさせるのは DB のパスワードと最初の管理者だけ。`*_FILE` で Docker secrets を受け付ける。
  - アプリは非特権のポート1つで待ち受け、メディア系の UDP（通話、TURN）はプロキシを通さず直接公開する。
  - ヘルスチェックはイメージの `HEALTHCHECK` に置く。
  - 非 root の固定の UID で動かし、バインドのマウントには `chown` を手順に含める。
  - 機械の要件は「最低の RAM + 推奨 + 人数別の表」で書く。SQLite を本番で禁じ PostgreSQL を指定する。
- 割れている点と本システムの選択：
  - 設定の置き場は、(a) 設定ファイルが正、(b) DB と管理 UI が正で環境変数は初期値と上書き、(c) 環境変数が正で起動時にテンプレートから生成、の3系統。本システムは (b) に寄せ、「設定ファイル（YAML）が正、`APP_*` の環境変数で上書き、UI で変えた値は DB、環境変数とファイル由来の項目は UI でロック表示」とする（技術者でない管理者が UI で扱えること、設定ファイルの差分でバックアップと再現ができることの両立）。
  - TLS をアプリ自身で終端するものは例外（内蔵の nginx、内蔵の ACME）。本システムは Caddy を同梱し、外部のプロキシも選べるものとする。

### 2. 初回とブートストラップ

- 準拠する慣行：Web のウィザードまたは「最初のアカウントが管理者」と、CLI と環境変数による非対話の作成の二系統を必ず用意する。ウィザードが尋ねるのは最小で「サーバーの名前、管理者の ID、パスワード、メール」。「1回限り・期限付き（7日）のリンク」で初期の管理者を作る方式が、公開の登録を避けつつ Web で完結させる定石。サーバーの名前（ドメイン）は後から変えられないと明記する。
- 本システムの選択：初回の起動の記録（ログ）と CLI が「1回限り・7日有効の管理者の作成のリンク」を発行し、管理者はそのリンクを開いて自分のアカウントを作る。メールは尋ねない（D-11-2）。`app admin create` に当たる CLI も置く。

### 3. 構成員の管理

- 準拠する慣行：
  - 既定は招待制またはクローズ。公開の登録は明示のフラグと警告。
  - 招待の属性は「有効期限 × 使用回数 × 付与する役割 × 誰が作れるか」。期限の選択肢は 1/7/15/30日/無期限 または 1/3/10/30日/無期限/任意、使用回数は 1 回から無制限。
  - 役割は4〜5段（owner または admin、moderator、member、guest）で、サーバーの管理者のフラグと会話ごとの権限の二層。
  - 無効化（可逆、データを保持、全セッションを失効）が主で、削除は例外。
  - 端末とセッションの一覧と遠隔のログアウトは全プロジェクトが提供する。パスワードの変更で全セッションを失効させるのが既定。
  - メール無しの管理者によるパスワードの再設定は、全プロジェクトが CLI か API で可能。
  - ログインの失敗の制限（例：5回/30分）。
- 割れている点と本システムの選択：削除した構成員のメッセージの扱い（残す／消す）が割れており、設定で選ばせるのは1つだけ。本システムは「残す」を既定とし（家族の記録であるため）、管理者が削除の時に「本人の送信した本文と添付も消す」を選べるものとする（第11.5節の「設計書で定める」の答え）。
- 本システムに固有：家族は招待により閉じているので、役割は管理者と構成員の2段を基本とし（D-11-7）、会話ごとの権限（グループの作成者の権限）を別に持つ。guest は設けない。

### 4. 設定の一覧と既定値

- 準拠する慣行：アップロードの上限の既定は 50〜100MB（軽量な実装は 20〜24MiB）。画像の画素数の上限（32M〜90M 画素）で画像爆弾を防ぐ。メッセージとメディアの保持は既定で永久、保持のポリシーは opt-in。URL のプレビューは既定で無効か、プロキシ経由で、有効にする時は内部の IP の範囲を拒む。レート制限は「ログイン」「登録」「送信」「API」の4種。TURN は URI と共有の秘密と TTL（1〜24時間）の組。
- 本システムの選択：アップロードの上限は、一般的な通信アプリの標準の数値（調査 B）を下回らない範囲で基本設計で定める（D-8-1）。保持は永久を既定とし、管理者が上限と消す規則を設定する（D-8-6）。URL のプレビューは家族のサーバーで取得し、内部の IP の範囲を拒む。

### 5. バックアップと復元

- 準拠する慣行：対象の4点は、DB のダンプ、メディア、設定（と秘密）、署名の鍵と証明書。道具は `pg_dump -Fc`、rsync。DB のダンプはオンラインで取れる（止めずに取れると明記するものと、ファイルと DB の不整合を理由に停止かメンテナンスモードを求めるものがある）。戻すのは空の新しい DB へ、同じ版へ。「更新の前に必ずバックアップを取る」を全プロジェクトが明記。日次の自動のバックアップを内蔵するものは2つ。
- 本システムの選択：`app backup` が「`pg_dump -Fc` + メディア + 設定 + 秘密の鍵」を1つのアーカイブにする。日次の自動のバックアップを内蔵し（D-14-4）、置き場（同じ機械の別のディスク、USB の HDD、クラウド）は管理者が選ぶ。メディアと DB の不整合を避けるため、バックアップの間はメディアの書き込みを短時間止める方式を基本設計で定める。復元は空の DB へ、同じ版へ。

### 6. 更新

- 準拠する慣行：DB のマイグレーションは起動時に自動。ダウングレードは原則非対応（例外的に、戻せる下限の表、1つ前のメジャーまで、マイナーのみ）。メジャーは順番に上げる。イメージのタグは固定し、`latest` を避ける。クライアントの互換は「期間」で宣言する（例：サーバーは過去12か月のクライアントを、クライアントは過去18か月のサーバーを支える）。更新の直前にバックアップ、直後に版のエンドポイントで確認。サポート終了の後にアプリがログインを拒むものがある。
- 本システムの選択：起動時の自動のマイグレーション、固定のタグ、ダウングレード非対応の明記、`/version` のエンドポイント。クライアントの互換の期間は基本設計で定める。ホーム画面のウェブアプリは家族のサーバーの更新で自動的に新しくなり、Android のアプリは版の情報を家族のサーバーから受けて自己更新する（調査 I-03）。

### 7. 運用

- 準拠する慣行：ログは標準出力が一次（JSON を選べる）、既定は INFO。無認証の `/health` 系で依存するサービスまで検査する。`/metrics` は opt-in で既定無効、localhost か専用ポートに限る。ディスクの容量や証明書の期限の管理者への通知は、どのチャットのサーバーも内蔵していない（設定の警告の画面と例外のメールが最も近い）。
- 本システムの選択：慣行に従いつつ、「管理者が対処すべき事柄を知らせる」（D-14-6）は本システムが内蔵する（容量、証明書の期限、バックアップの失敗、更新の有無を、管理者のトーク（システムからの通知）に流す）。これは慣行を超える点であり、設計の根拠は D-14-6 と利用者の実像（管理者が1人）である。

### 8. メディア

- 準拠する慣行：EXIF の除去と自動の回転。サーバー側で固定の大きさの群のサムネイルを作る（例：32×32、96×96、320×240、640×480、800×600、または 840×560 の WebP）。HEIC はライブラリの依存で既定無効か新しめの機能。HEVC の動画の変換はどのサーバーも行わない（「変換しない」と明記するものがある）。アンチウイルスは外付け。メディアのアクセスは閲覧の権限に連動し、署名付きまたは認証付きの URL。
- 本システムの選択：HEIC と HEVC の変換を行う（D-8-2）。これは慣行を超える点であり、根拠は構成員の端末が iPhone と Android で混在すること（利用者の実像）と調査 I-08 である。サムネイルの大きさの群、認証付きの URL は慣行に従う。

### 9. 通知

- 準拠する慣行：FCM と APNs の鍵はストアで配布するアプリの発行者が持ち、発行者の中継を経由する（全プロジェクト）。発行者の経路には登録、規約への同意、無料の枠が伴う。自分で立てる側の代わりは、自分で組んだアプリと鍵と中継、または UnifiedPush。本文を第三者に送らない形式（識別子のみ、端末の鍵で暗号化）が標準になりつつある。
- 本システムの選択：UnifiedPush と Web Push の送信路（調査 I-02）。本文を送らない形式を既定とする（D-10-3 の「本文を示さない設定」とは別に、中継には常に本文を送らない）。

### 10. 通話

- 準拠する慣行：coturn と TURN REST API（共有の秘密と TTL）。3478、5349、49152〜65535/udp、443 の TURNS。少人数は P2P と TURN、それ以上は SFU。
- 本システムの選択：SFU の内蔵の TURN（調査 I-07）。

### 11. 出典

- 各プロジェクトの公式の設置の文書、設定のリファレンス、管理の API の文書、バックアップと更新の文書（2026年10月13日に取得。製品名と URL は記さない。名前つきの記録は NRSD の内部の調査の記録にある）。
- coturn, turnserver.conf. https://github.com/coturn/coturn/blob/master/examples/etc/turnserver.conf

## 準拠の調査 2：一般的な通信アプリの標準の機能と数値（2026-10-13）

設計計画書 D-2-4「一般的な通信アプリの標準の機能を最低要件とする」、D-7-3 および D-8-1「数値は標準の機能の数値を下回らない範囲で定める」の根拠である。国内で最も広く使われている一般的な通信アプリ1つを主な対象とし、その公式の案内（ヘルプ、ガイド、運営会社の発表）で確かめた値を「公式」、第三者の解説にしか見当たらない値を「第三者」とする。製品名、運営会社名および URL は記さない（名前つきの記録は NRSD の内部の調査の記録にある）。2026年10月13日時点。有料の会員に限られる機能も含めて最低要件とする（設計計画書 第2.2節）。

### 1. トークとメッセージ

|機能|標準の数値・振る舞い|根拠|
|---|---|---|
|テキストの最大の長さ|1件 10,000 文字|第三者|
|スタンプ|静止画、動きのあるもの、音の付くもの、画面全体の演出、文字を差し替えられるもの。最大6個を組み合わせて1件で送れる|第三者|
|メンション|グループで `@` により相手を指定。全員を指定する `@All`|公式|

### 8. 設計への帰結（第7章〜第12章 へ）

- 本システムの上限と期限は、次を下回らない：テキスト 10,000文字、1回の送信 50件、動画 5分（ファイルとしては無制限）、ファイル 1GB、ボイス 30分、アルバム 100個・1,000件、投票の選択肢 10・締切 30日、ノートの添付 20、アナウンス 5件、送信の取消 7日（有料の会員の値を最低要件とする）、編集 15分（同）、呼び出し 60秒。
- 一般的な通信アプリの保存の期間（2週間前後、7日）は、本システムでは「容量が続く限り」（D-8-6）で上回る。
- グループの最大人数（500人）は、家族の規模（20人）を大きく超えるため、本システムの上限は家族の人数（インスタンスの人数）とする（第7.1節）。
- 既読で「誰が読んだか」を示さないのが標準であるが、本システムは第7.5節のとおり基本設計で定める（家族の中では知りたい場面が多い）。
- 入力中の表示は国内の標準にはない（O-10 の判断の材料）。
- 通話の着信は、iPhone では OS の電話の着信画面との統合が標準であるが、本システムは実現できない（D-5-2）。Android の全画面の着信は標準どおり（D-9-2）。
- 複数の端末は「主の端末1台と副3台、iPhone は副にできない」が標準であるが、本システムはサーバーに全記録を置くため、端末の種類と台数の制限を設けない（D-11-5）。これは慣行を超える点である。
- 登録に電話番号と SMS を要するのが標準であるが、本システムは招待制のため要しない（D-11-2）。
- 設定の分類（通知、トーク、写真と動画、プライバシー、データの削除、着せ替え）、文字の大きさの4段階、アニメーションの停止、トークごとの背景、トークごと・期間ごとのデータの削除は、標準に合わせて備える（第12.5節）。
- 通知の「内容を表示しない」「トークごとの通知オフでもメンションは届く」「一時停止（1時間 / 翌朝まで）」は、標準に合わせて備える（D-10-3）。

## 準拠の調査 3：一般的な通信アプリの導入、人の追加、端末、設定、安全、操作の慣行（2026-10-13）

NRSD の指示（2026-10-13）により、国内外で広く使われている一般的な通信アプリ 8 種（製品名は記さない）の公式のヘルプ、ガイド、公開の仕様を調べ、大半が採っている慣行と、割れている点をまとめた。本システムが準拠するもの、および本システムが慣行と異なる選択をする点（根拠つき）を各節の末尾に示す。「未確認」は公式の文書で確かめられなかったもの。

### 1. 導入（登録）

- 慣行：
  - 識別子は電話番号（SMS または音声通話で6桁のコードを確かめる）が事実上の標準。ユーザー名は任意の補助の識別子として加える流れがある。アカウント ID 型（メールアドレスなど）は2つ。
  - 画面の順は、利用規約への同意 → 電話番号 → コード → バックアップからの復元または旧端末からの移行 → 名前（必須。1つの欄で短く、25文字または20文字程度。写真は任意）→ 任意のユーザー名 → 安全の設定（PIN、パスキー）の提案。
  - 権限は使う瞬間に求める（カメラとマイクは初回の通話、連絡先は友だちの検索の時）。通知の許可だけは早く（規約の直後に）求めるものがある。権限の正確な順序は公式の文書に列挙がなく未確認。
- 本システムの選択：
  - 電話番号も SMS も使わない（D-11-2。家族は招待で閉じ、外部に連絡先を確かめる手段も必要もない）。招待のリンクまたは QR を開く → 名前（必須、短く）と写真（任意）→ 安全の設定（パスキーの提案）の3画面で完結させる。通知の許可は、最初のトークを開いた時にユーザーの操作を起点に求める（iPhone の Web Push の条件。調査 I-01）。
  - 旧端末からの移行の画面は要らない（記録は家族のサーバーにある。D-11-5）。

### 2. 人の追加

- 慣行：
  - 個人は「自分の QR コード」と共有のリンクを1つの画面に置き、「更新（リセット）」で失効させる。期限は原則ない。
  - グループは「リンクで招待」のトグル（既定は無効のものが多い）、「新しいメンバーの承認」のトグル（既定は無効）、「リンクをリセット」の3つ。期限と使用回数を付けた複数のリンクを持つものが1つ。
  - 「誰が自分をグループに加えられるか」は、全員 / 連絡先のみ / 連絡先の一部を除く、の3択。
  - 知らない人からの連絡は「リクエスト」の箱に隔離し、受諾 / ブロック / 通報 / 削除の3〜4つのボタンを置く。
  - 連絡先の同期は任意のトグルと「同期した連絡先を削除」。
- 本システムの選択：
  - 招待は設計計画書 D-11-1（期限付き、1回限り）。慣行の「期限なし + リセット」ではなく、自分で立てる同種のサーバーの慣行（期限 × 回数 × 役割。準拠の調査1の3）に合わせる。理由は、家族の外の第三者が招待のリンクを手に入れた場合の備え（設計計画書 第3.5節）。招待の画面は、QR とリンクを1つの画面に置き、「無効にする」と「作り直す」を備える点で一般的な通信アプリの慣行に合わせる。
  - 家族は招待で閉じているため、「誰が自分を加えられるか」「リクエストのメールボックス」「連絡先の同期」は要らない（D-7-2）。

### 3. 端末の連携

- 慣行：
  - 「主の端末（スマートフォン）1台 + 連携する端末」の形が主流（5つ）。クラウド型（主の端末なし。どの端末も対等）は2つ。
  - 連携の手順：新しい端末が QR を表示 → 主の端末の「設定 > 連携する端末 > 端末を連携」で生体認証の後に読み取る → 履歴を転送するかを選ぶ。代わりに「電話番号 + 短いコード（6〜8文字）を主の端末で承認」。
  - 上限は4〜5台。無操作での失効は14日、30日、数週間。
  - 「ログイン中の端末」の一覧（端末の名前、最終の利用の時刻、IP アドレス）と、個別の「ログアウト」と「他のすべての端末からログアウト」。新しいログインの通知。
  - 履歴の同期は「直近 N 日」（14日、メディアは45日）または「最近のメッセージ」にとどめ、全履歴はバックアップから戻す。
- 本システムの選択：
  - クラウド型（対等）を採る（D-11-5。記録は家族のサーバーにあり、主の端末を要しない。家族には iPhone 1台だけの構成員がおり、「iPhone は副の端末にできない」という主流の制約を持ち込まない）。これは主流の慣行と異なる点であり、根拠は利用者の実像（設計計画書 第3.3節）と D-11-5 である。
  - 新しい端末の追加の手順は慣行に合わせる：新しい端末が QR を表示し、ログイン済みの端末で読み取って承認する（RFC 8628 のデバイス認可の流れ。準拠する標準規格の5）。加えて、パスキーによるログイン（端末が1台しかない場合）。
  - 「ログイン中の端末」の一覧、個別と全部のログアウト、新しいログインの通知は慣行どおり（D-11-6）。
  - 端から端の暗号化を採る場合（O-01）、履歴の復元に鍵の受け渡しが要る点は調査 I-10 のとおり。

### 4. 設定の分類

- 慣行：
  - 最上位は7〜9項目：アカウント / プライバシー / トーク / 通知 / ストレージとデータ / 外観（テーマ） / 連携する端末 / ヘルプ / 友だちを招待。国内と近隣の製品は「友だち」「写真と動画」「通話」を独立した項目にする。
  - 通知の粒度：全体のトグル → 種別（1対1 / グループ / 通話 / リアクション）→ プレビューの表示（名前と本文 / 名前のみ / なし）→ 音と振動。トークごとのミュートは、8時間 / 1週間 / 常に、または 1時間 / 8時間 / 1日 / 1週間 / 常に + 日時の指定。国内の製品は ON/OFF のみで、全体の一時停止（1時間 / 翌朝8時まで）を持つ。メンションはミュート中でも通知する（止めるトグル付き）。
  - プライバシー：既読の通知のトグル / 入力中の表示 / 最終のオンライン / プロフィールの写真の公開範囲 / ブロックの一覧 / アプリのロック / 「誰が自分を見つけられるか」。公開範囲の値は、全員 / 連絡先 / 連絡先の一部を除く / なし。国内の製品は既読を切れない。
  - トーク：バックアップ（頻度 日次/週次/月次 + 動画を含める + 端から端の暗号化）/ 書き出し（テキスト、メディアの有無）/ 背景 / 文字の大きさ3〜4段 / アーカイブ（ミュート中のトークを自動で）/ ピン留めの上限 / Enter で送信。
  - ストレージ：自動ダウンロードは、モバイル / Wi-Fi / ローミング × 写真 / 音声 / 動画 / 文書の表（既定：モバイルは写真（+音声）、Wi-Fi は全部、ローミングはなし）。メディアの品質は標準 / 高画質。「ストレージの管理」はトークごとの使用量を大きい順に並べ、「5MB 超」「何度も転送されたもの」の絞り込みと、種類ごとの削除。
- 本システムの選択：
  - 最上位の項目を、アカウント / 端末 / 通知 / トーク / 写真と動画 / 通話 / プライバシー / 外観 / データと容量 / ヘルプ とし、国内の製品の慣行（写真と動画、通話を独立）に合わせる。
  - 通知の粒度（種別、プレビューの3択、トークごとのミュートの期間、全体の一時停止、メンションの例外）は慣行どおり（D-10-3）。トークごとのミュートは期間付き（1時間 / 8時間 / 1週間 / 常に）とし、国内の ON/OFF のみより細かい方に合わせる。
  - 既読のトグルは設けない（国内の慣行。家族の中で既読を隠す場面は想定しない）。入力中の表示は O-10。最終のオンライン、プロフィールの公開範囲、「見つけられる人」は、家族が閉じているため要らない。
  - 自動ダウンロードの表（モバイル / Wi-Fi × 写真 / 動画 / ファイル）と、品質の標準 / 高画質、ストレージの管理（トークごとの使用量、種類ごとの削除）は慣行どおり（D-8-7、第12.5節）。
  - バックアップの設定は要らない（家族のサーバーがバックアップを取る。D-14-4）。端末のキャッシュの削除は慣行どおり。

### 5. アカウントの安全

- 慣行：
  - 乗っ取りを防ぐ PIN（6桁）からパスワードまたはパスキーへ移行中。忘れた時は7日の待機が標準。
  - アプリのロックは端末の生体認証を使い、時間切れは 即時 / 1分 / 5〜15分 / 1時間 の4段階。
  - 鍵の検証（端から端の暗号化のある製品）は、QR の読み取りか数字・絵文字の比較 → 「検証済み」の印 → 変更の時に警告。
  - アカウントの削除は、識別子の再入力 + 理由 + 失うものの一覧。
- 本システムの選択：
  - ログインはパスキーを一次とし（WCAG 3.3.8 と WebAuthn Level 3。準拠する標準規格）、回復のコードを備える。PIN と「7日の待機」は、家族のサーバーの管理者が本人を確かめて再設定できるため要らない（準拠の調査1の3：メール無しの管理者による再設定）。
  - アプリのロックの時間切れの4段階は慣行どおり（D-11-4）。
  - 鍵の検証の UI は O-01 の結論による。
  - アカウントの削除は管理者が行う（D-11-7）。本人が自分で消す導線を置くかは基本設計で定める。

### 6. ブロックと通報

- 慣行：
  - ブロックは相手に通知しない。相手の側の手がかりは「配達や既読が付かない」「写真や最終のオンラインが見えない」だけ。
  - 閉じたグループの中では、ブロックしても双方がグループに残り、少なくとも相手は自分の投稿を見られる（自分からは相手を非表示にするものと、両方見えるものがある）。グループ自体はブロックできず、退出 / ミュート / 管理者に削除を頼む。
  - 通報は、理由の区分 → 直近 N 件（5、9、3、30）を送る → 同時にブロックの選択。
- 本システムの選択：
  - 通報の宛先（事業者）がない本システムでは、通報は設けない。ブロック（O-11）は、慣行から「ブロックよりミュートと管理者による対処」が閉じたグループに合うことが分かったため、O-11 の判断の材料とする：構成員ごとのミュート（通知を出さない）と、管理者による構成員の停止（D-11-7）で代える方向。

### 7. メッセージの操作の UI

- 慣行：
  - 長押しで、上段にリアクションの行（6個 + 「+」で全絵文字）、下段に操作の一覧。操作の順はおおむね「返信 → 転送 / コピー → 保存系（スター、ピン）→ 情報 → 編集 → 削除（赤）」。右へのスワイプで返信。
  - 全員からの削除の猶予：24時間（2つ）、2日、1時間（国内。2026年に短縮）、無期限（2つ）。削除の後は「このメッセージは削除されました」の表示が残る。
  - 編集の猶予：15分（5つ）、24時間・10回（1つ）。「編集済み」の表示と履歴。
  - 消えるメッセージの選択肢は、なし / 24時間 / 7日 / 90日（2つ）か細かい段階（1つ）で、「新しいトークの既定のタイマー」を別に持つ。国内と近隣の製品にはない。
  - ボイスメッセージは「長押しで録音 → 上にスワイプで固定 → 左にスワイプで取り消し → 送る前に確認」+ 1x / 1.5x / 2x の再生。
  - ピン留めは3件・期間付き（24時間 / 7日 / 30日）が新しい標準。国内は「アナウンス」（5件）。
- 本システムの選択：
  - 長押しのメニュー（上段のリアクション6 + 全絵文字、下段の順）、右スワイプの返信とその代わりの操作（WCAG 2.5.7）、ボイスメッセージの操作と再生の速度は慣行どおり。
  - 削除（送信の取消）の猶予は7日（国内の有料の会員の値を最低要件とする。準拠の調査2）、編集は15分。
  - 消えるメッセージは設けない（国内の慣行になく、家族の記録を残す本システムの目的に合わない）。
  - アナウンスは5件（国内の慣行。準拠の調査2）とし、期間付きのピン留めは設けない。

### 8. 通話の UI

- 慣行：
  - 着信の画面は OS の通話の仕組みと統合し、「応答 / 拒否（/ 音声だけで応答）」。ロック中はスワイプ。グループ通話は「参加 / 無視」のバックアップめなバナーで、1対1のような着信画面は出さない。
  - 「通話」のタブ：履歴（着信 / 発信 / 不在の絞り込み）+ 新しい通話 + 通話のリンクの作成。リンクは「参加の承認（待機室）」と未使用での失効（30〜90日）。
  - 設定：「通話のデータの使用を抑える」（しない / モバイルのみ / 常に）、「知らない発信者を消音」、「IP アドレスを保護（中継）」、着信音（全体 + 連絡先ごと）。
  - グループ通話の人数は 10〜500。
- 本システムの選択：
  - 着信の画面、「応答 / 拒否 / 音声だけで応答」、グループ通話の「参加 / 無視」のバナーは慣行どおり（第9.2節の「グループの通話を始めた時に構成員をどう呼ぶか」の答え：1対1は着信として鳴らし、グループはバナーと通知で参加を待つ。基本設計で確定）。
  - 通話の一覧（履歴と絞り込み）は慣行どおり（D-9-3）。通話のリンクは、家族の外の人を入れない本システムでは設けない。
  - 「データの使用を抑える」の3択と着信音の選択は慣行どおり（D-9-4、D-9-6）。「知らない発信者」「IP の保護」は、家族が閉じ、通話が常に家族のサーバーを経由する（D-9-5）ため要らない。

### 9. メディアの送信の UI

- 慣行：
  - 画質は「標準 / 高画質」の2択を送信の画面に置き、既定の値を設定に持つ。原寸は「ファイルとして送る」で回避する。
  - 上限は 100MB（2つ）、300MB、2GB（2つ）。動画は圧縮しつつ 64〜100MB が目安。
  - 複数の写真は1つの吹き出しに束ねる（10件、120件を30件ずつ、4件以上で重ねる）。
  - 写真から自作のスタンプは、「被写体の自動の切り抜き → 文字と落書き → パックに保存」が共通の流れ。
- 本システムの選択：
  - 送信の画面の「標準 / 高画質 / オリジナル」（国内の3択。準拠の調査2）と既定の設定は慣行どおり。
  - 複数の写真の束ね（国内の10件ずつ）は慣行どおり。
  - スタンプの作成（D-7-4）は、「被写体の切り抜き → 文字と落書き → パックに保存」の流れに合わせる。被写体の切り抜きは端末の中で行う（第8.3節の文字の抽出と同じく、外部に送らない）。

### 10. ヘルプ、見やすさ、言語

- 慣行：
  - ヘルプは「ヘルプセンター（Web）/ 問い合わせ / バージョン・ライセンス・規約」の3点。初回のヒントは「リクエストの時の安全のヒント」「新機能のお知らせのトーク」。
  - 文字の大きさは 小 / 中 / 大 / 特大 + 「システムの設定に従う」。アニメーションの抑制のトグル。
  - アプリの言語は、Android はアプリの中で、iOS は OS の「アプリごとの言語」に委ねる。
- 本システムの選択：
  - ヘルプは、家族のサーバーの画面の中の手順書（管理者向けと構成員向け）、問い合わせ先は管理者（家族の中）、バージョンとライセンスの表示（Apache License 2.0 の表示の義務と、同梱する部品の表示）。新機能のお知らせは、システムからのトークに流す（準拠の調査1の7と同じ経路）。
  - 文字の大きさの4段階 + システムに従う、アニメーションの抑制は慣行どおり（D-12-3、第12.5節）。
  - 言語は日本語のみ（D-12-6）。iOS の「アプリごとの言語」は、ホーム画面のウェブアプリには適用されない。
