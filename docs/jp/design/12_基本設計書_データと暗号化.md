## 本書の位置付け

- 概要設計書 第12章「データの所在、秘密、暗号化」を詳細化し、設計計画書の未決事項 O-01「端から端の暗号化」を閉じる。本章の結論は、第3章〜第9章と第11章の形を決める（認証、トーク、メディア、通話、通知、シェル、運用）。
- 本章は arc42 の「横断的な概念」のうち、データの所在と保護に当たる。脅威は第1章 11.2 の T-1〜T-18 を受け、対策を本章に置き、残る既知の制約を 16 で宣言する。
- 準拠する規格は次のとおり。出典は調査資料と NRSD の作業記録にある。
  - 暗号：MLS（RFC 9420、RFC 9750）、HPKE（RFC 9180）、HKDF（RFC 5869）、AES-GCM（NIST SP 800-38D）、Argon2（RFC 9106）
  - ウェブ：WebCrypto（W3C）、WebAuthn Level 3（W3C Recommendation 2026-08-25）
  - 鍵の管理：NIST SP 800-63B-4（回復）、NIST SP 800-57 Part 1 Rev.5（鍵の管理）、NIST SP 800-53 Rev.5（AU-9(4)、SC-12(1)）
  - 消去と記憶装置：NIST SP 800-88 Rev.2（消去）、NIST SP 800-111（記憶装置の暗号化）
  - 通信：RFC 8291（Web Push の暗号）、RFC 5763/5764（DTLS-SRTP）、RFC 8446（TLS 1.3）

## 2. 目的と範囲

### 2.1 受ける要件

概要設計書 第12章の R-12-1-1、R-12-2-1、R-12-3-1、R-12-3-2、R-12-4-1、R-12-5-1、R-12-6-1、R-12-7-1。対応は 14。

### 2.2 扱うもの・扱わないもの

- 扱う：データの所在と保護の区分。通信の保護。E2EE の設計（群、スイート、サーバーの責務、端末の鍵、鍵バンドルと回復、履歴、新しい端末、添付、通知、検索、プレビュー、通話）。サーバーと端末の保存の保護。明示と外へ送る情報。消すこと。秘密の鍵とログの秘匿。
- 扱わない：各機能の API と画面（第2〜7章、第10章）、設置とバックアップの手順（第11章）、Android の鍵保管庫の使い方（第9章）、認証の流れ（第3章。本章は鍵の受け渡しだけ）。

## 3. データの所在と保護の区分

- トークの名前とアイコンは MLS の GroupContext の拡張ではなく、本文と同じ暗号文のイベント（種類「トークの設定」）として持つ。一覧の画面は端末のコピーから描く。サーバーは「トーク n」の番号だけを知る。

## 5. 端から端の暗号化の設計

### 5.1 比較の結論（O-01）

第1章 2.3 の目標の順で 3 つの設計を比較した。詳細は NRSD の作業記録にあり、要点は次のとおり。

|目標|送信者鍵の方式|MLS|E2EE なし|
|---|---|---|---|
|1 記録を失わない|端末と紙に依存|端末、家族の端末、紙の 4 段（DD-12-4、DD-12-5）で E2EE なしと同等|サーバーの記録とバックアップの鍵（紙）|
|2 いつでも届く|端末側の通知・検索・プレビュー|同左。SW とシェルの復号、端末の索引、同梱のプレビュー、iOS の写真の選択時の変換で小さな劣化に収まる|サーバーで素直に成立|
|3 外に出さない|受動的な管理者、実行時の侵害からの過去、VPS、SFU の終端に対して守れる|同左|守れない|
|4 迷わない|新しい端末の承認と回復の画面が増える|同左。標準的な通信アプリの「端末の連携」と「バックアップの鍵」の形にする|ログインすれば全部見える|
|6 運用が続く|既製の部品がない|部品は 2 系統（差し替え点を切る）。サーバーは暗号を持たない|部品は標準|

- 目標 1 と 2 は本章の設計で同等まで持っていけ、目標 3 で MLS が勝つ。第1章 DD-1-16 により MLS を採る（DD-12-1）。
- 送信者鍵の方式は退ける。寛容なライセンスを持ちブラウザで動く既製の部品がなく、侵害後の安全性の回復（PCS）もないため。

### 5.2 群の暗号（MLS）

- トークごとに 1 つの MLS グループ。1 対 1 のトークも 2 人のグループ。構成員の端末ごとに 1 つの leaf（1 人 3 端末なら 3 leaf）。
- 暗号スイート 0x0002（DD-12-2）。耐量子のスイート（MLS WG の文書が RFC になった時）への移行は、グループの再作成（新しいスイートで新しいグループを作り、古いグループに「移行した」の本文を残す）で行う。スイートはグループの作成時に固定され変えられないため。
- 部品：ウェブは TypeScript の MLS の実装（MIT）を一次とする。差し替え点（MLS の操作のインターフェース）の後ろに、Rust の実装の WASM（Apache-2.0 OR MIT。WebCrypto の provider）を二次として持つ。両方を公式の相互運用の検証ベクトルで試験する（第14章 13.1、試験設計書）。Android のシェルは MLS を持たない（復号は WebView の中。DD-12-10）。
- グループの識別子（RFC 9420 8.1 の `group_id`）は 20 バイトとする。形は、トークの識別子（UUIDv7）の 16 バイトに、グループの世代（符号なし 32 ビット、ビッグエンディアン。0 から）を続けた物。1 つのトークに同時に 1 つのグループがあり、世代は「拒まれた Commit からの復旧」（下）の再初期化でだけ 1 増える。暗号スイートの移行（上）は新しいトークを作って行う（同じトークの中で任意にグループを作り直す形は採らない）。世代を識別子に含める理由：再初期化の後のグループの epoch と鍵のバックアップ（5.6）と暗号文のイベントを、前の世代の物と番号で区別できるようにする。
- 境界を越える MLS の物（KeyPackage、Commit、Welcome、本文）は、どれも RFC 9420 6 の MLSMessage の TLS 符号化で送る。先頭の 4 バイトは版（`mls10`）と wire format で、サーバーはこの 2 つを読んで物の種類を確かめる。
  - KeyPackage：wire format `mls_key_package`。
  - Commit：wire format `mls_public_message`（PublicMessage。RFC 9420 6.2）。内容の種類は `commit`。
  - Welcome：wire format `mls_welcome`。
  - 本文：wire format `mls_private_message`（PrivateMessage。RFC 9420 6.3）。内容の種類は `application`。
- Commit を PublicMessage で送る理由：RFC 9420 6 は、配送サービスが handshake のメッセージを見る必要がある時に PublicMessage で送ることを許す。RFC 9750 6.4 は、仲介者が Commit の方針を課すにはそれが要るとする。本システムでは、サーバーが Add と Remove を自分で読んで leaf の記録を更新し、端末の申告に頼らない。PublicMessage は署名と membership tag で守られる（RFC 9420 6.2）。暗号化されていないのは Commit の中の公開情報だけである（追加する端末の KeyPackage、外す leaf の番号、UpdatePath の公開鍵と暗号文）。グループの構成はサーバーが構成員の表で既に知っているので、サーバーに新たに見えるものは無い（16 の H-12-16）。
- 家族のサーバー（Go）は MLS の暗号を持たない。持つのは：
  - KeyPackage の保管：端末ごとに使い切りの KeyPackage を 20 個（初期値）と「最後の手段」の 1 個。10 個を下回ると端末が補充する。サーバーの保持の期限は、置いた時から 90 日と、leaf の `not_after` の 1 日前の、早い方。置く時にサーバーは次の 9 つを確かめる（1 つでも通らなければ `KEY-009`）。
    1. 版は `mls10`、スイートは 0x0002。
    2. leaf の `credential` が 5.3 の形でその端末の物。
    3. leaf の `signature_key` がその端末の登録した署名鍵（SEC 1 の非圧縮の形。RFC 9420 5.1.1）。
    4. `leaf_node_source` が `key_package`。
    5. KeyPackage の署名がその署名鍵で通ること（`SignWithLabel` のラベル `KeyPackageTBS`。RFC 9420 5.1.2。ECDSA の署名は DER）。
    6. leaf の署名がその署名鍵で通ること（ラベル `LeafNodeTBS`。`key_package` 由来の leaf は文脈を持たない。RFC 9420 7.2）。
    7. leaf の `encryption_key` と `init_key` が、どちらも P-256 の公開鍵の形であること。形は、SEC 1 の非圧縮の 65 バイトで、曲線の上の点で、無限遠点でないこと。根拠は RFC 9180 7.1.1 の DHKEM(P-256) の公開鍵の形と、同 7.1.4 が受け手に求める公開鍵の確かめ（5.3 の登録の確かめと同じ）。加えて、2 つが互いに違うこと（RFC 9420 10.1）。鍵の形を確かめる理由：受け手の端末は RFC 9180 7.1.4 により形の崩れた公開鍵を拒まねばならず、サーバーが通すと受け手が拒んで復旧の経路に乗る。公開の情報だけで確かめられるので、先に拒む（16 の H-12-19 の範囲を狭める）。
    8. capabilities に版 `mls10`、スイート 0x0002、credential の種類 `basic` があること。leaf の extensions のうち既定でない種類（RFC 9420 7.2 の 5 つ以外）が全部 capabilities の extensions にあること（RFC 9420 7.3）。
    9. leaf の有効期間が「leaf の有効期間」（下）の規則に合うこと。
  - KeyPackageRef（RFC 9420 5.2）はサーバーが求めて主キーにする。
  - Commit の直列化と読み取り：グループごとに世代と epoch を持つ。現在の世代の現在の epoch に対する Commit を 1 つだけ受け付け、それ以外は 409 で拒む（`KEY-007`）。受け付ける前に Commit（PublicMessage）の外側と中身を読む。読むのは `group_id`、`epoch`、送信者の leaf の番号、提案の一覧（Add の KeyPackage、Remove の leaf の番号、Update）。`path` の有無と `path` の leaf も読む。読まない物は、UpdatePath の暗号文、FramedContent の署名、confirmation_tag、membership_tag、parent hash の 5 つ。読むには GroupContext とグループの秘密が要り、受け手の端末が確かめる（16 の H-12-19）。読んだ結果で leaf の記録（下）を更新し、端末の追加待ち・削除待ち・再参加待ち（5.5 と「拒まれた Commit からの復旧」）を解く。受け付けた Commit は他の端末へ配る。
  - Commit の参照（`commit_ref`）：受け付けた Commit の MLSMessage のバイト列の SHA-256 の base64url。`room.mls`、`GET /rooms/{id}/mls/commits`、拒みの報告（下）が同じ値を使い、端末は取った Commit が知らされた物と同じかをこれで確かめる。
  - leaf の記録：グループごとに「どの leaf の番号にどの端末がいるか」と、その leaf の `encryption_key`（分かる時）を持つ。グループの作成で leaf 0 に作成した端末を置く（作成者の `encryption_key` は、作成者の最初の `path` 付きの Commit で埋まる）。Commit を受け付けた時に RFC 9420 の規則で leaf の番号を求める。規則は 3 つ。12.1.1（Add は左端の空いた leaf。無ければ木を右に広げた最初の leaf）。12.1.3（Remove で leaf を空にし、右端の空の部分木を切り詰める）。12.3（Update、Remove、Add の順に適用）。木の幅は、記録にある leaf の最大の番号から求めた 2 のべき乗で、切り詰めの後の幅と一致する。`encryption_key` は、Add の KeyPackage の leaf と、Commit を作った端末の `path` の leaf から更新する。サーバーが読めない提案を含む Commit は `KEY-009` で拒む（提案の参照、PSK、ReInit、ExternalInit、GroupContextExtensions）。
  - Commit の確かめ：次の 9 つを順に確かめ、1 つでも成り立たなければ `KEY-009` で拒み、epoch は進まない。
    1. 送信者の leaf の番号が送信した端末の leaf であること。
    2. Remove の番号が記録にある leaf で、送信者自身でないこと。同じ leaf の Remove が 2 つ無いこと（RFC 9420 12.2）。
    3. 値で含めた Update が無いこと。値で含める提案は Commit を作った端末の物で、自分の Update を含む Commit は不正である（RFC 9420 12.2、12.4）。
    4. Add の KeyPackage が「KeyPackage の保管」の 1〜9 を全部満たすこと。Commit を作る端末はサーバーに置かれていない KeyPackage を入れられるので、受け付けの時にもう一度確かめる。加えて、今の時刻が leaf の有効期間の中（`not_before` の 1 日前から `not_after` まで）であること。RFC 9420 7.3 が Commit を作る端末に求める確かめを、サーバーも行う。
    5. Add の KeyPackage の credential の端末が、承認済みか休眠で、そのトークの構成員（追加待ちを含む）の物で、Remove を当てた後の記録に leaf を持たないこと。Add の中で端末が重ならないこと。
    6. Add の KeyPackage の leaf の `encryption_key` が、他と違うこと（RFC 9420 7.3）。比べる相手は、Remove を当てた後の記録の `encryption_key` の全部と、他の Add の物。
    7. `path` の要否：提案が空か、Remove を含めば `path` が要る（RFC 9420 12.4）。無ければ拒む。
    8. `path` があれば、その leaf について次を確かめる。`credential` と `signature_key` が Commit を作った端末の登録と同じ。`leaf_node_source` が `commit`。capabilities と extensions が「KeyPackage の保管」の 8 を満たす。leaf の署名が、`group_id` と送信者の leaf の番号を文脈として通る（RFC 9420 7.2）。`encryption_key` が P-256 の公開鍵の形（「KeyPackage の保管」の 7）であること。同じ `encryption_key` が、送信者の今の記録の値と違い、記録の他のどの値とも、Add の物とも違う（RFC 9420 12.4.2、7.3）。
    9. Add があれば Welcome があり、Welcome のスイートが 0x0002 であること。`secrets[]` の `new_member` の集合が、Add の KeyPackage の KeyPackageRef の集合と同じこと（RFC 9420 12.4.3.1）。`secrets[]` の各 `kem_output` が P-256 の公開鍵の形（「KeyPackage の保管」の 7）であること。HPKE の KEM の出力は送り手の一時の公開鍵で、受け手が形を確かめる（RFC 9180 7.1.1、7.1.4）。Add が無ければ Welcome が無いこと。
  - Welcome の中継：GroupInfo は Welcome の中にある（RFC 9420 12.4.3.1 の `encrypted_group_info`）。サーバーは Commit の Add で加わった各端末の端末宛メールボックス（to-device）に、同じ Welcome を置く。端末は Welcome の GroupInfo に含まれる ratchet tree（拡張 `ratchet_tree`）を使う。サーバーは木を持たないので、Commit を作る端末は Welcome に `ratchet_tree` の拡張を必ず入れる。
  - 暗号文の保管と順序：MLS の PrivateMessage をイベントとして記録し（第1章 DD-1-6）、順序と時刻を付ける。
  - 外形の検査：本文（PrivateMessage）の外側（RFC 9420 6.3 の `group_id`、`epoch`、`content_type`）と MLSMessage の先頭だけを読む。確かめるのは 4 つ。(1) wire format が `mls_private_message` で `content_type` が `application`。(2) 外側の `group_id` と `ft.event.mls/1` の `group_id` が同じで、このトークのグループの識別子（20 バイト。違えば `ROOM-005`）。(3) その識別子の世代と、外側の `epoch` と `ft.event.mls/1` の `epoch` が、現在の世代と epoch（古ければ `ROOM-006`）。(4) 送信した端末（セッションの端末）がそのグループの leaf の記録にある（無ければ `ROOM-006`）。送信者の leaf の番号は暗号化された SenderData の中にあり、サーバーは読めない。暗号文の送信者と送信した端末の一致は、受け手の端末が MLS の署名で確かめる（違えば表示しない）。本文は読めない。
- leaf の有効期間（RFC 9420 7.2 の lifetime。DD-12-18）：
  - 端末は KeyPackage の leaf に `not_before` を今の 1 日前、`not_after` を今の 100 日後として置く。
  - 有効期間の全長の上限は 120 日とする（RFC 9420 7.2 が応用に定めを求める上限）。全長が 120 日を超える leaf は、サーバーと受け手の端末が拒む。サーバーは KeyPackage の保管と Commit の Add で拒む。受け手の端末は Commit の Add の leaf と、Welcome の `ratchet_tree` の `key_package` 由来の leaf で拒む。
  - サーバーは置く時に、`not_before` が今の 1 日後より前で、`not_after` が今の 7 日後より後であることも確かめる（時計のずれの余裕。外れれば `KEY-009`）。
  - KeyPackage を Add に使う端末は、使う前に今の時刻が有効期間の中であることを確かめる（RFC 9420 7.3 の MUST）。外れていれば捨てて取り直す。
  - 受け手の端末は、受け取った leaf について今の時刻の確かめをしない。RFC 9420 7.3 はこれを RECOMMENDED に留める。Commit を作らない構成員の leaf は `key_package` 由来のまま木に残り、期限を過ぎた leaf を受け手が拒むと、新しい端末が Welcome を処理できなくなる。二次の実装の受信時の有効期間の確かめは切る。
- 拒まれた Commit からの復旧（RFC 9420 16.12、RFC 9750 5.3。DD-12-17）：受け手の端末は、サーバーの確かめを通った Commit も拒むことがある。サーバーの読めない部分が壊れている時で、RFC 9420 12.4.2 による。読めない部分は FramedContent の署名、confirmation_tag、membership_tag、UpdatePath の暗号文、parent hash の 5 つ。その端末はサーバーより古い epoch に取り残され、自分では Commit を作れない（`KEY-007`）。復旧は 2 段で、どちらも利用者の操作を要しない。
  1. 端末の再参加：Commit（または Welcome）を処理できなかった端末は、まず自分が取りこぼした Commit を全部取り込み直す。使うのは `GET /rooms/{id}/mls/epoch` と `GET /rooms/{id}/mls/commits`。それでも処理できなければ、`POST /rooms/{id}/mls/reject`（世代、epoch、`commit_ref`、理由）で報告する。そのグループの現在の状態は捨てる（過去の epoch の受信専用の状態と鍵のバックアップは残す）。サーバーは報告を記録し、その端末を「再参加待ち」にする（`mls_pending` の種類 `readd`。`room.member` の `pending_readd`）。構成員の他の端末のうちサーバーの epoch にある端末が、引き継ぎの規則（第4章 4.1）で行う。その端末の leaf の Remove と新しい KeyPackage の Add を 1 つの Commit に入れる。RFC 9420 12.2 は、同じ Commit に Remove があれば、既にいる端末の Add を許す。端末は Welcome で戻り、取りこぼした epoch の本文は鍵のバックアップと `key_request`（13）で読む。引き継ぐ端末がその端末の KeyPackage を取れない時（使い切りも最後の手段も無く `KEY-001`）は、Remove だけの Commit を行う。サーバーは、再参加待ちの端末が Remove されて同じ Commit で Add されなければ、その端末を端末の追加待ちに替える。記録は `mls_pending` の `add` で、`room.member` の `pending_add` を流す。その端末が KeyPackage を置いた後は、5.5 の 4 の経路で Add される。替えなければ、その端末は再参加待ちのまま leaf だけを失う。次に引き継ぐ端末は記録に無い leaf の Remove を含む Commit を作れず（`KEY-009`）、`POST /me/mls/rejoin` も行が残るため立て直せず、端末は戻れない。退けた案：Remove だけの Commit を `KEY-009` で拒む形。KeyPackage が尽きた端末の再参加を引き継ぐ端末が止まり、取り消しによる Remove（`remove` に替わった行）との区別も要る。
  2. グループの再初期化：再参加を行える端末が無い時は、再参加待ちの端末が `POST /rooms/{id}/mls/reinit` でグループを作り直す。無い時とは、Commit を作った端末だけがサーバーの epoch にあり、その端末が壊れているか現れない時。サーバーは世代を 1 増やし、呼んだ端末を leaf 0 とする epoch 0 のグループを作り、前の世代の leaf の記録・待ち・Commit を消す。そのトークに入るべき全端末（構成員と追加待ちの構成員の承認済みの端末）を端末の追加待ちにする。呼んだ端末は引き継ぎの規則で各端末を Add する（5.5 の 4 と同じ経路）。他の端末は `room.mls` の世代が自分より新しければ、現在の状態を捨てて Welcome を待つ。
  - サーバーが再初期化を許す条件：呼んだ端末が再参加待ちで、次のどれかが成り立つ時。(a) 現在の epoch の Commit を、Commit を作った端末以外の全 leaf の端末が拒んだ。(b) 呼んだ端末が現在の世代で 2 回以上拒んだ。(c) 呼んだ端末の最後の報告から 10 分（固定）が過ぎ、その間にサーバーが Commit を受け付けていない。満たさなければ `KEY-013`（`params.reason` は `not_pending`、`too_early`（`params.allowed_at` に許される時刻）、`limit` のいずれか）。
  - 上限：1 つの端末が同じトークで再初期化できるのは 24 時間に 2 回まで。3 回目は `KEY-013`（`limit`）で、端末はそのトークを「この端末では読めない」として表示し、アプリの更新を待つ（16 の H-12-20）。繰り返し拒むのはその端末の実装であり、サーバーと他の端末からは直せない。
  - 知らせ：再初期化のたびに管理者へ `mls_reinit`（第7章 9）。上限に当たった時は `mls_reinit_limit`。
  - 安全：再初期化は、構成員の端末が新しい KeyPackage から作る通常のグループの作成と同じ。サーバーが渡す GroupInfo による外部参加（RFC 9750 5.3 が警告する形）は使わない。加わる端末は Welcome の木と credential を「送信者の認証」（下）で確かめる。悪意の構成員は再初期化を繰り返せるが（上限 2 回/日）、既に本文を読める構成員で、新たに読める物は無い。
  - 退けた案：RFC 9420 16.12 の、UpdatePath の節ごとの確認（acknowledgement）を待ってから Commit を確定する形。家族の端末は多くが閉じていて確認が揃わず、その間は本文を送れない。サーバーの epoch を戻す形。epoch n+1 を処理した端末が送った本文と鍵のバックアップが宙に浮き、同じ番号の epoch が 2 つできる。
- 端末宛メールボックス（to-device）：端末から端末への暗号文（下の表の種類）を置く。`welcome` 以外の種類は HPKE で相手の端末の鍵合意鍵へ暗号化する（RFC 9180。base モード、DHKEM P-256、HKDF-SHA256、AES-128-GCM）。`info` は文字列 `family-talk/v1/inbox` の UTF-8、1 バイトの 0、種類の文字列の UTF-8 の連結。AEAD の追加データは、送り手の端末の識別子の 16 バイトと宛先の端末の識別子の 16 バイトの連結。置く暗号文は KEM の出力（65 バイト）と AEAD の暗号文の連結。送り手の端末の署名鍵（5.3）で署名する。署名の対象は次の 7 つの連結。文字列 `ft.inbox/1` の UTF-8。1 バイトの 0。種類の文字列の UTF-8。1 バイトの 0。送り手の端末の識別子の 16 バイト。宛先の端末の識別子の 16 バイト。暗号文。署名の形は `device_sig` と同じ（ECDSA P-256、SHA-256、r と s の 64 バイト）。サーバーは送り手の登録した署名鍵で署名を確かめてから置く（通らなければ `KEY-009`）。受け手の端末も同じ鍵で確かめる。受け取ったら消す。期限 30 日。
- `welcome` の種類だけは MLS の Welcome（MLSMessage）そのものを置く。Welcome は MLS が KeyPackage の init 鍵へ HPKE で暗号化する。中の GroupInfo には Commit を作った端末の leaf の署名が付いている（RFC 9420 12.4.3.1）。二重に包まず、メールボックスの署名も付けない（署名の欄は空）。置くのはサーバー（Commit の受け付け）で、送り手は Commit を作った端末。

端末宛メールボックスの種類（`kind`）は次のとおり。サーバーは種類、送り手、宛先だけを知る。中身（復号した後の形）は JSON で、`v: 1` を持つ。

|kind|中身|送り手と宛先|根拠|
|---|---|---|---|
|`welcome`|MLS の Welcome（GroupInfo を含む。上のとおり HPKE で包まず、署名の欄は空）|Commit を作った端末から新しい leaf の端末へ（サーバーが置く）|本節|
|`keybundle`|`{v: 1, s (base64url の 32 バイト), key_version}`。`key_version` は 5.4 の版|本人の既存の端末から本人の新しい端末へ（承認の時）と、`S` の交代の時に本人の全端末へ|5.4 の (a)|
|`key_backup`|`{v: 1, items: [{group_id, epoch, secrets}]}`。`secrets` は全体実装設計書 4.6 の履歴の秘密（復号済み）。1 件 64 KiB に収まるよう分割|本人の既存の端末から本人の新しい端末へ（承認の時）。または `key_request` への応答|5.6|
|`key_request`|`{v: 1, group_id, epochs[]}`（足りない epoch の秘密の転送の依頼）|復号できない端末から、本人の他の端末と家族の端末へ|13 の「受け取った暗号文を復号できない」|

|`call_key_request`|`{v: 1, call_id}`|通話の鍵を復号できない参加者の端末から、鍵を配った端末へ|5.11|

|`sticker_remove_request`|`ft.content.sticker_remove_request/1`|タグされた本人の端末から、作成者と管理者の端末へ|第4章 5.9|

- 送信者の認証：MLS の leaf の署名鍵は端末の署名鍵。端末の署名鍵は本人の署名鍵（鍵バンドルから導く）で署名される（`user_sig`。対象は 5.3）。サーバーは「本人の署名鍵の公開部」、「端末の公開鍵」、「端末の証」を登録して配る（認証サービス）。leaf の credential は RFC 9420 5.3 の basic で、`identity` は本人の識別子の 16 バイトと端末の識別子の 16 バイトの連結（形は 5.3）。受け手の端末は、leaf の credential の `identity` および `signature_key` が、登録された `fdev/1` と一致することを確かめる。続けて、その `user_sig` が本人の署名鍵の公開部で通ることを確かめる（本人ごとの信頼。cross-signing の形）。本人の署名鍵の公開部は、初回に家族の端末が受け取った後は固定する。変わった時は警告する（TOFU + 変化の警告。5.4 の `S` の交代。`user.changed` の `fields` に `signing_key`）。安全番号（2 人の公開鍵から導く 60 桁）の照合は設定の画面に置く（第3章、第10章）。
- 構成員の追加と退出：招待で参加した本人の最初の端末は、既存の構成員の端末（誰でもよい。最初に処理した端末）がグループに Add する。退出・削除・端末の取り消しは Remove（以後の epoch を読めない。forward secrecy の後ろ側）。Remove を行う端末は、処理した端末。Commit の直列化（上）で競合を解く。提案（Proposal）を Commit と別に送る経路は設けない。Add と Remove は、Commit を作る端末がその Commit の中に値で入れる（RFC 9420 12.4 の「値で含める」）。サーバーは提案を作らず、署名鍵も持たない。外部提案は `external_senders` の拡張とサーバーの署名鍵を要し（RFC 9420 12.1.8）、DD-12-1 に反する。
- 端末が長く現れない時：90 日（初期値）現れない leaf は、サーバーが端末の削除待ちを立て、他の端末が Remove する。記録は 5.5 と同じで、`room.member` の `pending_remove` に `device_id` を添える。端末の取り消しと同じ経路で、サーバーは提案を作らない。本人の鍵バンドルのコピー（DD-12-4 の (a)）も消す。本人が戻った時は、端末が `POST /me/mls/rejoin` で端末の追加待ち（5.5）を立て直し、鍵のバックアップで履歴を取る。RFC 9750 の 8.2.2 節の推奨。

### 5.3 端末の鍵（DD-12-3）

|鍵|生成|形|置き場|用途|
|---|---|---|---|---|
|端末の署名鍵|端末の初回|P-256（ECDSA）。WebCrypto、抽出不可|IndexedDB|MLS の leaf の署名、端末宛メールボックスの署名、既知の端末で入り直す時の端末の証（`device_sig`。第3章 4.2）|
|端末の鍵合意鍵|端末の初回|P-256（ECDH）。WebCrypto、抽出不可|IndexedDB|HPKE の受け手（端末宛メールボックス、秘密分散の断片）|
|端末鍵|端末の初回|乱数 256 ビット|IndexedDB（WebCrypto の AES の鍵として抽出不可で保存）。Android はシェルが OS の鍵保管庫（StrongBox があれば）で包んだものを JS ブリッジから渡す（第9章）|鍵バンドルのコピー (a) の包み、端末の保存の鍵の包み|
|MLS の leaf の秘密（HPKE の鍵、path secret）|MLS の操作|MLS の実装が管理|IndexedDB（端末の保存の鍵で暗号化）|MLS|

- `device_sig` の署名の対象は、次の 3 つを順に連結したもの。
  - 文字列 `ft.device_proof/1` の UTF-8
  - 1 バイトの 0
  - WebAuthn の challenge（32 バイト。ログインの options が返した物）
- `device_sig` の署名の形：ECDSA P-256、SHA-256。署名は WebCrypto の形（r と s の 64 バイト）を base64url で送る。先頭の文字列で、MLS とメールボックスの署名と取り違えない。サーバーは `device_keys` の公開部（`fdev/1`）で確かめる。
- 端末の証（`user_sig`。本人の署名鍵による端末の公開鍵への署名。5.4、5.5 の 2）の署名の対象は、次の 6 つを順に連結したもの。
  - 文字列 `ft.device_cert/1` の UTF-8
  - 1 バイトの 0
  - 本人の識別子（UUIDv7）の 16 バイト
  - 端末の識別子（UUIDv7）の 16 バイト
  - 端末の署名鍵の公開部の SEC 1 の非圧縮の形（`0x04`、X、Y の 65 バイト）
  - 端末の鍵合意鍵の公開部の同じ形（65 バイト）
- `user_sig` の署名の形は `device_sig` と同じ（ECDSA P-256、SHA-256、r と s の 64 バイト、base64url）。本人と端末の識別子を含めるのは、同じ公開鍵の組を別の端末や別の人の記録に付け替えられないため。サーバーは本人の署名鍵の公開部（`fusr/1`）で確かめ、通らなければ `KEY-003`。家族の端末も同じ対象で確かめる（5.2 の送信者の認証）。
- MLS の credential（`fdev/1` の `mls_credential`）：RFC 9420 5.3 の `Credential` の TLS 符号化。`credential_type` は `basic`（0x0001）。`identity` は本人の識別子の 16 バイトと端末の識別子の 16 バイトの連結（32 バイト）。全体で 35 バイト（0x00、0x01、長さ 0x20、32 バイト）。値は本人と端末の識別子から決まるので、サーバーは登録の時に同じ値かを確かめる（違えば `KEY-009`）。端末は KeyPackage の leaf にこの credential を入れる。
- 試験のベクトル（`user_sig` と `mls_credential`）は次のとおり。
  - 本人の識別子は `0199e1c2-0000-7000-8000-000000000001`。端末の識別子は `0199e1c2-0000-7000-8000-000000000002`。
  - 端末の署名鍵の公開部は P-256 の基点 G、鍵合意鍵の公開部は 2G（JWK は上の指紋のベクトルと同じ）。
  - 本人の署名鍵の秘密は 3（公開部は 3G）。JWK の `x` は `Xsvk0aYzCkTI9--VHUvxZebGtyHvramF-0FmG8bn_Ww`。`y` は `hzRkDEmY_343SwbOGmSi7NgqsDY4T7g9mnmxJ6J9UDI`。
  - 署名の対象は 179 バイト。その SHA-256 は `ef88bfcaeeda45220ad62882a56ef8ed164ee5d55f427721a14553d60d897e25`。
  - この対象に対する `user_sig` の 1 つは次の値。`NQmuB28fr3taQAYp_b_iTQSIKoVXcTlU0v3VbM2MjjW0K6VsXjsvmBiC0N13IS2RHp4AEIlMIfLSkMLA3sRs_A`。ECDSA は乱数を使うので値は 1 つに定まらない。試験はこの値が 3G で通ることと、本人の識別子を 1 バイト変えた対象では通らないことを確かめる。
  - `mls_credential` は 16 進で `0001200199e1c20000700080000000000000010199e1c2000070008000000000000002`。base64url は `AAEgAZnhwgAAcACAAAAAAAAAAQGZ4cIAAHAAgAAAAAAAAAI`。
- 端末の鍵の指紋（第3章 4.4 の承認の画面と 5.2 の一覧）：端末の署名鍵と鍵合意鍵の公開部を 1 つに束ねた値で、人が 2 つの画面で見比べる。求め方は次のとおり。
  - 入力：次の 4 つを順に連結したもの。文字列 `ft.device_fingerprint/1` の UTF-8。1 バイトの 0。署名鍵の公開部の SEC 1 の非圧縮の形（`0x04`、X、Y の 65 バイト）。鍵合意鍵の公開部の同じ形（65 バイト）。
  - SHA-256 を取り、先頭 8 バイトをビッグエンディアンの符号なし整数にし、10 進で 20 桁（0 埋め）にして 5 桁ずつ 4 組を空白で区切る。例：`11811 22211 31855 63267`。
  - 2 つの鍵を束ねる理由：鍵合意鍵だけでは、サーバーが署名鍵を差し替えて攻撃者の leaf を本人の端末として全グループに Add させられる。署名鍵だけでは、鍵合意鍵を差し替えて `S` を攻撃者の鍵へ HPKE で送らせられる。
  - 求めるのは端末だけ（web-crypto）。サーバーは指紋を求めず返さない（サーバーが求めた指紋は、鍵を差し替えたサーバーに対して無力）。既存の端末は、`GET /auth/qr/{user_code}` の公開部から求めた値を承認の画面に出す。署名の前に `GET /me/devices` の `keys` から求めた値と突き合わせる（第3章 4.4）。
  - 64 ビットの理由：見比べる相手は人で、高齢者が読み上げられる長さにする。攻撃者が表示された値に合う別の鍵を 10 分（QR の期限）の中で探すには、EC の鍵の生成を 2^64 回の桁で要する。
  - 試験のベクトル：署名鍵の公開部を P-256 の基点 G、鍵合意鍵の公開部を 2G とする。SHA-256 は `a3e9e3eef3aa028394d2a1c66c597fcf9f626b0f89788e5aa1172f79a0750535`。指紋は `11811 22211 31855 63267`。JWK の `x`、`y`（base64url）は次のとおり。G は `axfR8uEsQkf4vOblY6RA8ncDfYEt6zOg9KE5RdiYwpY` と `T-NC4v4af5uO5-tKfA-eFivOM1drMV7Oy7ZAaDe_UfU`。2G は `fPJ7GI0DT36KUjgDBLUaw8CJaeJ38hs1pgtI_EdmmXg` と `B3dVENuO0EApPZrGn3Qw27p9reY86YIpngS3nSJ4c9E`。
- サーバーは端末の鍵の登録（`PUT /me/devices/{id}/keys`）で、署名鍵と鍵合意鍵の公開部が他の端末に登録済みでないことを確かめる（登録済みなら `KEY-009`）。理由：MLS の木の中で `signature_key` が一意であること（RFC 9420 7.3）を、サーバーの確かめ（5.2）がこの登録に依って担う。
- `navigator.storage.persist()` を初回に要求し、結果を記録する（調査資料 I-01 1.8 と 1.11、第8章 3.4）。iOS 17 以降のホーム画面のアプリでは許可される。許可されなければ設定の画面で知らせる。
- 端末の保存（コピー、下書き、キュー、索引、MLS の状態）は「端末の保存の鍵」（端末ごとの乱数 256 ビット。端末の初回に作り、端末鍵で包んで IndexedDB に置く）で暗号化する。鍵バンドルの秘密 `S` からは導かない。`S` の交代（5.4）で端末の保存を暗号化し直す必要を無くすため。アプリのロック（第3章）は画面の制御であり、鍵は OS の保存領域の暗号化に守られる（iOS、Android とも OS が暗号化。PC のブラウザは OS 次第で、手順書に書く）。

### 5.4 鍵バンドルと回復（DD-12-4、DD-12-5）

鍵バンドルの秘密 `S`（乱数 256 ビット）から、HKDF-SHA256（RFC 5869）で次の鍵を導く。

|導く鍵|info|用途|
|---|---|---|
|本人の署名鍵の種|`family-talk/v1/user-signing`|P-256 の秘密鍵を決定的に導く（RFC 6979 の手順で種から）。端末の公開鍵に署名|
|鍵のバックアップの鍵|`family-talk/v1/key-backup`|epoch の秘密のバックアップ（5.6）の暗号化（AES-256-GCM）|
|秘密分散の係数|`family-talk/v1/share-coef`|(c) の片を決定的に作る 1 次の係数（32 バイト）。同じ `S` からはどの端末でも同じ片ができる|

- 端末の保存の鍵は `S` から導かない（5.3。端末ごとの乱数）。
- `S` には版（`key_version`。1 から始まる整数）がある。本人の署名鍵の公開部（`fusr/1` の `version`）と同じ値で、`S` の交代（下）のたびに 1 増える。コピー（`fkb/1`）と鍵のバックアップ（`fkb-history/1`）は、作った時の `S` の版を `key_version` に持つ。サーバーは今の版と違う `key_version` の書き込みを `KEY-011` で拒む（交代の後に古い `S` で書かれた物を混ぜない）。

`S` の包んだコピーをサーバーに置く（AES-256-GCM または HPKE。版と方式の識別子を先頭に）。系統は次のとおり。

|系統|包む鍵|置き場|回復の操作|備考|
|---|---|---|---|---|
|(a) 本人の端末|各端末の端末鍵（AES-256-GCM）|サーバー（端末ごと）|既存の端末で新しい端末を承認（QR。第3章）。既存の端末が `S` を新しい端末の鍵合意鍵へ HPKE で送る（端末宛メールボックス）|端末の取り消しでコピーも消す|
|(b) 回復コード|回復コード（128 ビット。base32 の 26 文字。4 文字ずつの区切りと検査文字）から Argon2id（m=64 MiB、t=3、p=4。RFC 9106 第 2 推奨。salt は本人の識別子）で導いた 32 バイト `A` を、HKDF-SHA256（salt なし、info `family-talk/v1/recovery-wrap`）に通した鍵（AES-256-GCM）|サーバー|回復コードを入力。使ったら新しいコードを発行する（NIST SP 800-63B-4 の 4.2.1.1 節）|初回に必ず表示し、「書き留めた」の確認を取る。設定から再発行。サーバーは照合の値（`A` を HKDF-SHA256（salt なし、info `family-talk/v1/recovery-verify`）に通した 32 バイト）だけを持ち、定数時間で比べる。入力の試行を 10 回/日に制限する。照合の値から包む鍵は導けないので、サーバーの記録とバックアップを持つ人（管理者）はコピー (b) を開けない（7.1）。端末は `A` を送らない|
|(c) 家族の秘密分散の断片|`S` を GF(256)（多項式 x^8 + x^4 + x^3 + x + 1）の Shamir の秘密分散でしきい値 2 に分ける。バイトごとに、片の値 = `S` のバイト XOR（係数のバイト × x）で、係数の 32 バイトは `S` から HKDF で導く（上の表）。x は片の番号（1〜255）で、片を持つ構成員ごとに 1 つ。同じ構成員の端末は同じ番号の片を持つ。各片を、片を持つ構成員の承認済みの全端末の鍵合意鍵へ HPKE で包む（端末ごとに 1 つのコピー）|サーバー（片を持つ構成員の端末ごと）|新しい端末で「家族に頼む」を選ぶ。片を持つ構成員の全端末に「{name}さんの新しい端末を承認しますか」が出る。承認した端末は `GET /recovery/{request_id}/share` で自分の端末宛ての片のコピーを取って開き、片を新しい端末の鍵合意鍵へ HPKE で送る（`POST /recovery/{request_id}/approve`）。別の構成員の 2 片そろえば `S` が戻る（同じ構成員の 2 台は同じ片で数えない）|片を持つ構成員が 2 人に満たない家族では (c) は成立しないので、(b) と (d) を必須にする。片を持つ構成員が新しい端末を承認した時（`device.changed` の `approved`）は、本人の端末がその端末のコピーを足す（係数が `S` から決まるので、どの端末でも同じ片を作れる）。片を持つ構成員の端末が取り消された時は、サーバーがそのコピーを消す。片の番号は、本人の端末が既にある片の番号を読み、新しい構成員には使っていない最小の番号を割り当てる|
|(d) 家族回復鍵|家族回復鍵 `F`（乱数 256 ビット）から HKDF で導いた HPKE の鍵対の公開部（HPKE。RFC 9180。備考）|サーバー|カード 2 枚の語を入力。端末が検査語で誤りを見つけ、`F` を組み立ててから `POST /family/recovery-key/use` でコピー (d) を受け取り、復号する。サーバーはコピーを渡したことを「家族回復鍵の使用」として記録し、全構成員に知らせる（DD-12-16）|`F` はサーバーに置かない。`F` の公開部（`F` から導いた HPKE の公開鍵）だけをサーバーに置き、各端末は `S` を公開鍵へ HPKE で包んでサーバーに置く（家族回復鍵の秘密がなくてもコピーを作れる）。サーバーは `F` を持たないので開けたかどうかを知り得ず、渡したことを使用と数える。コピーを受け取るのは本人のセッション（未承認の端末も可）だけで、`F` が無ければ開けない。渡した回数を 10 回/日に制限する（(b) と同じ枠）|

- 家族回復鍵 `F` はしきい値 2 の 3 片に分け、各片を本システムの語表の語（2048 語の日本語の語表。語の数と符号化は第10章 10。語表は公開）に符号化して 3 枚のカードに印刷する。カードには片の番号と検査語が入る。設置の時（第11章 7.2 の初回）に印刷し、管理者は「印刷した」の確認を取るまで先へ進めない。
- カードの持ち主：3 枚は別々の大人が持つ。管理者が 2 枚以上を持つと、管理者はサーバーの記録とバックアップから全構成員の `S` を開けるので、E2EE は管理者に対して成り立たない。カード 1 は印刷した管理者（`families.card_printed_by`）。カード 2 と 3 は、受け取った構成員が自分の端末で「受け取った」を記録する（`POST /me/recovery-cards/{n}`。第3章 3.1）。サーバーは持ち主の名前を明示の文（7.1 の `{card_holders}`）に出し、管理者の画面に所在の表を出す。カードの作り直しで持ち主の記録は消える。
- 受け取りの記録の規則（サーバーが `POST /me/recovery-cards/{n}` で確かめる。`n` は 2 か 3）：
  1. カードを持てるのは、子ども区分でなく（第3章 9.1）、状態が通常（第3章 8）の構成員（管理者を含む）。子ども区分の構成員の記録は `MEM-010` で拒む。カード 2 枚で全構成員の記録を開けるので、保護者の制限の下にある子どもにはその力を置かない。
  2. その札を本人が既に持つと記録されていれば、何もしない（冪等）。別の人が持つと記録されていれば `MEM-009`。
  3. 本人が既に別の札（カード 1 は印刷した管理者、2 と 3 は記録された持ち主）を持つ時は、記録の時点でカードを持てる構成員（1 の条件）が 3 人以上いれば `MEM-011` で拒む。3 人未満なら許し、明示にそのまま出す。数えるのは記録の時点で、後から構成員が増えても記録は変えない。
  4. 記録は本人の申告で、サーバーは紙の所在を確かめられない。記録の役目は、明示（7.1）と管理者の画面の所在の表の 2 つ。
- 持ち主の変化：カードを別の人に渡す操作は設けない。手を離れた紙はコピーを取られ得るので、持ち主を変える時は「カードを作り直す」（10）を使う。作り直しで記録は消える。カード 1〜3 の持ち主が停止・削除・抹消された時は、記録を残し（紙は本人の手にある）、管理者に作り直しを勧める知らせを出す（第7章 9）。
- (c) の片は「代表の端末」ではなく、片を持つ構成員の承認済みの全端末に置く。本人が選ぶ設定は無い。理由は 3 つ。片を持つ人が手元のどの端末でも承認できる（高齢者が別の端末を探さない）。端末の取り消しで片の作り直しが要らない（同じ人の他の端末が片を持つ）。代表の端末の記録と経路（設定、一覧の欄、自動の移し替え）が要らない。
- (c) の試験のベクトル：`S` を 0x20 から 0x3f の 32 バイトとする。係数は `S` から HKDF-SHA256（salt なし、info `family-talk/v1/share-coef`、32 バイト）で導く。
  - 係数は `1be17cb5ec2c71edbaeb56f77a52eb544db8ac6cec7662a7b47d0d29419b716b`。
  - 片 1 は `3bc05e96c80957ca92c27cdc567fc57b7d899e5fd84354908c4437127da64f54`。
  - 片 2 は `16f8da52e77dc4e647e486ded889e387aa5a71ebf7d9f2624bc32069be10dce9`。
  - 片 3 は `0d19a6e70b51b50bfd0fd029a2db08d3e7e2dd871baf90c5ffbe2d40ff8bad82`。どの 2 片からも `S` が戻る。
- (b) の試験のベクトル：`A` を 0x00 から 0x1f の 32 バイトとする。
  - 包む鍵は `be2627735afaa2e01c1e7be08a96fa9fec844e402dc00fc55f5525c23db73dd0`。
  - 照合の値は `af0afa9c11573dfa41d7c5c978460ae1f0af5be3998d22e01b2fe400aac2af9d`。
  - 照合の値の base64url は `rwr6nBFXPfpB18XJeEYK4fCvW-OZjSLgGy_kAKrCr50`。
- 回復の順序（新しい端末の画面）：1 既存の端末で承認、(e) PRF（使える端末だけ）、2 家族に頼む、3 回復コード、4 家族回復鍵。(e)、2、3、4 を使った時は、どれを使ったかを `recovery.used`（第2章 6.2）で本人の全端末と管理者に知らせる。method は `prf`、`share`、`recovery-code`、`family` で、4 は全員に知らせる（第7章 9）。1 は端末の追加（第3章 4.4）であって回復ではなく、`recovery.used` は出さない。サーバーは既存の端末の承認を通常の端末の追加と区別できない（どちらも `/me/devices/{id}/approve`）。`S` の受け渡しは端末宛メールボックスの暗号文で、サーバーには見えない。1 の知らせは `device.changed` と `new_device` が担う。
- 鍵バンドルの秘密 `S` の交代：本人が「鍵を作り直す」を選んだ時（端末の侵害を疑う時。再認証）。承認済みの端末が次の順で行い、途中で切れても次に開いた時に続きから行う（端末は進み具合を IndexedDB に持つ）。
  1. 新しい `S'` を作り、本人の署名鍵を導き直す。承認済みと休眠の全端末（`GET /me/devices` の `keys`）の `user_sig` を新しい署名鍵で作り直す。`PUT /me/signing-key` に新しい公開部と全端末分の `user_sig` を 1 つの要求で送る。サーバーは全部が新しい鍵で通る時だけ置き換え、版を 1 増やし、古い版のコピー（全系統）を消す。続けて家族の全員に `user.changed`（`fields` に `signing_key`）、本人の全端末に `keybundle.changed` を流す。1 台でも欠けるか通らなければ `KEY-003` で何も変えない。
  2. 本人の他の端末へ `S'` を端末宛メールボックス（`keybundle`。新しい `key_version` を添える）で送る。各端末は受け取って自分のコピー (a) を置き直す。
  3. (b)（新しい回復コードを示す）、(c)、(d)、(e) のコピーを作り直す。
  4. 鍵のバックアップを `S'` の鍵で暗号化し直す（`?rewrap=true`。5.6）。
  - 2 以降の書き込みは新しい `key_version` を持つ。古い `S` を持つ端末が交代の後に書いた物は `KEY-011` で拒まれ、その端末は 2 の受け取りで追いつく。
  - MLS の leaf と鍵のバックアップの中身は端末の鍵なので変わらない。変わるのは本人の署名鍵（家族の端末が TOFU の警告を出す。5.2）と、`S` から導く鍵で包んだ物だけ。
- 任意の追加層：WebAuthn の PRF 拡張が使える端末（iOS 18 以上、PC の主要なブラウザ）では、パスキーの PRF の出力から導いた鍵で `S` を包んだコピー (e) を置く。パスキーでのログインと同時に鍵バンドルを開けられるようにするためである（第3章。［要実測］iOS 18 の `get()` の PRF）。(e) は (a)〜(d) を置き換えない。(e) の作り方は次のとおり。
  - salt：固定の公開の値で、文字列 `family-talk/v1/prf-salt` の UTF-8 の SHA-256（32 バイト）。16 進で `4f088cc6f62a0cac56f3685d5a9ad32d57df332429483b8a862dad7ef0a0b0ff`。端末はログインの `get()`（第3章 4.2）と登録の `create()`（第3章 4.1）で、options の `extensions.prf.eval` を `{first: salt}` とする。サーバーの options には無い。発見可能なログインは `allowCredentials` が空で、資格情報ごとの salt（`evalByCredential`）を使えない。そのため salt は、資格情報を選ぶ前に端末が持つ固定の値にする。salt が公開でも、PRF の出力は認証器の中の資格情報の秘密に依り、資格情報ごとに違う。
  - 鍵：`prf.results.first`（32 バイト）を HKDF-SHA256（salt なし、info `family-talk/v1/prf-wrap`）に通した 256 ビット。コピーは AES-256-GCM で `S` を包む。`fkb/1`（kind `prf`、`target_id` は資格情報の識別子の base64url）で `PUT /me/keybundle/prf/{cred_id}` に置く。
  - 出力の扱い：端末は PRF の出力をサーバーへ送らない。登録の応答では `clientExtensionResults.prf.results` を除き、`prf.enabled` は残す（登録の options は `prf` を求める）。ログインの応答では `clientExtensionResults` から `prf` を丸ごと除く。`get()` の出力に `enabled` は無く、`results` だけを除くと空の `prf` が残る。ログインの options は `prf` を求めないので、サーバーは空でも `prf` があれば求めていない拡張の出力として拒む。サーバーは、登録の応答に `prf.results` があれば `AUTH-003` で拒む。ログインの応答に `prf` があれば同じく `AUTH-003` で拒み、値を記録しない。サーバーが PRF の出力を知ると、サーバーの記録だけで (e) を開けて 7.1 の文が成り立たない。
  - いつ作るか：登録の `create()` で `results` が返れば直ちに。返らなければ（認証器が `create()` で評価しない時）、`prf.enabled` のパスキーでの次のログインで作る。`S` の交代では他の系統と同じく作り直す。
  - 消す時：パスキーを消す（`DELETE /me/passkeys/{id}`）と同じトランザクションで、その資格情報のコピー (e) も消す。PRF が使えない端末では `results` が無いだけで、ログインは変わらない。
  - 使用の知らせ：未承認の端末がコピー (e) を受け取った時（`GET /me/keybundle/prf/{cred_id}`）を回復 (e) の使用とする。同じトランザクションで `recovery.used`（method `prf`、result `success`）を本人の全端末と管理者に書く。承認済みの端末が取る時は知らせない（回復ではない）。サーバーは PRF の出力を持たず開けたかを知り得ないので、渡したことを使用と数える（H-12-17）。

### 5.5 新しい端末の参加（第3章と往復）

1. 新しい端末がログイン（パスキーまたは QR のログイン。第3章）し、端末の鍵（5.3）を作ってサーバーに登録する（未承認の端末）。
2. 回復の 4 段のどれかで `S` を得る。`S` から本人の署名鍵を導き、自分の端末の公開鍵に署名してサーバーに登録する（承認済みの端末になる）。子ども区分で保護者の「端末の追加の承認」（第3章 9.2）が有効な時は、その端末が保護者に承認されていなければこの登録は `MEM-006` で止まり、サーバーが保護者に求めを出す（第3章 4.4）。
3. 鍵のバックアップ（5.6）を取得して復号し、各グループの epoch の秘密を得る。
4. KeyPackage を置き、各グループに自分の leaf を Add してもらう。承認（2）の時にサーバーが、本人が構成員である全グループに「端末の追加待ち」を立てる。記録は srv-keys が持ち、`room.member` の `pending_add` に `device_id` を添えて流す。追加待ちを受けた端末が、新しい端末の KeyPackage でグループに Add する（Commit）。受ける端末は本人の既存の端末でも家族の端末でもよく、最初に処理した端末が行う（第4章 4.1 の引き継ぎと同じ規則）。サーバーが Commit の Add を読んで追加待ちを解く（5.2）。新しい端末は Welcome を受け取る。
5. サーバーの暗号文（過去のイベント）を取得し、epoch の秘密で復号して端末のコピーと索引を作る（第4章の同期）。

- 既存の端末が 1 台もない時の 4 は、家族の端末が追加待ちを引き継ぐ（家族がオンラインになった時）。それまでは新しいメッセージを受け取れない（画面に「家族の誰かが開くと受け取れます」）。
- 承認済みのまま leaf を失った端末（休眠の後に戻った端末、停止からの再開、保存の復元の後）は、起動時に自分が構成員のグループで leaf が無いことを見つける。そして `POST /me/mls/rejoin`（第2章 5.4）で同じ「端末の追加待ち」を立てる。入口は承認、rejoin、再参加（5.2 の復旧の 1。Remove を伴う）、再初期化（同 2。全端末を追加待ちにする）の 4 つ、仕組みは 1 つ。
- 未承認の端末は、グループに入れず、鍵バンドルのコピーも作れない。サーバーは未承認の端末の一覧を本人と管理者に示し、7 日で消す。

### 5.6 鍵のバックアップ（履歴）（DD-12-6）

- 端末は、グループの epoch が進むたびに、その epoch の秘密（中身は次の項）をサーバーの鍵のバックアップに置く。置く前に「鍵のバックアップの鍵」による AES-256-GCM で暗号化する。置き場は本人ごと、グループと epoch ごとに 1 件で、既にあれば置かない。
- 過去のイベントの復号には、MLS の PrivateMessage の復号に要る秘密を使う。秘密とは、RFC 9420 の 9 節の秘密木のうち、各 leaf の application ratchet の generation 0 の根を指す。履歴の鍵から HKDF でイベントの鍵を導く形は採らない。バックアップに置く中身（履歴の秘密）は、epoch ごとに 4 欄とする。欄は `epoch`、`group_context`（GroupContext の TLS 符号化）、`sender_data_secret`、`leaves[]` の 4 つ。`leaves[]` の要素は leaf ごとに `leaf_index`、`application_secret`、`signature_public_key`、`device_id` を持つ。形は全体実装設計書 4.6。端末はこれを、epoch が切り替わった直後（その epoch のメッセージを 1 つも処理する前）の状態から取り出す。新しい端末は、MLS の実装の「過去の epoch の受信専用の状態」（一次の実装の公開の型）を組んで取り込む。二次の実装は秘密木と epoch の秘密を公開しない。そのため、履歴の秘密を置くのと復号するのは一次の実装だけが担う（16 の H-12-14）。
- 新しい端末は鍵のバックアップを全部取得して復号し、epoch ごとの秘密で過去の暗号文を復号する。
- 鍵のバックアップの大きさ：グループ数 × epoch 数 ×（約 150 バイト + leaf の数 × 約 70 バイト）。10 人 × 3 端末のグループで約 3 KB／epoch。家族の 10 年で数十 MB。
- 鍵のバックアップはサーバーのバックアップ（restic）に含まれる（暗号文）。
- 既存の端末からの直接の転送：承認の時に既存の端末が鍵のバックアップの中身（復号済み）を新しい端末へ HPKE で送る（端末宛メールボックス、分割）。サーバーからの取得より速い。

### 5.7 メッセージと添付（第4章・第5章と往復）

- 本文は MLS の PrivateMessage の application data。中身の形式（JSON。種類、本文、関係、添付の一覧、プレビュー）は第2章。
- 添付（DD-12-7）：
  1. 端末が原本を読み、必要なら変換する（iOS の写真の選択は HEIC を JPEG に、動画を互換の形式に変換して渡す。調査資料。Android は第5章の規則で端末が縮小）。
  2. ファイルごとの鍵 `K_f`（乱数 256 ビット）と、サムネイル用の `K_t`、BlurHash（本文に入れる文字列）を作る。
  3. 64 KiB のチャンクごとに AES-256-GCM（nonce = チャンク番号 11 バイト + 最終フラグ 1 バイト。決定的）で暗号化する。AAD はチャンク番号。暗号文全体の SHA-256 を名前にする。
  4. スロットを取って PUT する（第5章。再開可）。
  5. 本文に添付の項目（`ft.content.attachment_item/1`。形は第5章 3。`K_f` は `key`、`K_t` は `thumb.key`）を入れて送る。
- 受け手は暗号文を取得し、ハッシュを確かめ、復号して表示する。サーバーが知るのは、端末が申告する暗号文の大きさだけで、MIME は知らない。
- サーバーの添付の上限（第5章）は暗号文の大きさで数える。
- 編集：編集の本文は新しい PrivateMessage（関係 `m.replace` 相当。第4章）。
- 予約送信：端末が現在の epoch で暗号化して予約する。送信までに epoch が進んだら、端末が次にオンラインの時に作り直す（サーバーは「予約の暗号文」を時刻にイベントとして記録するだけ。epoch が古い場合、受け手は鍵のバックアップから復号できる）。
- システムの知らせ（サーバーが発する「構成員が参加した」等）は平文のイベント（種類で区別）。本文を持たない。

### 5.8 通知（DD-12-10。第7章・第9章と往復）

- 通知の中身：`{event_id, room_id, sender_id}`（RFC 8291 で暗号化）。
- iPhone：SW が push を受け、`event_id` の暗号文を取得し、IndexedDB の MLS の状態で復号して `showNotification`（送信者の名前と本文の冒頭）。取得または復号に失敗したら「{name}さんからメッセージ」。宣言型の Web Push（iOS 18.4 以上）では、提案の通知の本文を「{name}さんからメッセージ」にし、SW が時間内に復号して通知を出せば提案の通知は出ない。出せなければ提案の通知が出る（第7章 5.1）。
- Android：シェルが UnifiedPush で受け、非表示の WebView（通知用の小さなページ）に `event_id` を渡して復号させ、結果で通知を出す。10 秒（初期値）で結果がなければ「{name}さんからメッセージ」。
- 着信（通話）の通知は本文を要しない（第6章）。

### 5.9 検索（DD-12-8。第4章と往復）

- 端末の SQLite（WASM。OPFS の同期アクセスの経路）に、復号した本文の FTS5 trigram の索引を持つ。Intl.Segmenter で分かち書きした語も入れる（2 文字以下の語のため）。
- 索引の中身は端末の保存の鍵で暗号化しない（SQLite のファイルは OPFS にあり OS の暗号化に守られる。アプリのロックで画面を守る。16 の既知の制約）。
- 新しい端末は過去のイベントを復号しながら索引を作る（背景。進み具合を表示）。
- サーバーは検索の API を持たない。

### 5.10 URL のプレビュー（DD-12-9。第4章と往復）

- 送信者の端末が URL を見つけたら、家族のサーバーの代理（`POST /preview`）に取得を頼む。代理は内部のアドレス帯と自分自身を拒み、時間と大きさの上限（第1章 4.2）で切り、`<title>`、説明、画像の URL、サイトの名前を返す。画像は代理が取得して端末に渡し、端末が添付と同じ形で暗号化する。
- 端末はプレビューを本文に同梱して送る。受け手は取得しない。
- サーバーは URL を知る（明示 7）。構成員の設定で切れる（既定は有効）。

### 5.11 通話（DD-12-11。第6章と往復）

- 通話の開始時、開始する端末が通話の鍵 `K_c`（乱数 256 ビット）と番号 `i`（0 から）を作り、トークの MLS グループの本文（種類「通話の鍵」）で配る。参加者は SFU の鍵の提供者に `K_c` を番号 `i` で渡す。
- 参加者が離れた時：残った参加者のうち識別子が最小の端末が新しい鍵と番号 `i+1` を配る。参加者が増えた時：前回の鍵の配布から 10 秒以内なら既存の鍵をそのまま使い、超えていれば新しい鍵を配る。番号は 256 で巡回する。
- 鍵の切り替えの遅れを埋めるため、配った後 1 秒待って使い始める。
- 参加者の端末が、トークの本文で配られた通話の鍵を復号できない時がある（新しい端末の Add の前、epoch の競合）。その時は、鍵を配った端末へ端末宛メールボックスで `call_key_request` を送る。配った端末は `call_key` で直接返す（5.2 の表）。利用者の操作は要らない。
- 全端末で SFU の SDK の設定を統一する。鍵の大きさ 128 ビット（SDK が HKDF で導く）、鍵の環の大きさ 256、ラチェットなし、共有鍵あり。共有鍵ありとは、参加者ごとの鍵ではなく、1 つの鍵を番号で切り替える設定を指す。フレームの変換の経路は端末のブラウザで自動（WebKit 系は `RTCRtpScriptTransform`、Chromium 系は `createEncodedStreams`。第6章 7）。
- SFU と TURN はフレーム暗号の暗号文を中継する。SFU の通話の記録（誰がいつ）は平文（3）。
- 制約：iOS 17.2 未満ではフレーム暗号とサイマルキャストを両立できない（SDK の制約）。そのため画質の自動調整を SFU の側で行わず、端末が 1 層で送る。AV1 は使わない（H.264 と VP8。第6章）。

## 6. サーバーと端末の保存の保護

### 6.1 サーバーの記憶装置（R-12-2-1）

- 自宅のサーバー：/data は LUKS2（cryptsetup 2.7 以上）のボリュームとする。TPM 2.0 があれば無人で解錠し、なければ起動時にパスフレーズを入れる。無人の解錠は `systemd-cryptenroll --tpm2-device=auto --tpm2-pcrs=7` で設定する。回復鍵（`--recovery-key`）を紙に印刷する。Docker には bind mount で渡し、docker.service に `RequiresMountsFor=/data` を置く（第11章の設置の道具が行う）。
- TPM の無人解錠は、機体ごと盗まれた場合には効かない（盗んだ側でも起動すれば解錠される）。これはエンベロープ暗号化（6.2）と E2EE で補う。16 の H-12-5。
- VPS：事業者の提供する記憶装置の暗号化に依る。事業者は記憶装置とメモリを読める。E2EE により本文は読めず、エンベロープ暗号化によりディスクの機微なメタデータは読めないが、KEK がメモリにある間は読める。明示（7）に「VPS の事業者」を加える。
- 記憶装置の廃棄：LUKS のヘッダのキースロットを消す（`cryptsetup erase`。NIST SP 800-88 Rev.2 の Cryptographic Erase）。管理者の画面に「このディスクを捨てる」の手順を置く（第11章）。

### 6.2 エンベロープ暗号化（DD-12-12）

|鍵|生成|置き場|用途|交代|
|---|---|---|---|---|
|KEK（主鍵。256 ビット。id は UUIDv7）|設置（`ft setup` の 3。第11章 4）|`/etc/family-talk/secrets/kek`（ホストのルートのファイルシステム。所有者と権限は 10）。Compose の secrets で `/run/secrets/kek` として api と worker に渡す。/data に置かない|利用者 DEK の包み（XChaCha20-Poly1305。24 バイトの乱数 nonce。鍵の id を先頭に）|自動では交代しない。管理者がホストで `sudo ft keys rotate kek` を行う（下の「KEK の交代」）。新しい KEK で全 DEK を包み直し、本体は暗号化し直さない|
|利用者 DEK（256 ビット）|構成員の作成|postgres（KEK で包んだもの）。バックアップには包んだままで入る|その構成員の機微なメタデータ（IP、端末の名前、プロフィールの本文、誕生日、招待の記録の中の連絡先）の AES-256-GCM（乱数 nonce 96 ビット。1 DEK あたり 2^32 件未満）|抹消で破棄（crypto-shredding）|
|バックアップの鍵（restic のパスワード。256 ビットの乱数を base64）|初回の起動|/data/secrets と管理者の手元（紙）|restic のリポジトリ|restic の `key add` / `key remove` で追加と削除|

- 本文と添付は E2EE の暗号文であり、エンベロープ暗号化の対象にしない（二重にしない）。
- 鍵のバックアップ（5.6）と鍵バンドルのコピー（5.4）は本人の鍵で暗号化済みなので対象外。

KEK の交代は次の順で行う（ホストの `ft` の `keys rotate kek`。srv-admin `HostTools.Keys`）。

1. 新しい KEK を作り、`/etc/family-talk/secrets/kek` に加える。前の KEK は残す。
2. 新しい KEK を紙に表示し、「書き留めた」を確かめる。紙には KEK の id の先頭 8 文字と作った日を載せる。
3. api と worker のコンテナを作り直す。api と worker は秘密を起動の時に読むので（第1章 7.1 の 2）、作り直さないと新しい KEK を使わない。
4. api の起動（第1章 7.1 の 2）が、KEK のファイルにあって `key_versions` に無い id を見つけ、`key_versions` に加えて現在の鍵にする。続いて仕事 `kek_rewrap` を積む。
5. worker が全 DEK を新しい KEK で包み直す。`ft` は完了を待つ。DEK の数は構成員の数なので数秒で終わる。
6. `ft` が前の KEK をファイルから消し、api と worker をもう一度作り直す。途中で止まった時は、同じ命令をもう一度行うと続きから進む。

- 自動で交代しない理由：/etc に書けるのはホストの root だけで、コンテナに書かせると、KEK を /data とコンテナの外に置く分離（DD-12-12）が崩れる。また、交代のたびに紙を作り直して確かめる必要があり、人の手が要る。自動で交代すると紙が黙って古くなり、復元の時に機微なメタデータを失う（16 の H-12-6）。
- 交代を勧める時期：KEK を作ってから 2 年で、管理者に知らせる（第7章 9。設定 `keys.kek_rotation_reminder`）。2 年の根拠は NIST SP 800-57 Part 1 Rev. 5 の、鍵を包む対称鍵の使用期間の目安（調査資料 調査 H 1.12）。周期で交代しないことは 16 の H-12-13 に宣言する。
- 前の KEK の紙は、交代より前のバックアップが保持から消えるまで残す（初期値は月次 6 で約 6 か月。第11章 9.1）。`ft` は交代の完了の時に、前の紙を捨ててよい日を表示する。
- 戻す時（第11章 9.2）は、戻した `user_dek` の `kek_id` に合う KEK の紙を求める。

### 6.3 バックアップ（第11章と往復）

- 日次：`pg_dump -Fc` と `pg_dumpall --globals-only` の出力を、restic の `--stdin-from-command` で取り込む。/data の中の media、config、secrets も restic で置き場（USB の HDD、S3 互換のバケット）へ送る。整合は次の不変条件で保つ（第5章・第11章）：暗号文は名前（ハッシュ）で書き終えてから DB で参照し、参照が消えてから猶予の後に消す。
- 保持：日次 7、週次 4、月次 6（初期値。管理者が変えられる）。`forget --prune` を週 1 回。`check --read-data-subset=10%` を日次。復元の試験を月 1 回（別のディレクトリに戻して開けることを確かめる）。
- 鍵の持ち主：バックアップの鍵は家族のサーバー（自動実行のため）と管理者の手元（紙）。バックアップの媒体には置かない。
- KEK は /data の外にあるため restic の対象に入らない。KEK は家族回復鍵のカードに同梱しない（別の紙に印刷して管理者が保管。第11章の設置の手順）。KEK を失うと機微なメタデータだけが読めなくなり、本文と添付は影響を受けない（16 の H-12-6）。

### 6.4 端末の保存

- iPhone、Android：OS の保存領域の暗号化に依る。コピーと索引は端末の保存の鍵（5.3）で暗号化（索引は除く。5.9）。アプリのロック（第3章）。端末の取り消し（第3章）で、取り消された端末は次にオンラインの時に自分の保存を消す（取り消しが届かなければ消せない。16）。
- PC のブラウザ：OS のディスクの暗号化を手順書で勧める。共有の PC では「このブラウザを信頼しない」（セッションの終了で保存を消す）を選べる（第3章）。

- 秘密はログに書かない（11）。環境変数に置かない。
- 秘密のファイルは、所有者を 10001（api、worker、postgres の実行の利用者。第11章 3.1）、権限を 0400 にする。Compose の file の secret は、ホストのファイルを所有者と権限のまま差し込み、`uid`、`gid`、`mode` は効かない（調査資料 調査 H 1.4）。そのため、コンテナの利用者が所有者でなければ読めない。/etc/family-talk のディレクトリは root 0700 のままでよい（差し込みはディレクトリの権限に関係しない）。
- 読む側は、所有者が自分（ホストの `ft` は root）であることと、グループと他人に権限が無いことを確かめる（srv-common `Loader.ReadSecretFile`）。
- 初回の起動で秘密を生成する段は第1章 7.1 の 2（設置の流れでは第11章 4 の 8）。生成に失敗したら起動しない（第1章 7.1）。
- Go の実装：秘密は `[]byte` で持ち、使い終えたら明示的にゼロで埋める。完全な消去は言語の保証の外（16）。

## 11. ログの秘匿（第1章 10.4 の具体）

- 書かない：本文（暗号文も）、添付、トークン、鍵、Cookie、パスワード、回復コード。IP アドレスの生の値（28 日で消す別の表に置く。ログには出さない）。端末の名前、プロフィール、電話番号、メール。URL（プレビューの代理の URL は書かない）。
- 書く：要求の種類と経路。構成員、端末、トークの識別子（UUID）。結果の分類（第1章 10.3 のエラーコード表）。時刻と所要。認証の成否、認可の失敗、レート制限。管理者の操作、裏の処理の結果、秘密の生成と交代の事実。
- 実装：秘匿の処理（Redact）を、ログに渡す型で強制する。文字列の直接の書き込みは lint で禁じる（第14章）。
- 保持：Docker の回転（100 MB × 7）。caddy のアクセスログは IP を書かない設定にする（第11章）。

## 12. データの形式（本章が定めるもの）

|形式|版|中身|
|---|---|---|
|鍵バンドルのコピー|`fkb/1`|`{v: 1, kind: "device"\|"recovery-code"\|"share"\|"family"\|"prf", user_id, target_id, key_version, alg: "A256GCM"\|"HPKE-P256", nonce, ciphertext, kdf: {alg: "argon2id", m, t, p, salt} (kind=recovery-code のみ), share: {index, threshold, n} (kind=share のみ), created_at}`。`target_id` は kind=device なら端末の識別子、share なら片を持つ構成員の端末の識別子（その端末の鍵合意鍵へ包む）、prf なら資格情報の識別子の base64url（salt は固定で持たない。5.4 の (e)）、recovery-code と family なら `self`（本人に 1 つ）。`key_version` は作った時の `S` の版（5.4）。`share.index` は片の番号、`share.n` は片を持つ構成員の数|
|鍵のバックアップ|`fkb-history/1`|`{v: 1, user_id, group_id, epoch, key_version, alg: "A256GCM", nonce, ciphertext, created_at}`。`group_id` はグループの識別子（トークの識別子の 16 バイトと世代の 4 バイト。5.2）の base64url|
|端末の登録|`fdev/1`|`{v: 1, device_id, user_id, sig_pub (P-256, JWK), kem_pub (P-256, JWK), user_sig (本人の署名鍵による署名。対象は 5.3), mls_credential (5.3 の 35 バイトの base64url), created_at, approved_at}`|
|本人の署名鍵の公開部|`fusr/1`|`{v: 1, user_id, user_sig_pub (P-256, JWK), version, created_at, rotated_at}`。`version` は `S` の版（5.4。初回は 1）|
|添付の記述（本文の中）|`ft.content.attachment_item/1`|形は第5章 3。作り方は 5.7|
|通話の鍵（本文の中）|`ft.content.call_key/1`|`{v: 1, call_id, index (0-255), key (base64, 32 bytes), issued_at}`|
|回復コード|—|128 ビットを base32（RFC 4648、小文字なし）の 26 文字にし、検査の 2 文字（CRC-16 の上位）を足して、4 文字ずつ 7 つに区切る|
|家族回復鍵のカード|`fcard/1`|片の番号（1〜3）、しきい値 2、語の並び（語の数と検査語は第10章 10）|
|エンベロープ暗号文（DB の列）|`fenv/1`|`{v: 1, dek_id, nonce (96 bit), ciphertext}`。バイナリの列で、版 1 バイト、`dek_id` 16 バイト（UUIDv7）、nonce 12 バイト、暗号文と認証タグ 16 バイトの順。認証の追加データは頭の 29 バイトと呼ぶ側の文脈（表、列、行の識別子）|
|DEK の包み|`fdek/1`|`{v: 1, kek_id, nonce (192 bit), wrapped}`。版 1 バイト、`kek_id` 16 バイト（UUIDv7）、nonce 24 バイト、包んだ DEK 48 バイト（32 と認証タグ 16）の順で、計 89 バイト。認証の追加データは頭の 41 バイトと `dek_id`|

- JSON の鍵は英語、値の符号化は base64url。API の形は第2章。
- `fenv/1` は `kek_id` を持たない。KEK が効くのは DEK の包みだけで、KEK の交代では本体を暗号化し直さない（6.2）。本体が `kek_id` を持つと、交代の後も古い値が残る。
- 認証の追加データは文脈を含む。暗号文を別の行や別の構成員の行へ移すと、開けなくなる。

## 13. 失敗の扱い

|失敗|扱い|
|---|---|
|新しい端末が鍵バンドルを回復できない（既存の端末なし、家族がオフライン、回復コード不明、カードなし）|端末は「未承認」のまま待つ（7 日）。画面に 4 段の案内。家族がオンラインになると承認の求めが届く|
|Commit の競合（同じ epoch に 2 つ）|サーバーは 1 つだけ受け付け、他は 409。端末は新しい epoch を取り込んで作り直す|
|Commit の中身がサーバーの規則に合わない（5.2 の「Commit の確かめ」の 9 つのどれか。送信者の leaf、Remove の番号、値の Update、Add の KeyPackage の署名・鍵の形・有効期間、Add の端末の状態、`encryption_key` の重なり、`path` の要否と中身、Welcome の宛先と `kem_output` の形、読めない提案）|サーバーは `KEY-009` で拒み、epoch は進まない。端末は最新の epoch と追加待ち・削除待ちを取り直して作り直す。端末の不具合なので記録する|
|受け手の端末が、サーバーが受け付けた Commit または Welcome を処理できない（サーバーが読めない部分の誤り）|5.2 の「拒まれた Commit からの復旧」。端末は取りこぼした Commit を取り込み直してから報告し、再参加を待つ。再参加を行える端末が無ければ再初期化。利用者の操作は要らない。取りこぼした epoch の本文は鍵のバックアップと `key_request` で読む|
|端末が同じトークで再初期化を 24 時間に 3 回求めた|サーバーは `KEY-013`（`limit`）で拒む。端末はそのトークを「この端末では読めない」と表示し、アプリの更新を待つ（H-12-20）|
|KeyPackage の有効期間が今の時刻を外れている（端末の時計のずれ）|Add に使う端末は捨てて取り直す。サーバーは置く時に `not_before` と `not_after` を確かめるので、ずれの余裕（1 日）を超える時計の端末の KeyPackage は置かれない|
|鍵バンドルの版が古い（`S` の交代の後に古い `S` で作ったコピー・バックアップを書いた）|サーバーは `KEY-011` で拒む。端末は端末宛メールボックスの `keybundle` で新しい `S` を受け取ってから書き直す|
|受け取った暗号文を復号できない（epoch の秘密がない、鍵のバックアップに未登録）|端末は「鍵のバックアップに無い」を表示し、本人の他の端末または家族の端末に鍵の転送を頼む（端末宛メールボックス）。届くまで「読めません」|
|KeyPackage が尽きた端末を Add できない|「最後の手段」の KeyPackage で Add し、端末が次にオンラインの時に補充。最後の手段も使えなければ、端末がオンラインになるまで Add を保留。その端末が再参加待ち（5.2 の復旧の 1）なら、引き継ぐ端末は Remove だけの Commit を行い、サーバーがその端末を追加待ちに替える|
|添付のハッシュが一致しない|破棄し「壊れています」。再取得を 1 回|
|SW が通知の復号に失敗|送信者の名前だけ表示|
|通話の鍵が届く前にフレームが来た|SDK が 10 フレーム（初期値）まで待ち、それでも復号できなければ無音と黒。鍵が届けば回復|
|KEK が読めない（ファイルがない）|api と worker は起動しない（第1章 7.1）。手順書に紙からの復元|
|家族回復鍵のカードを 2 枚失った|家族回復鍵は失われる。既存の端末が 1 台でもあれば「カードを作り直す」で新しい `F'` を作れる。全端末がなければ、各構成員の回復コードか家族の秘密分散の断片で `S` を回復し、その後カードを作り直す|
|全構成員が全端末と全ての紙を失った|記録は読めない（H-12-1）|
|LUKS の解錠に失敗（TPM の状態が変わった）|紙の回復鍵で解錠。手順書|
|バックアップの復元の後に鍵のバックアップとサーバーの暗号文の世代がずれる|鍵のバックアップは epoch ごとに 1 件で単調増加のため、古いバックアップに戻しても端末が持つ新しい epoch の秘密で埋め直せる。端末は復元の後の初回の同期で鍵のバックアップの欠けを検出し補う|
|DEK の破棄の後に古いバックアップから戻した|DEK の包みは戻るが、抹消の記録（別の表）により api は DEK を使わない（抹消の記録は戻しても消えないよう、復元の手順で抹消の一覧を先に適用する。第11章）|
