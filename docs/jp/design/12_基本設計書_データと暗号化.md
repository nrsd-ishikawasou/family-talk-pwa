## 本書の位置付け

- 概要設計書 第12章「データの所在、秘密、暗号化」を詳細化し、設計計画書の未決事項 O-01「端から端の暗号化」を閉じる。本章の結論は第3章（認証、構成員、端末）、第4章（トーク）、第5章（メディア）、第6章（通話）、第7章（通知）、第8章・第9章（シェル）、第11章（運用）の形を決める。
- 本章は arc42 の「横断的な概念」のうち、データの所在と保護に当たる。脅威は第1章 11.2 の T-1〜T-18 を受け、対策を本章に置き、残る既知の制約を 16 で宣言する。
- 準拠：MLS（RFC 9420、RFC 9750）、HPKE（RFC 9180）、HKDF（RFC 5869）、AES-GCM（NIST SP 800-38D）、Argon2（RFC 9106）、WebCrypto（W3C）、WebAuthn Level 3（W3C Recommendation 2026-08-25）、NIST SP 800-63B-4（回復）、NIST SP 800-57 Part 1 Rev.5（鍵の管理）、NIST SP 800-88 Rev.2（消去）、NIST SP 800-53 Rev.5（AU-9(4)、SC-12(1)）、NIST SP 800-111（記憶装置の暗号化）、RFC 8291（Web Push の暗号）、RFC 5763/5764（DTLS-SRTP）、RFC 8446（TLS 1.3）。出典は調査資料と NRSD の作業記録にある。

## 2. 目的と範囲

### 2.1 受ける要件

概要設計書 第12章の R-12-1-1、R-12-2-1、R-12-3-1、R-12-3-2、R-12-4-1、R-12-5-1、R-12-6-1、R-12-7-1。対応は 14。

### 2.2 扱うもの・扱わないもの

- 扱う：データの所在と保護の区分、通信の保護、E2EE の設計（群、スイート、サーバーの責務、端末の鍵、鍵バンドルと回復、履歴、新しい端末、添付、通知、検索、プレビュー、通話）、サーバーの保存の保護、端末の保存の保護、明示、外へ送る情報、消すこと、秘密の鍵、ログの秘匿。
- 扱わない：各機能の API と画面（第2〜7章、第10章）、設置とバックアップの手順（第11章）、Android の鍵保管庫の使い方（第9章）、認証の流れ（第3章。本章は鍵の受け渡しだけ）。

## 3. データの所在と保護の区分

第1章 8.1 の一覧を、本章の結論で確定する。「平文」は家族のサーバーが読める、「暗号文」は読めない。

|データ|保存先|区分|鍵の持ち主|バックアップ|
|---|---|---|---|---|
|メッセージの本文（テキスト、スタンプ、位置、投票、ノート、アルバムの説明）|postgres（MLS の暗号文）|暗号文|トークの構成員の端末|要（暗号文のまま）|
|添付の原本、サムネイル、BlurHash|media（暗号文。名前は暗号文の SHA-256）|暗号文|送信者が作った鍵（本文に同梱）|要|
|検索の索引|端末（OPFS）|端末のみ|端末|不要（再作成）|
|URL のプレビュー|本文に同梱|暗号文|同上|—|
|通話の音声と映像|保存しない|—|通話の参加者（通話ごとの鍵）|—|
|トーク（種類、名前、アイコン、構成員、設定）|postgres|平文（名前とアイコンは暗号文。4 を参照）|—|要|

|端末（識別子、名前、最終の利用、IP、購読、公開鍵、署名）|postgres|識別子・公開鍵・署名・購読は平文。名前と IP はエンベロープ暗号文|家族のサーバー（KEK）|要|

|鍵のバックアップ（epoch の秘密）|postgres|暗号文|本人（鍵のバックアップの鍵）|要|

- トークの名前とアイコンは MLS の GroupContext の拡張ではなく、本文と同じ暗号文のイベント（種類「トークの設定」）として持つ。一覧の画面は端末のコピーから描く。サーバーは「トーク n」の番号だけを知る。
- 通話の音声と映像は保存されない（D-13-1、R-12-1-1）。SFU はフレーム暗号の暗号文を中継するだけで、録画と混合の機能を持たない。

## 4. 通信の保護

|経路|保護|版と下限|
|---|---|---|
|端末 ↔ caddy（HTTPS、WebSocket）|TLS 1.3 を既定、TLS 1.2 を下限（iOS 16.4 と WebView 138 は 1.3 対応。1.2 は古い PC のため）。暗号の組は AEAD（AES-GCM、ChaCha20-Poly1305）に限り、RSA の鍵交換と CBC は無効。HSTS（max-age 1 年、preload なし）。証明書は第11章|RFC 8446、RFC 7525 の後継（BCP 195）|
|端末 ↔ sfu（WebRTC）|DTLS-SRTP（RFC 5763、5764）。ICE/TURN は第6章。その内側にフレーム暗号（DD-12-11）|—|
|家族のサーバー → プッシュ配信サービス|RFC 8291（aes128gcm）、RFC 8292（VAPID）。中身は event_id と room_id（DD-12-10）|—|
|Android のシェル ↔ 家族のサーバー（常時接続）|TLS 1.3（WebSocket）。中身は UnifiedPush の仕様（RFC 8291 で暗号化された通知）|第9章|
|家族のサーバー → URL のプレビューの取得先|HTTPS（相手次第）。内部のアドレス帯を拒む。時間切れ 10 秒、応答 1 MiB まで|第4章|
|家族のサーバー → 証明書の発行機関、DNS の提供者、公開リポジトリ|HTTPS。トークンは *_FILE|第11章、第13章|
|シェル ↔ WebView|`WebMessageListener` のオリジンの許可リスト（第9章）|—|

- WebSocket は第1章 10.6 の専用トークンとオリジンの検証。
- 端末の中：MLS の状態と鍵は Service Worker と画面の間で IndexedDB を共有し、Web Locks で epoch の処理を直列化する（第7章）。

## 5. 端から端の暗号化の設計

### 5.1 比較の結論（O-01）

第1章 2.3 の目標の順で 3 つの設計を比較した。詳細は NRSD の作業記録にあり、要点は次のとおり。

|目標|送信者鍵の方式|MLS|E2EE なし|
|---|---|---|---|
|1 記録を失わない|端末と紙に依存|端末、家族の端末、紙の 4 段（DD-12-4、DD-12-5）で E2EE なしと同等|サーバーの記録とバックアップの鍵（紙）|
|2 いつでも届く|端末側の通知・検索・プレビュー|同左。SW とシェルの復号、端末の索引、同梱のプレビュー、iOS の写真の選択時の変換で小さな劣化に収まる|サーバーで素直に成立|
|3 外に出さない|受動的な管理者、実行時の侵害からの過去、VPS、SFU の終端に対して守れる|同左|守れない|
|4 迷わない|新しい端末の承認と回復の画面が増える|同左。標準的な通信アプリの「端末の連携」と「バックアップの鍵」の形にする|ログインすれば全部見える|
|6 運用が続く|既製の部品がない|部品は 2 系統（差し替え点を切る）。サーバーは暗号を持たない|部品は標準|

- 目標 1 と 2 は本章の設計で同等まで持っていけ、目標 3 で MLS が勝つ。第1章 DD-1-16 により MLS を採る（DD-12-1）。
- 送信者鍵の方式は、寛容なライセンスでブラウザで動く既製の部品がなく、侵害後の安全性の回復（PCS）がないため退ける。

### 5.2 群の暗号（MLS）

- トークごとに 1 つの MLS グループ。1 対 1 のトークも 2 人のグループ。構成員の端末ごとに 1 つの leaf（1 人 3 端末なら 3 leaf）。
- 暗号スイート 0x0002（DD-12-2）。耐量子のスイート（MLS WG の文書が RFC になった時）への移行は、グループの再作成（新しいスイートで新しいグループを作り、古いグループに「移行した」の本文を残す）で行う。スイートはグループの作成時に固定され変えられないため。
- 部品：ウェブは TypeScript の MLS の実装（MIT）を一次とし、差し替え点（MLS の操作のインターフェース）の後ろに Rust の実装の WASM（Apache-2.0 OR MIT。WebCrypto の provider）を二次として持つ。両方を公式の相互運用の検証ベクトルで試験する（第14章 13.1、試験設計書）。Android のシェルは MLS を持たない（復号は WebView の中。DD-12-10）。
- 家族のサーバー（Go）は MLS の暗号を持たない。持つのは：
  - KeyPackage の保管：端末ごとに使い切りの KeyPackage を 20 個（初期値）と「最後の手段」の 1 個。10 個を下回ると端末が補充する。有効期限 90 日。
  - Commit の直列化：グループごとに epoch を持ち、現在の epoch に対する Commit を 1 つだけ受け付け、それ以外は 409 で拒む（第2章のエラーコード表）。受け付けた Commit は他の端末へ配る。
  - Welcome と GroupInfo の中継：新しい leaf への Welcome を端末宛メールボックス（to-device）に置く。
  - 暗号文の保管と順序：MLS の PrivateMessage をイベントとして記録し（第1章 DD-1-6）、順序と時刻を付ける。
  - 外形の検査：MLS の wire format の外側（種類、グループの識別子、epoch、送信者の leaf の index）だけを読み、送信者が認証された端末と一致するかを確かめる。本文は読めない。
- 端末宛メールボックス（to-device）：端末から端末への暗号文（Welcome、鍵の転送、通話の鍵の補助、検証の補助）を置く。HPKE（RFC 9180、DHKEM P-256、HKDF-SHA256、AES-128-GCM）で相手の端末の公開鍵へ暗号化し、本人の署名鍵（5.4）または端末の署名鍵で署名する。受け取ったら消す。期限 30 日。
- 送信者の認証：MLS の leaf の署名鍵は端末の署名鍵。端末の署名鍵は本人の署名鍵（鍵バンドルから導く）で署名され、サーバーは「本人の署名鍵の公開部」と「端末の公開鍵と署名」を登録して配る（認証サービス）。受け手の端末は、leaf の鍵が本人の署名鍵で署名されていることを確かめる（本人ごとの信頼。cross-signing の形）。本人の署名鍵の公開部は、初回に家族の端末が受け取った後は固定し、変わった時は警告する（TOFU + 変化の警告）。安全番号（2 人の公開鍵から導く 60 桁）の照合は設定の画面に置く（第3章、第10章）。
- 構成員の追加と退出：招待で参加した本人の最初の端末は、既存の構成員の端末（誰でもよい。最初に処理した端末）がグループに Add する。退出・削除・端末の取り消しは Remove（以後の epoch を読めない。forward secrecy の後ろ側）。Remove を行う端末は、処理した端末。Commit の直列化（上）で競合を解く。
- 端末が長く現れない時：90 日（初期値）現れない leaf は、他の端末が Remove し、本人の鍵バンドルのコピー（DD-12-4 の (a)）も消す。本人が戻った時は新しい端末として参加する（鍵のバックアップで履歴を取る）。RFC 9750 §8.2.2 の推奨。

### 5.3 端末の鍵（DD-12-3）

|鍵|生成|形|置き場|用途|
|---|---|---|---|---|
|端末の署名鍵|端末の初回|P-256（ECDSA）。WebCrypto、抽出不可|IndexedDB|MLS の leaf の署名、端末宛メールボックスの署名|
|端末の鍵合意鍵|端末の初回|P-256（ECDH）。WebCrypto、抽出不可|IndexedDB|HPKE の受け手（端末宛メールボックス、秘密分散の断片）|
|端末鍵|端末の初回|乱数 256 ビット|IndexedDB（WebCrypto の AES の鍵として抽出不可で保存）。Android はシェルが OS の鍵保管庫（StrongBox があれば）で包んだものを JS ブリッジから渡す（第9章）|鍵バンドルのコピー (a) の包み、端末の保存の鍵の包み|
|MLS の leaf の秘密（HPKE の鍵、path secret）|MLS の操作|MLS の実装が管理|IndexedDB（端末の保存の鍵で暗号化）|MLS|

- `navigator.storage.persist()` を初回に要求し、結果を記録する（iOS のホーム画面では許可される。第14章 4）。許可されなければ設定の画面で知らせる。
- 端末の保存（コピー、下書き、キュー、索引、MLS の状態）は「端末の保存の鍵」（乱数 256 ビット。鍵バンドルから HKDF で導き、端末鍵で包む）で暗号化する。アプリのロック（第3章）は画面の制御であり、鍵は OS の保存領域の暗号化に守られる（iOS、Android とも OS が暗号化。PC のブラウザは OS 次第で、手順書に書く）。

### 5.4 鍵バンドルと回復（DD-12-4、DD-12-5）

鍵バンドルの秘密 `S`（乱数 256 ビット）から HKDF-SHA256（RFC 5869）で導く：

|導く鍵|info|用途|
|---|---|---|
|本人の署名鍵の種|`family-talk/v1/user-signing`|P-256 の秘密鍵を決定的に導く（RFC 6979 の手順で種から）。端末の公開鍵に署名|
|鍵のバックアップの鍵|`family-talk/v1/key-backup`|epoch の秘密のバックアップ（5.6）の暗号化（AES-256-GCM）|
|端末の保存の鍵の種|`family-talk/v1/local-storage`|端末ごとに端末の識別子を salt にして導く|

`S` の包んだコピーをサーバーに置く（AES-256-GCM または HPKE。版と方式の識別子を先頭に）：

|系統|包む鍵|置き場|回復の操作|備考|
|---|---|---|---|---|
|(a) 本人の端末|各端末の端末鍵（AES-256-GCM）|サーバー（端末ごと）|既存の端末で新しい端末を承認（QR。第3章）。既存の端末が `S` を新しい端末の鍵合意鍵へ HPKE で送る（端末宛メールボックス）|端末の取り消しでコピーも消す|
|(b) 回復コード|回復コード（128 ビット。base32 の 26 文字。4 文字ずつの区切りと検査文字）から Argon2id（m=64 MiB、t=3、p=4。RFC 9106 第 2 推奨。salt は本人の識別子）で導いた鍵|サーバー|回復コードを入力。使ったら新しいコードを発行する（NIST SP 800-63B-4 §4.2.1.1）|初回に必ず表示し、「書き留めた」の確認を取る。設定から再発行。サーバーは回復コードのハッシュを持ち、入力の試行を 10 回/日に制限する|
|(c) 家族の秘密分散の断片|`S` を GF(256) の Shamir の秘密分散でしきい値 2、片数 n−1（本人を除く家族の人数。上限 10）に分け、各片を各構成員の「代表の端末」の鍵合意鍵へ HPKE で包む|サーバー（構成員ごと）|新しい端末で「家族に頼む」を選ぶ。家族 2 人の端末に「○○さんの新しい端末を承認しますか」が出る。承認した端末は自分の片を新しい端末の鍵合意鍵へ HPKE で送る。2 片そろえば `S` が戻る|構成員が 2 人以下の家族では (c) は成立しないので、(b) と (d) を必須にする。構成員の端末が替わった時は片を作り直す（本人の端末が次にオンラインの時）|
|(d) 家族回復鍵|家族回復鍵 `F`（乱数 256 ビット）から HKDF で導いた鍵（AES-256-GCM）|サーバー|カード 2 枚の語を入力。サーバーは「家族回復鍵が使われた」を全構成員に知らせ、記録する（DD-12-16）|`F` はサーバーに置かない。`F` の公開部（`F` から導いた HPKE の公開鍵）だけをサーバーに置き、各端末は `S` を公開鍵へ HPKE で包んでサーバーに置く（家族回復鍵の秘密がなくてもコピーを作れる）|

- 家族回復鍵 `F` はしきい値 2 の 3 片に分け、各片を 20 語（本システムの語表。2048 語の日本語の語表は第10章で定める。語表は公開）に符号化して 3 枚のカードに印刷する。カードには片の番号と検査語が入る。設置の時（第11章 7.2 の初回）に印刷し、管理者は「印刷した」の確認を取るまで先へ進めない。
- (c) の「代表の端末」は本人が設定で選ぶ（既定は最初の端末）。代表の端末が取り消されたら、次の端末を代表にして片を作り直す。
- 回復の順序（新しい端末の画面）：1 既存の端末で承認、2 家族に頼む、3 回復コード、4 家族回復鍵。どれを使ったかは本人と管理者に知らせる。
- 鍵バンドルの秘密 `S` の交代：本人が「鍵を作り直す」を選んだ時（端末の侵害を疑う時）。新しい `S'` を作り、全系統のコピーを作り直し、鍵のバックアップを `S'` で暗号化し直す。古い `S` で包んだコピーは消す。
- 任意の追加層：WebAuthn の PRF 拡張が使える端末（iOS 18 以上、PC の主要なブラウザ）では、パスキーの PRF の出力から導いた鍵で `S` を包んだコピー (e) を置き、パスキーでのログインと同時に鍵バンドルを開けられるようにする（第3章。［要実測］iOS 18 の `get()` の PRF）。(e) は (a)〜(d) を置き換えない。

### 5.5 新しい端末の参加（第3章と往復）

1. 新しい端末がログイン（パスキーまたは QR のログイン。第3章）し、端末の鍵（5.3）を作ってサーバーに登録する（未承認の端末）。
2. 回復の 4 段のどれかで `S` を得る。`S` から本人の署名鍵を導き、自分の端末の公開鍵に署名してサーバーに登録する（承認済みの端末になる）。
3. 鍵のバックアップ（5.6）を取得して復号し、各グループの epoch の秘密を得る。
4. 各グループに自分の leaf を Add してもらう：本人の既存の端末または家族の端末が、新しい端末の KeyPackage でグループに Add する（Commit）。Welcome を受け取る。
5. サーバーの暗号文（過去のイベント）を取得し、epoch の秘密で復号して端末のコピーと索引を作る（第4章の同期）。
- 既存の端末が 1 台もない時の 4 は、家族の端末が行う（家族がオンラインになった時）。それまでは新しいメッセージを受け取れない（画面に「家族の誰かが開くと受け取れます」）。
- 未承認の端末は、グループに入れず、鍵バンドルのコピーも作れない。サーバーは未承認の端末の一覧を本人と管理者に示し、7 日で消す。

### 5.6 鍵のバックアップ（履歴）（DD-12-6）

- 端末は、グループの epoch が進むたびに、その epoch の秘密（epoch secret から導く「履歴の鍵」。MLS の exporter で `family-talk/v1/history` のラベルで 256 ビット）を「鍵のバックアップの鍵」で AES-256-GCM で暗号化し、サーバーの鍵のバックアップ（本人ごと、グループと epoch ごとに 1 件）に置く。既にあれば置かない。
- 過去のイベントの復号は、履歴の鍵から HKDF でそのイベントの鍵を導く形ではなく、MLS の PrivateMessage の復号に要る秘密（epoch ごとの「秘密木」の根）をバックアップる。バックアップる中身は `{epoch, tree_hash, encryption_secret, sender_data_secret, confirmed_transcript_hash}`（RFC 9420 の epoch の秘密。秘密木を再構成できる）で、新しい端末は MLS の実装の「復号専用の epoch の状態」の口から取り込む（全体実装設計書 4.6。二次の実装はこの口を持たないため、履歴の復号は一次の実装だけが担う）。
- 新しい端末は鍵のバックアップを全部取得して復号し、epoch ごとの秘密で過去の暗号文を復号する。
- 鍵のバックアップの大きさ：グループ数 × epoch 数 × 約 100 バイト。家族の 10 年で数 MB。
- 鍵のバックアップはサーバーのバックアップ（restic）に含まれる（暗号文）。
- 既存の端末からの直接の転送：承認の時に既存の端末が鍵のバックアップの中身（復号済み）を新しい端末へ HPKE で送る（端末宛メールボックス、分割）。サーバーからの取得より速い。

### 5.7 メッセージと添付（第4章・第5章と往復）

- 本文は MLS の PrivateMessage の application data。中身の形式（JSON。種類、本文、関係、添付の一覧、プレビュー）は第2章。
- 添付（DD-12-7）：
  1. 端末が原本を読み、必要なら変換する（iOS の写真の選択は HEIC を JPEG に、動画を互換の形式に変換して渡す。調査資料。Android は第5章の規則で端末が縮小）。
  2. ファイルごとの鍵 `K_f`（乱数 256 ビット）と、サムネイル用の `K_t`、BlurHash（本文に入れる文字列）を作る。
  3. 64 KiB のチャンクごとに AES-256-GCM（nonce = チャンク番号 11 バイト + 最終フラグ 1 バイト。決定的）で暗号化する。AAD はチャンク番号。暗号文全体の SHA-256 を名前にする。
  4. スロットを取って PUT する（第5章。再開可）。
  5. 本文に `{name, size, mime, key: K_f, hash, thumbnail: {name, key: K_t, hash, w, h}, blurhash, duration, w, h}` を入れて送る。
- 受け手は暗号文を取得し、ハッシュを確かめ、復号して表示する。サーバーは大きさと MIME（本文に入れる前に端末が申告する「大きさ」だけ。MIME は知らない）を知る。
- サーバーの添付の上限（第5章）は暗号文の大きさで数える。
- 編集：編集の本文は新しい PrivateMessage（関係 `m.replace` 相当。第4章）。
- 予約送信：端末が現在の epoch で暗号化して予約する。送信までに epoch が進んだら、端末が次にオンラインの時に作り直す（サーバーは「予約の暗号文」を時刻にイベントとして記録するだけ。epoch が古い場合、受け手は鍵のバックアップから復号できる）。
- システムの知らせ（サーバーが発する「構成員が参加した」等）は平文のイベント（種類で区別）。本文を持たない。

### 5.8 通知（DD-12-10。第7章・第9章と往復）

- 通知の中身：`{event_id, room_id, sender_id}`（RFC 8291 で暗号化）。
- iPhone：SW が push を受け、`event_id` の暗号文を取得し、IndexedDB の MLS の状態で復号して `showNotification`（送信者の名前と本文の冒頭）。取得または復号に失敗したら「○○さんからメッセージ」。宣言型の Web Push（iOS 18.4 以上）では、宣言の本文を「○○さんからメッセージ」にし、SW が復号できれば置き換える。
- Android：シェルが UnifiedPush で受け、非表示の WebView（通知用の小さなページ）に `event_id` を渡して復号させ、結果で通知を出す。10 秒（初期値）で結果がなければ「○○さんからメッセージ」。
- 着信（通話）の通知は本文を要しない（第6章）。

### 5.9 検索（DD-12-8。第4章と往復）

- 端末の SQLite（WASM。OPFS の同期アクセスの経路）に、復号した本文の FTS5 trigram の索引を持つ。Intl.Segmenter で分かち書きした語も入れる（2 文字以下の語のため）。
- 索引の中身は端末の保存の鍵で暗号化しない（SQLite のファイルは OPFS にあり OS の暗号化に守られる。アプリのロックで画面を守る。16 の既知の制約）。
- 新しい端末は過去のイベントを復号しながら索引を作る（背景。進み具合を表示）。
- サーバーは検索の API を持たない。

### 5.10 URL のプレビュー（DD-12-9。第4章と往復）

- 送信者の端末が URL を見つけたら、家族のサーバーの代理（`/api/preview?url=`）に取得を頼む。代理は内部のアドレス帯と自分自身を拒み、10 秒・1 MiB で切り、`<title>`、説明、画像の URL、サイトの名前を返す。画像は代理が取得して端末に渡し、端末が添付と同じ形で暗号化する。
- 端末はプレビューを本文に同梱して送る。受け手は取得しない。
- サーバーは URL を知る（明示 7）。構成員の設定で切れる（既定は有効）。

### 5.11 通話（DD-12-11。第6章と往復）

- 通話の開始時、開始する端末が通話の鍵 `K_c`（乱数 256 ビット）と番号 `i`（0 から）を作り、トークの MLS グループの本文（種類「通話の鍵」）で配る。参加者は SFU の鍵の提供者に `K_c` を番号 `i` で渡す。
- 参加者が離れた時：残った参加者のうち識別子が最小の端末が新しい鍵と番号 `i+1` を配る。参加者が増えた時：前回の鍵の配布から 10 秒以内なら既存の鍵をそのまま使い、超えていれば新しい鍵を配る。番号は 256 で巡回する。
- 鍵の切り替えの遅れを埋めるため、配った後 1 秒待って使い始める。
- 全端末で SFU の SDK の設定を統一する：鍵の大きさ 128 ビット（SDK が HKDF で導く）、鍵の環の大きさ 256、ラチェットなし、共有鍵なし。
- SFU と TURN はフレーム暗号の暗号文を中継する。SFU の通話の記録（誰がいつ）は平文（3）。
- 制約：iOS 17.2 未満ではフレーム暗号とサイマルキャストを両立できない（SDK の制約）→ 画質の自動調整を SFU の側で行わず、端末が 1 層で送る。AV1 は使わない（H.264 と VP8。第6章）。

## 6. サーバーと端末の保存の保護

### 6.1 サーバーの記憶装置（R-12-2-1）

- 自宅のサーバー：/data は LUKS2（cryptsetup 2.7 以上）のボリュームとし、TPM 2.0 があれば `systemd-cryptenroll --tpm2-device=auto --tpm2-pcrs=7` で無人の解錠、なければ起動時にパスフレーズ。回復鍵（`--recovery-key`）を紙に印刷する。Docker には bind mount で渡し、docker.service に `RequiresMountsFor=/data` を置く（第11章の設置の道具が行う）。
- TPM の無人解錠は、機体ごと盗まれた場合には効かない（盗んだ側でも起動すれば解錠される）。これはエンベロープ暗号化（6.2）と E2EE で補う。16 の H-12-5。
- VPS：事業者の提供する記憶装置の暗号化に依る。事業者は記憶装置とメモリを読める。E2EE により本文は読めず、エンベロープ暗号化によりディスクの機微なメタデータは読めないが、KEK がメモリにある間は読める。明示（7）に「VPS の事業者」を加える。
- 記憶装置の廃棄：LUKS のヘッダのキースロットを消す（`cryptsetup erase`。NIST SP 800-88 Rev.2 の Cryptographic Erase）。管理者の画面に「このディスクを捨てる」の手順を置く（第11章）。

### 6.2 エンベロープ暗号化（DD-12-12）

|鍵|生成|置き場|用途|交代|
|---|---|---|---|---|
|KEK（主鍵。256 ビット）|初回の起動|`/etc/family-talk/secrets/kek`（ホストのルートのファイルシステム。0600、root）。Compose の secrets で `/run/secrets/kek` として api と worker に渡す。/data に置かない|利用者 DEK の包み（XChaCha20-Poly1305。24 バイトの乱数 nonce。鍵の版を先頭に）|年 1 回自動（新しい KEK で全 DEK を包み直す。本体の再暗号化は不要）。NIST SP 800-57 の 2 年以内|
|利用者 DEK（256 ビット）|構成員の作成|postgres（KEK で包んだもの）。バックアップには包んだままで入る|その構成員の機微なメタデータ（IP、端末の名前、プロフィールの本文、誕生日、招待の記録の中の連絡先）の AES-256-GCM（乱数 nonce 96 ビット。1 DEK あたり 2^32 件未満）|抹消で破棄（crypto-shredding）|
|バックアップの鍵（restic のパスワード。256 ビットの乱数を base64）|初回の起動|/data/secrets と管理者の手元（紙）|restic のリポジトリ|restic の `key add` / `key remove` で追加と削除|

- 本文と添付は E2EE の暗号文であり、エンベロープ暗号化の対象にしない（二重にしない）。
- 鍵のバックアップ（5.6）と鍵バンドルのコピー（5.4）は本人の鍵で暗号化済みなので対象外。

### 6.3 バックアップ（第11章と往復）

- 日次：`pg_dump -Fc` + `pg_dumpall --globals-only` → restic の `--stdin-from-command`、media と config と secrets（/data の中）を restic で置き場（USB の HDD、S3 互換のバケット）へ。整合は「暗号文は名前（ハッシュ）で書き終えてから DB に参照、参照が消えてから猶予の後に消す」の不変条件（第5章・第11章）。
- 保持：日次 7、週次 4、月次 6（初期値。管理者が変えられる）。`forget --prune` を週 1 回。`check --read-data-subset=10%` を日次。復元の試験を月 1 回（別のディレクトリに戻して開けることを確かめる）。
- 鍵の持ち主：バックアップの鍵は家族のサーバー（自動実行のため）と管理者の手元（紙）。バックアップの媒体には置かない。
- KEK は /data の外にあるため restic の対象に入らない。KEK は家族回復鍵のカードに同梱しない（別の紙に印刷して管理者が保管。第11章の設置の手順）。KEK を失うと機微なメタデータだけが読めなくなり、本文と添付は影響を受けない（16 の H-12-6）。

### 6.4 端末の保存

- iPhone、Android：OS の保存領域の暗号化に依る。コピーと索引は端末の保存の鍵（5.3）で暗号化（索引は除く。5.9）。アプリのロック（第3章）。端末の取り消し（第3章）で、取り消された端末は次にオンラインの時に自分の保存を消す（取り消しが届かなければ消せない。16）。
- PC のブラウザ：OS のディスクの暗号化を手順書で勧める。共有の PC では「このブラウザを信頼しない」（セッションの終了で保存を消す）を選べる（第3章）。

## 11. ログの秘匿（第1章 10.4 の具体）

- 書かない：本文（暗号文も）、添付、トークン、鍵、Cookie、パスワード、回復コード、IP アドレスの生の値（28 日で消す別の表に置く。ログには出さない）、端末の名前、プロフィール、電話番号、メール、URL（プレビューの代理の URL は書かない）。
- 書く：要求の種類と経路、構成員と端末とトークの識別子（UUID）、結果の分類（第1章 10.3 のエラーコード表）、時刻、所要、認証の成否、認可の失敗、レート制限、管理者の操作、裏の処理の結果、秘密の生成と交代の事実。
- 実装：ログに渡す型に秘匿の処理（Redact）を型で強制し、文字列の直接の書き込みを lint で禁じる（第14章）。
- 保持：Docker の回転（100 MB × 7）。caddy のアクセスログは IP を書かない設定にする（第11章）。

|---|---|
|新しい端末が鍵バンドルを回復できない（既存の端末なし、家族がオフライン、回復コード不明、カードなし）|端末は「未承認」のまま待つ（7 日）。画面に 4 段の案内。家族がオンラインになると承認の求めが届く|
|Commit の競合（同じ epoch に 2 つ）|サーバーは 1 つだけ受け付け、他は 409。端末は新しい epoch を取り込んで作り直す|
|受け取った暗号文を復号できない（epoch の秘密がない、鍵のバックアップに未登録）|端末は「鍵のバックアップに無い」を表示し、本人の他の端末または家族の端末に鍵の転送を頼む（端末宛メールボックス）。届くまで「読めません」|
|KeyPackage が尽きた端末を Add できない|「最後の手段」の KeyPackage で Add し、端末が次にオンラインの時に補充。最後の手段も使えなければ、端末がオンラインになるまで Add を保留|
|添付のハッシュが一致しない|破棄し「壊れています」。再取得を 1 回|
|SW が通知の復号に失敗|送信者の名前だけ表示|
|通話の鍵が届く前にフレームが来た|SDK が 10 フレーム（初期値）まで待ち、それでも復号できなければ無音と黒。鍵が届けば回復|
|KEK が読めない（ファイルがない）|api と worker は起動しない（第1章 7.1）。手順書に紙からの復元|
|家族回復鍵のカードを 2 枚失った|家族回復鍵は失われる。既存の端末が 1 台でもあれば「カードを作り直す」で新しい `F'` を作れる。全端末がなければ、各構成員の回復コードか家族の秘密分散の断片で `S` を回復し、その後カードを作り直す|
|全構成員が全端末と全ての紙を失った|記録は読めない（H-12-1）|
|LUKS の解錠に失敗（TPM の状態が変わった）|紙の回復鍵で解錠。手順書|
|バックアップの復元の後に鍵のバックアップとサーバーの暗号文の世代がずれる|鍵のバックアップは epoch ごとに 1 件で単調増加のため、古いバックアップに戻しても端末が持つ新しい epoch の秘密で埋め直せる。端末は復元の後の初回の同期で鍵のバックアップの欠けを検出し補う|
|DEK の破棄の後に古いバックアップから戻した|DEK の包みは戻るが、抹消の記録（別の表）により api は DEK を使わない（抹消の記録は戻しても消えないよう、復元の手順で抹消の一覧を先に適用する。第11章）|

## 15. 用語

|用語|意味|
|---|---|
|MLS|Messaging Layer Security。RFC 9420 の群の鍵合意と暗号化の規格|
|グループ、leaf、epoch、Commit、Welcome、KeyPackage|MLS の用語。グループは暗号化の単位、leaf は端末、epoch は鍵の世代、Commit は世代を進める操作、Welcome は新しい leaf への案内、KeyPackage は leaf を加えるための公開鍵の束|
|配送サービス（DS）、認証サービス（AS）|RFC 9750 のサーバーの役割。本システムでは家族のサーバーの api が担う|
|鍵バンドルの秘密 `S`|本人ごとの根の秘密。そこから署名鍵、鍵のバックアップの鍵、端末の保存の鍵を導く|
|回復コード|本人が紙に持つ 128 ビットの秘密|
|秘密分散の断片|家族の他の構成員の端末に預ける `S` の秘密分散の片|
|家族回復鍵 `F`、カード|設置の時に作る根の秘密と、それを 2-of-3 に分けた紙|
|鍵のバックアップ|グループごと epoch ごとの秘密を本人の鍵で暗号化してサーバーに置いたもの。履歴の復号に使う|
|端末宛メールボックス|端末から端末への暗号文をサーバーが一時的に預かる場所|
|エンベロープ暗号化、KEK、DEK|サーバーの機微なメタデータを利用者ごとの鍵（DEK）で暗号化し、DEK を主鍵（KEK）で包む形|
|削除済みの印|消したイベントの代わりに残す「誰がいつ消したか」の骨|
|Cryptographic Erase|鍵の破棄による消去（NIST SP 800-88 Rev.2）|

## 16. 本章で宣言する既知の制約

|番号|既知の制約|理由|緩和|
|---|---|---|---|
|H-12-1|全構成員が全端末と全ての紙（回復コード、カード）を失うと、記録は永久に読めない|E2EE の原理|4 段の回復、家族回復鍵の印刷を初回に必須、年 1 回の「紙を確かめる」知らせ（第11章）|
|H-12-2|家族のサーバーが侵害され改竄された JavaScript が配られると、端末が次に読み込んだ時から鍵と本文が抜かれ得る。iOS ではこれを検知できない|ウェブアプリの配信の性質（調査 I-10）。第1章 T-5|過去の記録はクライアントが読み込むまで守られる。TLS、CSP、更新の署名の検証（第13章）、サーバーの更新の運用（第11章）。シェルの Android はイメージの中の資産の検証を第9章で検討|
|H-12-3|メタデータ（誰がいつ誰と、添付の大きさ、通話の時刻、端末、購読）はサーバーと管理者に見える|配送に要る|明示（7）、機微な部分のエンベロープ暗号化（6.2）|
|H-12-4|端末が侵害されれば（XSS、解錠済みの端末の開発者ツール、OS の侵害）鍵と本文が読める|端末の信頼の境界（第1章 11.1）|CSP、アプリのロック、端末の取り消し、鍵の作り直し|
|H-12-5|自宅のサーバーが機体ごと盗まれた場合、TPM の無人解錠により /data は解錠される|TPM の無人解錠と盗難耐性は両立しない|本文と添付は E2EE で読めない。機微なメタデータは KEK が別の場所（同じ機体のルートのファイルシステム）にあるが、機体ごとなら OS の認証が最後の壁。手順書に OS のログインの強化|
|H-12-6|KEK の紙と /etc の両方を失うと、機微なメタデータ（IP、端末の名前、プロフィールの本文、誕生日）は読めなくなる|鍵の分離の代償|本文と添付は影響を受けない。プロフィールは本人が入れ直せる|
|H-12-7|非抽出の CryptoKey はハードウェアに結び付かず、OS の保存領域の暗号化とアプリのロックに依る|ブラウザの仕様|Android はシェルの鍵保管庫で端末鍵を包む。iOS は OS の暗号化|
|H-12-8|端末の検索の索引は端末の保存の鍵で暗号化しない|SQLite のファイルの暗号化の部品を持たない|OS の暗号化、アプリのロック|
|H-12-9|取り消しが届かない端末（取り消しの前にオフラインになり二度と繋がらない端末）の保存は消えない|端末に届かないものは消せない|アプリのロック、OS の暗号化|
|H-12-10|受動的でない管理者（配る JS を改竄する管理者）に対しては E2EE は守れない|H-12-2 と同じ|明示には書かない（手順書に「改竄は犯罪になり得る」と書く。法務調査 L-2）|
|H-12-11|Android の通知の本文の表示は非表示の WebView の復号に依り、OS がシェルを止めている時は送信者の名前だけになる|Android の背景の制限（第9章）|「○○さんからメッセージ」で届く|
|H-12-12|Go の実装は秘密のメモリの完全な消去を保証できない|言語の仕様|使い終えたらゼロで埋める。将来の言語の仕組みを採り入れる|

［要実測］：iOS のホーム画面の Web アプリでの Worker + 変換 API の通話の E2EE；iOS 18 の WebAuthn PRF（`get()`）；iOS 16.4 の AES-KW/HKDF の実動；iOS での Argon2id（64 MiB）の所要時間；Android WebView 138 の通話の E2EE の経路；SW の中の MLS の復号の時間；シェルの非表示 WebView での復号の時間と電池；端末の索引の大きさと速度（10 年分の想定で 10 万件）；iOS の写真の選択時の動画の変換の条件。
