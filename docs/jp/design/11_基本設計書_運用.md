## 3. 配布の形（DD-11-1）

### 3.1 compose.yaml（初期値。digest は版ごと）

|サービス|イメージ|ネットワーク|公開|ボリューム|備考|
|---|---|---|---|---|---|
|api|`ghcr.io/<組織>/family-talk@sha256:…`（command: `serve`）|internal、edge|`127.0.0.1:8080`（host の loopback だけ。sfu の Webhook の到達用。外には出さない）|`/data`（bind、rw）|`user: 10001`、`cap_drop: [ALL]`、`security_opt: [no-new-privileges:true]`、`read_only: true`、`tmpfs: [/tmp]`、`secrets: [db_password, kek]`、`healthcheck: /health`|
|worker|同じイメージ（command: `work`）|internal|なし|`/data`（rw）|同上。`secrets: [db_password, kek, backup_password, dns_token]`|
|postgres|公式のイメージ（18 系。digest）|internal|なし|`/data/postgres`|`user: 10001`、`POSTGRES_PASSWORD_FILE`、`healthcheck: pg_isready`、`shm_size: 256m`|
|sfu|公式のイメージ（1.13 系。digest）|`network_mode: host`|3478/udp、5349/tcp（または割り当て）、50000〜60000/udp、7881/tcp|`/data/sfu`（設定）、caddy の証明書（ro）|`cap_drop: [ALL]`、`cap_add: [NET_BIND_SERVICE]`（443 を使う形の時）|
|caddy|本システムのビルド（DNS のモジュール入り。digest）|edge、internal|80/tcp、443/tcp（または割り当て）|`/data/caddy`（証明書）、`/data/www`（ro。イメージから同期）|`cap_add: [NET_BIND_SERVICE]`、`secrets: [dns_token]`|

- `restart: unless-stopped`。`logging: {driver: json-file, options: {max-size: 100m, max-file: 7}}`。
- `secrets`：`db_password`（/data/secrets/db_password）、`kek`（/etc/family-talk/secrets/kek。/data の外）、`backup_password`（/data/secrets/backup）、`dns_token`（/etc/family-talk/secrets/dns_token）。
- `depends_on`：api と worker は postgres の `service_healthy`。caddy は api の `service_healthy`（起動の順。第1章 7.1）。
- sfu が host のネットワークである理由：UDP の広い範囲と TURN のポートを NAT の変換なしに扱い、性能と ICE の候補の正しさを保つ（調査 I-07）。
- 内部の通信：api ↔ postgres、worker ↔ postgres、caddy → api（HTTP）、api → sfu（host の 7880。内部の API の鍵）、sfu → api（Webhook。sfu は host のネットワークなので、api が host の loopback に出した `127.0.0.1:8080` の `/internal/sfu/webhook` へ POST する。認証は SFU の鍵による JWT）、caddy → api（forward auth `/internal/auth`。地図と手順書の認証）。caddy は `/internal/*` を外へ出さない（404）。全体実装設計書 2.1。

## 4. 設置の流れ（DD-11-2、DD-11-3）

|順|操作|`ft` の処理|
|---|---|---|
|0|Ubuntu 24.04 LTS 以上を入れ、`ft` を取得して検証（sha256、ビルド証明）|—|
|1|`sudo ft setup`|前提の確認（Docker と Compose の版、空き、CPU、RAM、TPM2 の有無、IPv6）。Docker がなければ公式の配布元の手順を表示（自動で入れない）|
|2|/data のディスクを選ぶ|LUKS2 の作成（新しいディスクかパーティション。既存のデータの警告）、TPM2 があれば `systemd-cryptenroll --tpm2-device=auto --tpm2-pcrs=7`、紙の回復鍵を表示して「書き留めた」を確認、crypttab と fstab、`RequiresMountsFor=/data` の drop-in|
|3|KEK|生成して /etc/family-talk/secrets/kek に。紙に表示して確認（「この紙を失うと一部の情報が読めなくなります」）|
|4|ドメイン|独自か無料の DDNS かの案内（費用）。名前を入力|
|5|DNS の提供者とトークン|提供者の選択（手順書の一覧）。ゾーン限定のトークンの作り方の案内。トークンを secrets に|
|6|回線の判定|5 の検出と形の選択。MAP-E なら割り当てポートの入力（図）。ポートの割り当て|
|7|.env と compose.yaml の生成|digest は Release の版の情報から。設定の要約を表示|
|8|起動|`docker compose up -d`。秘密の自動生成（第1章 7.1）、証明書の取得（DNS-01）、health の待ち（最大 5 分）|
|9|外からの確認|「携帯回線のスマートフォンで https://<ドメイン>[:ポート]/ を開いてください」。`ft doctor` の結果（名前の解決、証明書、ポートの待ち受け）|
|10|管理者の作成|リンクを表示（第3章 3.1）。カードの印刷は画面で|
|11|バックアップの置き場|「バックアップの置き場を決めましょう」（管理者の画面へ）。決まらないまま 7 日で知らせ|

- `ft doctor`：いつでも。回線の種別、ポート、DNS の A/AAAA、証明書の期限、health、ディスク、TPM の状態、Compose の版、イメージの digest の一致、時刻の同期（NTP）。結果は秘密を含まない。

## 5. 回線の分岐（DD-11-4）

|形|条件|HTTPS|通話|費用|手順書の要点|
|---|---|---|---|---|---|
|A 自宅・直接|グローバルの IPv4、または IPv6 のみで外から届く|443（ルーターの転送）|UDP 直接、TURN 3478/5349|0 円（ドメインを除く）|ルーターの転送の設定。IPv6 のみは iPhone と Android の回線が IPv6 であること（国内の携帯は概ね可）|
|B 自宅・MAP-E|IPv4 over IPv6 で割り当てポート（240〜1,008 個）だけ着信|割り当てポートの 1 つ（URL にポート）|TURN と SFU の TCP も割り当てポート、メディアの UDP は割り当ての範囲に縮める|0 円|ルーターの画面から範囲を読む（図）。80 は使えないので DNS-01|
|C 自宅 + VPS の中継|DS-Lite、事業者の NAT、携帯のホームルーター。データは自宅に置きたい|VPS の TURN が中継しても HTTPS は届かない → VPS の逆プロキシ（TCP の転送）で自宅へ（自宅から VPS へ常時の接続を張る。WireGuard または SSH の逆トンネル）|VPS の TURN（coturn）。メディアは VPS 経由|VPS 月 500〜1,500 円|VPS に `ft relay setup`。自宅の機械は VPS へのトンネルを張る|
|D VPS に全部|同上で、データを VPS に置いてよい|VPS の 443|VPS の SFU|VPS 月 1,000〜3,000 円 + ディスク|手順は A と同じ。LUKS は事業者の暗号化に依る（第12章 6.1）。明示に「VPS の事業者」|

- 検出：(1) 機械のインターフェースのグローバル IPv6 の有無、(2) ルーターの外部アドレス（UPnP の `GetExternalIPAddress`。対応しなければ利用者の入力）→ グローバル／100.64.0.0/10（事業者の NAT）／RFC 1918（二重の NAT）、(3) 事業者の方式の選択（一覧：光の主な方式、ケーブル、携帯のホームルーター）、(4) 形の提案と費用。外からの到達の自動の検査は行わない（外部のサービスへの送信になる）。
- SFU の外部 IP：`FT_EXTERNAL_IPV4/6` が auto なら、起動のたびに自分の名前を解決した結果（DDNS の後）を `rtc.node_ip` に設定する。STUN のサーバーは設定しない（OS の提供者の STUN を使わない。第12章 8）。
- 固定 IP の購入（月 770〜3,245 円）は A に含める案内。
- 「必ず動く」と書かず、形ごとの成否と費用を手順書に。

## 6. ドメインと証明書（DD-11-5）

- 名前：`<家族>.<ドメイン>` または無料の DDNS のサブドメイン。ワイルドカードの証明書は `*.<ドメイン>` と `<ドメイン>`（サブドメインを 1 つだけ使う場合も、将来の複数の家族のために）。
- caddy：ACME は DNS-01（`FT_DNS_PROVIDER` のモジュール、`dns_token`）。発行機関は Let's Encrypt。`FT_ACME_FALLBACK=true` で代替の発行機関も（規約は管理者が当事者。L-11）。有効期間の短縮（2027 年に 64 日、2028 年に 45 日）は自動更新で吸収。
- 証明書の共有：caddy の保存先（/data/caddy）を sfu が読む（同じ UID）。更新のたびに sfu に再読み込みの合図（worker が監視し、sfu の内部の API または再起動（通話がない時））。
- DDNS：worker が 5 分ごとに自分の外部アドレス（5）を提供者の API で A と AAAA に書く。失敗が 1 時間続けば知らせ。
- 期限の監視：worker が証明書のファイルを読み、14/7/1 日前と失効で知らせ。

## 9. バックアップと復元（DD-11-8）

### 9.1 取る

|項目|値|
|---|---|
|時刻|日次 3:00（設定）。更新の前にも|
|中身|`pg_dump -Fc`（stdin）、`pg_dumpall --globals-only`、/data/media、/data/config、/data/secrets、/data/maps（任意。既定は含めない）、/data/caddy（証明書。含める）|
|道具|restic（repository v2、圧縮 auto）。worker が実行（イメージに同梱）|
|置き場|ローカル（別のディスク、USB の HDD。パスを設定）、S3 互換（endpoint、bucket、アクセスキー。Versioning と Object Lock（governance、保持 ≥ 14 日）を要件。削除の権限を持たないキー）。両方を推奨（3-2-1 + 不変の 1 部）|
|保持|日次 7、週次 4、月次 6（`forget` は OR）。`forget --prune` 週 1。Object Lock の保持は prune の周期より長く|
|検証|`check --read-data-subset=10%` 日次（10 日で全量）。失敗は知らせ|
|復元の試験|月 1：一時の領域に最新を restore し、一時の postgres に pg_restore、表の数と最新のイベントの pos を本番と照合。結果を知らせ|
|整合|「暗号文は名前（ハッシュ）で書き終えてから DB に参照、参照が消えてから猶予（7 日）の後に GC」。pg_dump → media の順で取る。スナップショットは不要|
|鍵|restic のパスワード（自動生成。/data/secrets/backup と紙）、KEK（/etc と紙）。媒体には置かない|
|知らせ|失敗、検証の失敗、置き場が未設定で 7 日、置き場の空きが 10% 未満|

### 9.2 戻す（`ft restore`。新しい機械）

1. 設置の 0〜3（LUKS、KEK は紙から入力、.env のコピーがあれば使う）。
2. バックアップの置き場と restic のパスワード（紙）を入力 → 最新（または選んだ）のスナップショットを /data に restore（media、config、secrets、caddy）。
3. postgres を同じメジャー版で空に起動 → `pg_restore`（globals → dump）。
4. 抹消の一覧（DB の `erasures` の表。バックアップより後の抹消は失われる → 14）を api が起動時に適用（DEK の破棄の再実行）。
5. 起動 → health → 全端末に `sync.gap`（第2章 11）→ DDNS と証明書の再取得（名前は同じ）。
6. 確認：ダッシュボードの最新のイベントの時刻。手順書に「バックアップの時刻より後の送信は失われます」。
- 版の違い：バックアップの版とイメージの版が違う時は、バックアップの版のイメージで起動してから更新する（ダウングレードは非対応）。

## 10. 更新（DD-11-9）

|段|処理|
|---|---|
|確認|worker が日次に版の情報（第13章）を取得。新しい版があれば知らせ（内容の要約）|
|適用（手動）|管理者の画面の「更新」または `ft update apply <版>`：通話中の確認（api の `/admin/health` の通話の数）→ バックアップ（9.1）→ イメージを digest で pull → cosign の署名とビルド証明の検証（`ft` が内蔵。失敗なら中止）→ .env の digest を書き換え → `compose up -d` → 起動時のマイグレーション（第1章 7.1）→ health（60 秒）→ 完了の知らせと版の表示|
|失敗|health が通らなければ前の digest に戻す。マイグレーションが進んでいれば（版の表で判定）バックアップから戻す（9.2）。知らせ|

|アプリ|ウェブアプリはイメージの中（次に開いた時に新しい。第8章 5）。Android は版の情報で自己更新（第9章 10）。互換の期間は第1章 DD-1-14|
|ダウングレード|非対応（手順書に明記）。戻すのはバックアップから|
