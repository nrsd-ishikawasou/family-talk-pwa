## 3. 配布の形（DD-11-1）

### 3.1 compose.yaml（初期値。digest は版ごと）

|サービス|イメージ|ネットワーク|公開|ボリューム|備考|
|---|---|---|---|---|---|
|api|`ghcr.io/<組織>/family-talk@sha256:…`（command: `serve`）|internal、edge|`127.0.0.1:8080`（host の loopback だけ。sfu の Webhook の到達用。外には出さない）|`/data`（bind、rw）|`user: 10001`、`cap_drop: [ALL]`、`security_opt: [no-new-privileges:true]`、`read_only: true`、`tmpfs: [/tmp]`、`secrets: [db_password, kek]`、`healthcheck: /health`、`extra_hosts: [host.docker.internal:host-gateway]`（sfu の API へ）|
|worker|同じイメージ（command: `work`）|internal|なし|`/data`（rw）|同上。`secrets: [db_password, kek, backup_password, dns_token]`|
|postgres|公式のイメージ（18 系。digest）|internal|なし|`/data/postgres`|`user: 10001`、`POSTGRES_PASSWORD_FILE`、`POSTGRES_USER` と `POSTGRES_DB` は `family_talk`（api と worker はホスト `postgres` のポート 5432 に TLS なしでつなぐ。第12章 4）、`healthcheck: pg_isready`、`shm_size: 256m`|
|sfu|公式のイメージ（1.13 系。digest）|`network_mode: host`|3478/udp（または割り当て）、50000〜60000/udp、7881/tcp。TURN の平文の TCP 5350 は host の内部の IP だけ（caddy から。第6章 3.1）|`/data/sfu`（設定）。証明書は持たない|`cap_drop: [ALL]`、`cap_add: [NET_BIND_SERVICE]`（443 を使う形の時）|
|caddy|本システムのビルド（DNS のモジュールと Layer4 の部品入り。digest。第14章 5.2）|edge、internal|80/tcp、443/tcp、5349/tcp（TURN/TLS。または割り当て）|`/data/caddy`（証明書）、`/data/www`（ro。イメージから同期）|`cap_add: [NET_BIND_SERVICE]`、`secrets: [dns_token]`、`extra_hosts: [host.docker.internal:host-gateway]`（`/rtc` と TURN を sfu へ）。Layer4 が 5349 で TLS を終え、`host.docker.internal:5350` へ PROXY protocol をつけて渡す（第6章 3.1）|

- `restart: unless-stopped`。`logging: {driver: json-file, options: {max-size: 100m, max-file: 7}}`。
- `secrets` は次のとおり。
  - `db_password`（/data/secrets/db_password）
  - `kek`（/etc/family-talk/secrets/kek。/data の外）
  - `backup_password`（/data/secrets/backup）
  - `dns_token`（/etc/family-talk/secrets/dns_token）
- `depends_on`：api と worker は postgres の `service_healthy`。caddy は api の `service_healthy`（起動の順。第1章 7.1）。
- sfu が host のネットワークである理由：UDP の広い範囲と TURN のポートを NAT の変換なしに扱い、性能と ICE の候補の正しさを保つ（調査 I-07）。
- 内部の通信は次のとおり（全体実装設計書 2.1）。caddy は `/internal/*` を外へ出さない（404）。
  - api と postgres の間、worker と postgres の間
  - caddy から api へ（HTTP）
  - api から sfu へ（`host.docker.internal:7880`。内部の API の鍵）
  - caddy から sfu へ（`/rtc` を `host.docker.internal:7880` へ）。sfu の 7880 は host の内部の IP でだけ待ち受ける（第6章 3.1 の `bind_addresses`）
  - sfu から api へ（Webhook）。sfu は host のネットワークなので、api が host の loopback に出した `127.0.0.1:8080` の `/internal/sfu/webhook` へ POST する。認証は SFU の鍵による JWT
  - caddy から api へ（forward auth `/internal/auth`。地図と手順書の認証）

### 3.4 ホストの要求の受け口（DD-11-15）

ホストの権限が要る操作は、コンテナが要求を置き、ホストの `ft` が行う。

|要求の種類|置く側|`ft` が行うこと|
|---|---|---|
|`update_apply {version}`|api（管理者の画面の「更新」）、worker（自動の更新）|10 の適用の順（通話中の確かめ、バックアップ、pull、検証、.env の digest、作り直し、health、失敗ならロールバック）|
|`update_rollback {}`|api（管理者の画面）|前の digest に戻す（10 の失敗の行）|
|`sfu_restart {reason}`|worker（SFU の鍵の交代。通話が無い時）|sfu の作り直し（`docker compose up -d --force-recreate sfu`）。行う直前に通話の数を確かめ、通話があれば待つ|

- 置き方：要求は JSON の 1 ファイル（`{v: 1, id, kind, args, requested_by, created_at}`。id は UUIDv7）。一時の名前で書いてから `/data/host/requests/` に改名する。
- 受け方：要求のディレクトリにファイルがある間、ホストの systemd が `ft host run` を起動する。
- unit は `family-talk-host.path`（`DirectoryNotEmpty=`）と `family-talk-host.service`（deploy）。
- `ft` は要求を古い順に 1 つずつ行う。結果（`{id, ok, code, finished_at}`）を `/data/host/results/<id>.json` に書き、要求を `/data/host/done/` に移す。ディレクトリが空になると止まる。
- 確かめ：`ft` は種類と引数の形を確かめ、決まった種類でなければ行わずに結果を誤りにする。`update_apply` の版は署名とビルド証明を検証する（第13章）。同じ id の要求は 1 回だけ行う。
- 結果の読み：api と worker は結果のファイルを読み、`update_state` と知らせに反映する（srv-admin `HostRequests`）。
- done と results は 30 日で消す（`ft host run` の最後）。

## 5. 回線の分岐（DD-11-4）

## 6. ドメインと証明書（DD-11-5）

### 9.2 戻す（`ft restore`。新しい機械）

1. 設置の 0〜3（LUKS、KEK は紙から入力、.env のコピーがあれば使う）。KEK は、戻したバックアップの DEK を包んだ KEK の紙を入力する。`ft` は下の 3（`pg_restore`）の後に、DEK の `kek_id` と入力した KEK の id を比べる。合わなければ、合う紙の id の先頭 8 文字を示して入力を求め直す（第12章 6.2）。
2. バックアップの置き場と restic のパスワード（紙）を入力する。最新（または選んだ）のスナップショットを /data に restore する（media、config、secrets、caddy）。
3. postgres を同じメジャー版で空に起動し、`pg_restore` する（globals、続いて dump）。
4. 抹消の一覧（DB の `erasures` の表）を、api が起動時に適用する（DEK の破棄の再実行）。バックアップより後の抹消は失われる（14）。
5. 起動、health、全端末への `sync.gap`（第2章 11）、DDNS と証明書の再取得（名前は同じ）の順に進む。
6. 確認：ダッシュボードの最新のイベントの時刻。手順書に「バックアップの時刻より後の送信は失われます」。

- 版の違い：バックアップの版とイメージの版が違う時は、バックアップの版のイメージで起動してから更新する（ダウングレードは非対応）。

## 11. 監視と知らせ（DD-11-10）

- `/health`（無認証。第2章 5.11）の形は次のとおり。秘密は含めない。503 なら本文に理由の分類を入れる。

  ```text
  {status, checks: {postgres, sfu, caddy_cert_days, disk_free_pct, worker_last_job_at, ddns_last_ok_at, mode}}
  ```

- status の値：
  - `ok`：確かめが全部通る（200）。
  - `degraded`：sfu に届かない、worker の最後の仕事が 15 分（monitor の周期の 3 倍）より古い、証明書・ディスク・DDNS の値が取れない、のどれか（200）。
  - `setup`：設置の前と初回（200）。
  - `readonly`：読み取り専用（503）。`down`：停止、または postgres に届かない（503）。
- 503 の時は `reason` に分類を入れる：`stopped`、`postgres`、`migration`、`capacity`、`storage`、`restore`（後の 4 つは `SRV-001` の理由と同じ）。
- 読み取り専用を 503 にするのは、更新の手順（10）が health でロールバックを決めるため。
- checks の型：
  - postgres と sfu は真偽。caddy_cert_days と disk_free_pct は整数。
  - worker_last_job_at と ddns_last_ok_at は RFC 3339 の時刻（まだ無ければ null）。
  - mode は回線の形（A〜D。値が取れなければ設定の server.mode）。
  - 外への確かめは並行に行い、各 2 秒で打ち切って偽にする。
- `/metrics`：OpenMetrics の形式。`FT_ADMIN_BIND=127.0.0.1` に限る。opt-in（既定は無効）。
- 知らせの種類、宛先、時期は第7章 9 の表が正。本章の監視（worker の monitor）がその表の事象を見つけて出す。
- サーバーが止まっている間：端末は「サーバーにつながりません」を示しキューに保持（第1章 7.12）。管理者に知らせる経路はない（第1章 T-7。手順書に「家族が気づいたら連絡」）。

- 管理者の画面の「ログ」（`GET /admin/logs/summary`）は、api と worker が記録したエラーの番号ごとの件数を日ごとに示す（28 日）。コンテナの中の api は Docker のログを読めないため、各プロセスが 1 分ごとに DB の `log_counts` に件数を足す。本文と秘密は含まない。

### 13.2 廃棄（`ft disk dispose`）

1. 最新のバックアップと復元の試験の確認（30 日以内）。2. 家族のサーバーの停止。3. LUKS のヘッダのキースロットの全消去（`cryptsetup erase`）とヘッダの上書き（NIST SP 800-88 Rev.2 の Cryptographic Erase）。4. 可能なら ATA Secure Erase の案内。5. KEK と紙の扱い（新しい機械に移るなら残す）。

## 14. 失敗の扱い

|失敗|扱い|
|---|---|
|TPM の状態が変わり解錠できない（OS の更新、ハードの交換）|紙の回復鍵で解錠。`ft doctor` が TPM の再登録を案内|
|DNS-01 が失敗（トークンの期限、提供者の障害）|caddy が再試行。知らせ（1 時間）。既存の証明書で続く（期限まで）|
|DDNS の失敗|知らせ。古いアドレスの間は届かない|
|外からの到達の確認に失敗|`ft doctor` の案内（ルーターの転送、MAP-E の範囲、形の変更）|
|バックアップの置き場が満杯・切断|知らせ。もう一方の置き場で続く|
|復元の試験の失敗|知らせ（赤）。手順書「バックアップを取り直す」|
|更新の検証（署名・ビルド証明）の失敗|中止。知らせ。手順書「NRSD の公開の指紋と照合」|
|更新の後に health が通らない|前の digest に戻す。マイグレーション後ならバックアップから|
|復元の後にバックアップより新しい抹消が失われた|`erasures` の表がバックアップにない分は再実行できない（H-11-2）。手順書に「抹消は復元の後に再度」|
|ディスクが壊れた|バックアップから（9.2）。SMART の警告があれば事前に知らせ|
|時刻がずれた|知らせ。手順書（NTP）|
|Compose の版が古く compose.yaml を読めない|`ft setup` が 2.24.6 の範囲の機能しか使わないので起きない。起きれば `ft doctor` が版を表示|

## 15. 本章で宣言する既知の制約

|番号|既知の制約|理由|緩和|
|---|---|---|---|
|H-11-1|DS-Lite と事業者の NAT の家庭では VPS（または固定 IP）なしに成立しない|回線の方式（I-05）|C と D の形、費用の明示|
|H-11-2|バックアップから戻すと、バックアップの時刻より後の送信と抹消が失われる|日次のバックアップ|手順書の明示。復元の前の確認|
|H-11-3|家族のサーバーが止まっている間、管理者に知らせる経路がない|外部の監視を置かない|手順書|
|H-11-4|機体ごとの盗難には TPM の無人解錠が効かない|第12章 H-12-5|—|
|H-11-5|外からの到達の確認は利用者の携帯回線の端末に依る|外部のサービスを使わない|`ft doctor` と手順|
|H-11-6|全管理者と機械のログインの両方が失われると戻せない|第1章 21|引き継ぎの一覧、紙の確認|

［要実測］の事項は次のとおり。

- TPM2 の PCR 7 とカーネル引数
- MAP-E での TURN と SFU
- UPnP の外部アドレスの対応
- restic と Object Lock
- 復元の試験の所要（1 TB）
- 設置の所要時間（技術者でない管理者）
