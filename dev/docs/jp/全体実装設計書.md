## 2. 実行時の形

### 2.1 プロセス（サーバー側）

|プロセス|イメージ|役割|起動|由来|
|---|---|---|---|---|
|api（`ft serve`）|本システム|HTTP の API、WebSocket の hub、`/sync`、`/up/*`、静的でない配信（manifest、家族のアイコン、disclosure）、SFU の Webhook の受け口、forward auth。**1 プロセス、複製しない**|Compose（postgres の healthy の後）|第1章 4.1、第2章|
|worker（`ft work`）|同じイメージ|仕事のキュー（2.3）。利用者の要求に応答しない|Compose（postgres の healthy の後）|第1章 4.1|
|postgres|公式のイメージ（18 系）|全記録（添付の中身を除く）|Compose|第1章 4.1|
|sfu|SFU の公式のイメージ（第14章 5.2）|通話の中継と TURN。host のネットワーク|Compose|第6章 3.1、第11章 3.1|
|caddy|本システムのビルド（DNS のモジュール入り）|TLS、静的、逆プロキシ、forward auth|Compose（api の healthy の後）|第11章 3.1|
|`ft`（host モード）|同じバイナリを /etc/family-talk/ft に置く（静的リンク、CGO なし）|setup、doctor、restore、update、keys、disk、relay、logs、admin create-link|管理者（sudo）|第11章 4、第14章 5.1|
|`ft host run`（host モード）|同じバイナリ|ホストの要求の受け口（第11章 3.4）：`/data/host/requests/` の要求（`update_apply`、`update_rollback`、`sfu_restart`）を 1 つずつ行い、結果を書く|systemd の path unit（`DirectoryNotEmpty=`）|第11章 3.4、DD-11-15|

- 決定：Go のバイナリは 1 つ（`ft`）。サブコマンドで役割が決まる（`serve`、`work`、`migrate`、`admin`、`setup`、`doctor`、`restore`、`update`、`keys`、`disk`、`relay`、`logs`、`version`）。イメージの `ENTRYPOINT` は `ft`。理由：api、worker、host の道具が、同じ設定の読み方・同じ記録の型・同じ秘密の扱いを持つ（第1章 7.1、第11章）。host モードは Docker、LUKS、systemd を呼ぶ分だけが違う。
- 決定：api は 1 プロセス 1 台。WebSocket の hub はプロセスの中の表（端末から接続への対応）。複製しない理由：家族のサーバーは 1 台（第1章 DD-1-3）で、推奨の機械で 20 人・60 端末の接続は 1 プロセスで足りる（第1章 14.1）。複製が要る時は 2.4 の NOTIFY の経路がそのまま使える（hub を複数にしても配信は DB の feed が正）。
- 決定：sfu（host のネットワーク）から api への Webhook の経路。api は `ports: ["127.0.0.1:8080:8080"]` で、host の loopback にだけ内部ポートを出す。sfu は `http://127.0.0.1:8080/internal/sfu/webhook` に POST する（第11章 3.1 が本書に委ねた点。第11章 18 への改訂 15）。Webhook の認証は SFU の API 鍵による JWT（`Authorization`）を api が sfu の鍵（第12章 10）で検証する。caddy は `/internal/*` を外へ出さない（Caddyfile で 404）。
- 決定：caddy の forward auth（地図、`/dl/manual/`、`/maps/`）の設定は次のとおり。api は Cookie のセッションを検証して 200／401 を返すだけ（本文なし）。

  ```text
  forward_auth api:8080 { uri /internal/auth; copy_headers X-User-Id }
  ```

- 決定：api と worker の間に直接の通信は無い。worker への依頼は `jobs` 表（2.3）、worker から端末への配信は feed + NOTIFY（2.4）。理由：記録の書き込み担当を 1 つの経路に保ち、プロセスの死で依頼が失われない。

### 2.4 イベントの配信の経路（サーバー側）

- 決定：イベントは 1 つのトランザクションで、`events`（または `receipts` 等の持ち主の表）と `feed`（利用者ごとの pos。4.1）に書く。コミットの後に `NOTIFY ft_feed, '<user_id>'` を送る。api の hub は `LISTEN ft_feed` を 1 本持ち、通知を受けた利用者の接続中の端末ごとに「最後に送った pos より後の feed の行」を読んで WebSocket に流す。worker が書くイベント（予約送信、知らせ、誕生日、システムの知らせ）も同じ経路で api に届く。
- 理由：api と worker の 2 プロセスが同じ hub を要し、hub の状態を記憶の上だけで持つと再起動で配信が抜ける。feed が正であれば、hub は「追いつく」だけでよく、`/sync` と同じ読み方になる（第2章 5.9）。
- 利用者ごとの pos の採番：`feed_cursor(user_id, next_pos)` の行を `SELECT ... FOR UPDATE` して採る。同じ利用者への同時の書き込みは直列になる。トークの順序は、トークの行の更新で直列にする（第1章 10.5）。
- `room.typing`、`ping`、`pong` は feed に書かず hub の中だけ（第2章 6.2）。
- feed の行はフレーム（第2章 6.1）の id と、`room.*` なら room_id を持つ。`room.event` の payload は feed に写さず、hub と `/sync` が送る時に srv-rooms から引く（取り消しと退出を反映し、暗号文を受け手の数だけ複製しない）。他の 17 種は書く時の payload を feed に持つ。

### 2.5 端末の中の排他（ウェブ）

- 決定：MLS の状態（グループごと）、鍵バンドル、端末の鍵は IndexedDB が正。画面は記憶の上のコピーを持つが、`BroadcastChannel ft-mls` で「グループ X が変わった」を受けたらコピーを捨てる。画面と SW はどちらも次の順で触る。
  1. Web Locks `mls:<group_id>` を取る
  2. 読む
  3. 操作する（復号、暗号化、Commit の適用）
  4. 書く
  5. 放す
- 決定：IndexedDB の書き込み全部（イベント、キュー、設定）は Web Locks `db` で直列化する（第8章 3.4）。読み出しは錠なし。
- 決定：SW の push の処理は `event.waitUntil` の中で 10 秒の期限（第7章 5.1）。期限が来たら汎用の本文を出す。`showNotification` は必ず 1 回呼ぶ（iOS の「通知を出さない受信」の規則。第7章 R-7-2-1）。

### 2.7 失敗の扱いの一貫した形

- 決定：サーバー側の失敗は `Event`（エラーコード表の行。`code`、`status`、`retryable`、`params`）と `Fault`（想定外。panic の回収と不変条件の既知の制約）の 2 つだけ。`Event` は RFC 9457 の形で境界に出る（第1章 10.3）。`Fault` は `SRV-003` の形で返し、記録に書き、要求を止め、書きかけを残さない（トランザクションの rollback、一時の名前のファイルの削除）。プロセスは落とさない（他の要求が続く）。worker の `Fault` はその仕事を失敗にし、他の仕事は続く。
- 決定：ウェブの失敗は `AppError{code, params, retryable}` の 1 つの型。境界から来た `Event`、端末の中の失敗（保存、権限、復号）、JS ブリッジのエラーの全部をこの型に写す。画面は `code` から文言の鍵 `err.<code>.what` と `err.<code>.next` を引く（第10章 9.2）。未登録の `code` は `err.unknown` の文言（「問題が起きました」+ 番号）。
- 決定：シェルの失敗は、JS ブリッジの `{id, ok: false, error: {code, params}}` で WebView に返す。シェルの中では記録だけ（本文を含めない。第9章 4.2 `log`）。
- 試験の決定：`api/errors.yaml` の各行に `test` の欄（L1 の試験の名前）を置く。`tools/errors_check` が、エラーコード表と試験のコードの名前の一致を見る（T-L2-05、T-L1-13）。

### 2.8 試験のための差し替え（サーバー側）

- 決定：サーバー側で外と OS に触れる物は、全部 `Deps`（srv-common）の interface で差し込む。
  - `Clock`：壁の時計。試験は固定と進み
  - `Rand`
  - `PushTransport`：Web Push の中継への POST。試験は手元の受け口 E-6
  - `SfuAdmin`：ルームの削除。SFU は設定と鍵を読み直せないので、読み直しは再起動（ホストの要求の受け口。第11章 3.4）。トークンの発行は鍵だけで足り、srv-calls の中で行う。Webhook の受け口は試験が偽の sfu から叩く
  - `Fetcher`：URL の代理。試験は手元の HTTP
  - `DnsProvider`：DDNS
  - `Restic`：バックアップ。試験は手元のリポジトリ
  - `Docker`：`ft` の host モード。試験は記録だけの偽物
  - `Luks`、`Systemd`
  - `ReleaseSource`：version.json とイメージの digest。試験は手元の HTTP
  - `MapSource`：地図のデータの供給元からの切り出し。試験は手元の小さな PMTiles
- L1 は本物の postgres（コンテナ）と本物のファイルの保存（一時のディレクトリ）を使い、上の interface だけを差し替える。
- 決定：ウェブの差し替えは次のとおり。
  - `Platform`：JS ブリッジの有無、通知、保存、回線の種類、共有、ファイルの選択（web-shell）
  - `CryptoProvider`：MLS の一次・二次の切り替え（web-crypto）
  - `MediaRuntime`：Worker と主スレッドの切り替え（web-media）
  - `Transport`：fetch と WebSocket。L3 は fixtures を返す偽物、L4 は本物
  - `Clock`

### 4.5 版と移行の持ち主

- DB のスキーマの版は tern の番号（srv-store `migrations/`）。移行のファイルは持ち主のブロックが書き、srv-store のディレクトリに番号で並ぶ（1 つのディレクトリ）。ブロックの境は、番号の範囲ではなくファイル名の接頭辞 `NNN_<ブロック>_<名>.sql` で示す。起動時に `ft migrate`（`serve` が先に呼ぶ。第1章 7.1）。失敗は読み取り専用（I-9）。
- JSON の `schema` の版（`ft.event.*`、`ft.content.*`、`fkb/*`）は api/ が正。古い版を読む処理は api（平文の欄）とウェブ（中身）の両方に置く（第1章 8.3）。
- 端末の IndexedDB の版は Dexie の `version(n)`（web-core `Db`）。upgrade はコピーを捨てて正本から取り直すことを許す（送信のキューと鍵だけは必ず移す）。

### 4.6 鍵のバックアップの中身（第12章 5.6 の委任を本書で確定）

- 決定：端末は epoch ごとに「履歴の秘密」を `fkb-history/1` の `ciphertext` に置く。欄は `epoch`、`tree_hash`、`encryption_secret`、`sender_data_secret`、`confirmed_transcript_hash`。置く前に、鍵のバックアップの鍵（第12章 5.4）による AES-256-GCM で暗号化する。新しい端末はこれを復号し、`MlsEngine.importHistoricEpoch(group_id, secrets)` で「復号専用の epoch の状態」を作る。その epoch の PrivateMessage の復号では、秘密木を `encryption_secret` から再構成する。鍵は、送信者の leaf の index と generation から導く（RFC 9420 の 9 節）。
- 一次の実装（TypeScript）は内部の型（秘密木、key schedule）を公開しているとみる【未確認：版 1.x の公開の範囲】。公開していなければ vendoring（MIT）して `importHistoricEpoch` を足す。二次の実装（Rust の WASM）は過去の epoch の注入を持たないため、履歴の復号は一次だけが担う（`MlsEngine.capabilities.historic = false`）。二次を一次に昇格させる時は、この機能の実装が条件。T-L3-01 で確かめる。
- 理由（第12章 5.6 の「履歴の鍵から導く形ではなく秘密木の根」を守る）：本文を二重に暗号化しない（暗号文の大きさと送信者の処理を増やさない）。注入の口は MLS の外側の仕組みであり、プロトコルの wire format を変えない。

### 5.2 認可の表の生成

- 決定：第2章 5 の各経路の「認可」の欄は、openapi.yaml の `x-authz` に置く（値と `x-authz-rule` の名前は第2章 10 の表）。
  - srv-boundary は起動時、全 operation が `x-authz` を持つことを確かめる（無ければ `Fault` で起動しない。I-12）。
  - 認可の判定の実装は srv-boundary の 1 か所。
  - ただし path や本文に入るトークンは、それを使い切る操作（srv-identity）が同じトランザクションの中で確かめる。対象は `setup_token`、`invite_token`、`reset_token`、`device_code`。確かめと使い切りを分けると、同じトークンの同時の 2 回の使用が通るため。srv-boundary はその経路を通し、形は要求の検証で確かめる。
  - `internal` はネットワークの側で守る。caddy は `/internal/*` を外へ出さず、api の 8080 は Compose の internal とホストの 127.0.0.1 だけで受ける。

### 5.3 線上の失敗の形

- RFC 9457 + `code`、`retryable`、`params`（第1章 10.3、第2章 9.1）。`params` の型は errors.yaml の行が持ち、ウェブの `AppError` とシェルの `BridgeError` はそれを写す（5.1 の生成）。

### 5.4 fixtures（試験の代わりの応答）

- 決定：ウェブの L3 の試験が境界の代わりに返す値は、手で書かない。L1 のシーケンスの試験が、実際の応答とイベントを書き出す。置き場は `dev/generated/fixtures/<operationId>.json` と `fixtures/events/<type>.json`。L3 はその物を読む。揺れる欄（識別子、日時、ハッシュ、暗号文）は、書き出す時に固定の値に置き換える。全 operation に fixture があることを試験で見る（無ければ赤。試験設計書 D-4）。
- 暗号文の fixture：L1 は本文を知らないので、L3 の暗号の試験（T-L3-01〜02）は自分で鍵を作って暗号文を作る。fixtures の暗号文は「形の見本」であり、L3 の復号の試験には使わない。

### 5.5 版

- 境界の版（`boundary`）は openapi.yaml と asyncapi.yaml の `info.version` に同じ値（第2章 10）。CI は 2 つの値の一致と、oasdiff の破壊の検出（T-L2-04）。

### 6.2 L1 の形

- 1 本のシーケンス（サーバー側の分）に 1 つの試験の関数。`ft serve` のプロセスは立てない。srv-boundary の `http.Handler` を `httptest` で組み、`Deps`（2.8）の偽物と本物の postgres を使う。端末の役は試験のコードが演じる（Cookie、WebSocket、`/sync`）。暗号文は試験のコードが「本物の形の乱数」で作る（サーバーは中身を読まない）。
- 分岐（各章の「失敗の扱い」の事象）は同じファイルの中の別の試験。worker の仕事は `Runner.RunOnce(kind)` を手で回す（待たない）。
- 各試験の終わりに、共通の後始末で確かめる：`jobs` に `running` が残らない、`/data/media` に `.part` が残らない、feed の pos が連続、平文検査（6.4）が 0。
- fixtures（5.4）は L1 の各 operation の応答から書き出す。

- 道具は全部 Python 3.12（`python3 -m tools.<名>`）。実行環境を 1 つにして、CI の段と依存の固定を 1 つにするため。Python の依存は `tools/requirements.txt` に置く。中身は PyYAML、JSON Schema 2020-12 の検証器、ワークフローの検査の zizmor、REUSE の検査の reuse。推移的な依存までハッシュで固定し、`pip install --require-hashes` で入れる。
- 検査の Node の道具（Spectral、AsyncAPI CLI、markdownlint、textlint）は `tools/node/` に置く。推移的な依存まで package-lock.json の完全性のハッシュで固定し、`npm ci` で入れる。道具の試験は `tools/tests/`（L0）。
- Git の外の一覧（`tools/forbidden_words.txt`、`tools/plaintext_markers.txt`）は `.gitignore` に載せる。開発機では開発者が置き、CI は secret から書き出す。一覧が無ければ道具は赤（「一覧が無い」）を返す。

### 6.4 平文検査の組み込み

- 決定：L1 と L4 の試験のデータの本文は「固有の語」を含む（`tools/plaintext_markers.txt` から。例：乱数の 12 文字の語を本文と添付の中身に埋める）。試験の終わりに、`tools/no_plaintext` が次を走査する：DB（`pg_dump` の平文）、`/data/media`、api と worker の標準出力、バックアップのリポジトリ。語の一覧は Git の外（CI は secret として渡す。語が漏れても意味は無いが、走査の対象に語の一覧そのものが混ざらないため）。

### 6.5 L6 と各段の合格の判定

- 判定は試験設計書 第3章（本書は段と置き場だけ）。実測（T-M）の結果は `dev/docs/jp/手順/試験の記録.md` に書き、第16章 6.1 の表に「確認済み（日付）」を書き戻す。

- restic：worker のイメージに、公式の静的なバイナリを版と SHA-256 で固定して同梱し、CLI として呼ぶ。restic の本体は Go の `internal/` の下にあり、別のモジュールから部品として読み込めないため（第14章 5.4）。
- pg_dump：postgres のイメージの `docker exec` ではなく、worker のイメージに同じメジャー版の `pg_dump` を同梱する。基盤に合わせた静的ビルドの可否は【未確認】。できなければ、`ft` の host モードから `docker compose exec postgres pg_dump` を呼ぶ経路に切り替える。
- caddy のイメージ：caddy + DNS の提供者のモジュール群（第11章 6）+ Caddyfile の雛形。
- 予算：本システムのイメージ 150 MB 以下、caddy のイメージ 60 MB 以下（最初のビルドで実測し超えたら絵柄と OCR の学習データを別の取得にする）。

### 7.3 配布物に対する試験

- L5（試験設計書 第3章 5）。`tools/dist_check` は組んだイメージを `docker create` + `docker cp` で読む。Compose の起動は CI の KVM なしで可（postgres、api、caddy）。sfu は host のネットワークなので、CI では `network_mode` を bridge に上書きした試験用の compose で起動だけを確かめる。
